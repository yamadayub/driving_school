## 1. 申し送り項目ごとの対応

### D-1【RV-P3D-002】ワイヤ契約の統一

**`form-submission.md` §4.2**

1. **「または遅延した 201」を削除**し、注記 2 として整理した:
   > 遅延した 201 は Tier C ではなく **Tier A（遅延成功）**である。サーバーは待ち上限（2秒）内に空けば `201` を返す。**待機 UI を出すのは `202` を受け取ったときだけ**。

   これを状態設計（§2）にも落とし、`queued` への遷移条件を「`202` を受け取ったときのみ」と明記した。「または」で2つの応答を並べたままだと、実装者が「201 でも待機 UI を出す」か「202 を 201 と同じに扱う」のどちらかに倒れる。

2. **Tier 表を仕様 §4.11 と同じ列構成（Tier / 契機 / 応答 / 本文 / UI）に揃え**、相互参照を明示した:
   - 冒頭に「本表は仕様 §4.11 と同一の契約であり、片方だけを変えてはならない」旨と、参照先（§4.11 / AC-RL-1 / AC-RL-12 / F-010・F-009 の Error Responses）を記載。
   - Tier B の契機に **Cookie 不在・署名不正・期限切れ / 送信間隔下限未満 / ハニーポット非空**を明記（従来は「疑わしい / 逼迫の兆候」だけだった）。
   - Tier C の契機を「セマフォ（共有軸）の上限に到達し、**サーバー側の待ち上限（2秒）内に空かなかった**」に精緻化。
   - Tier D の契機を「**発信元軸・フォームセッション軸**（＝攻撃者自身に閉じた軸）の窓上限」に明記し、本文に `{ retryAfterMs }` を追加（従来は `Retry-After` ヘッダのみ書いていた）。
   - Tier A に `200`（冪等再送）を追加。

3. **注記5点を追加**（仕様 §4.11「契約のルール」と同一）:
   - **`200 + challengeRequired` は使わない**。UI は **HTTP ステータスのみで Tier を判別してよい**。
   - 遅延 201 = Tier A（上記）。
   - **`Retry-After` / `retryAfterMs` はサーバーが返し ±20% のジッタを含む**。**クライアントは独自のバックオフ・ジッタを重ねない**。同一条件で2回取ると値が異なるのは正常であり、**UI がこれを異常として扱ってはならない**。
   - **Tier B の表示は降格理由を出さない**（4経路で完全に同一の見た目）。
   - **テストフック**（`CI=1` かつ非本番で `retryAfterMs` を 1〜2秒に固定）は仕様に採用済み。

4. あわせて §1 のシーケンス図を Tier 表記に書き換え、§4.4（待機中の振る舞い）にジッタの前提を追記した。

**`license-upload.md` §4.3 — 4 Tier に統一（202 の受け側を新設）**

- 従来は「403 = 認証協力 / 429 = 待機UI」の 2 種しか無く、**Tier C（202）の受け側が抜けていた**。`POST /api/uploads/license` / `DELETE /api/uploads/license` も公開変更系であり同一契約が適用されるため、表を **B / C / D + 400 / 415 / 通信断 / 500** の形に揃えた。
- **「共有軸の枯渇で 429 は返らない」**ことを明記（429 を受け取ったなら自分に閉じた軸の上限である）。
- スロット状態に `queued` / `cooldown` を追加し（§2 の状態表・§7 の `SlotState`）、**待機中も `File` を捨てない**ことを明記。
- **Tier C/D の自動再試行と §4.2 の再発行上限（3回）を同一カウンタで数えないこと**を明記した。前者は「まだ上がっていない写真の発行の再試行」、後者は「上がった写真の期限延長」であり、混ぜると再発行上限が発行失敗で食い潰される。

### D-6【RV-P3D-S04】自動再発行の上限と非表示タブでの停止

**`license-upload.md` §4.2** に「自動再発行の上限と、非表示タブでの停止（SPEC-009 / AC-009-11 で確定）」を新設。

- **背景（なぜ上限が要るか）**を記録: 上限が無いと 8分ごとに発行2回 + PUT 2回×5MB が永久に繰り返され、**正規利用者が自分で自分をレート制限に到達させる**（本設計が善意で入れた救済策が別の受け入れ条件を壊していた、という診断ごと残した）。
- **1スロット最大3回** → 到達後は **`degraded`（縮退表示）**。「送信時に、お手数ですが写真をもう一度お選びください」+「今すぐ選び直す」。**Danger 色を使わない**（利用者の失敗ではない）。
- **`visibilityState === 'hidden'` の間は再発行 API を呼ばない**。表示は `uploaded` のまま変えない。
- **`visibilitychange` 復帰時に期限切れなら `failed`（`reason: "EXPIRED"`）**。
- **最悪ケースの発行回数が「2枚 ×（初回1 + 再発行3）= 8回」で頭打ちになる**こと、これが AC-RL-9 の実測入力であり **UI 側で上限を緩めると前提が崩れる**ことを明記。

**状態遷移（§2）への追加**: `Uploaded → Degraded`（上限到達）/ `Uploaded → Failed`（復帰時に期限切れ）/ `Degraded → Issuing`（手動）/ `Degraded → Empty` / `Degraded → [*]`（写真なしで送信）。

- **`Degraded` と `Failed` は別状態**であること（前者は「まだ有効な写真が付いている」）を明記。
- **抑止はタイマー側ではなく遷移の発火条件に置く**（タイマーを止めるだけだと復帰時にまとめて発火する実装になりうる）。

**§7 の型契約**: `SlotState` に `tokenExpiresAt`（`uploadTokenExpiresIn` 由来であることをコメントで固定）/ `reissueCount` / `degraded` / `queued` / `cooldown` を追加。判定を純関数 `shouldReissue({ tokenExpiresAt, now, reissueCount, visibilityState })` に切り出し、**`document` を直接読まず引数で受ける**ことを指定した（AC-009-11 がユニットテストを要求しているため）。

**§11 のテスト申し送り**: 項目 9（4回目の発行が起きず `data-state="degraded"`）/ 10（`visibilitychange` でネットワーク要求が発生しない・復帰時 `failed`）を追加。`data-state` の列挙も新状態に更新した。

**`form-submission.md` §4.4** の「タブが非表示のとき」に、**送信の自動再試行と写真の自動再発行は別ルールに従う**（前者は復帰時に即再試行、後者は hidden 中は呼ばない）ことを明記した。この2つは同じ `visibilitychange` ハンドラに書かれる可能性が高く、混同すると AC-009-11(b) が静かに壊れる。

### D-7【RV-P3D-S03】「削除する」ボタンの実体

**`license-upload.md` §5** の「削除 API の提案（S-5）」を「**削除 API（S-5 → 採用済み / SPEC-011）**」に書き換えた。

- **UI 文言は「削除する」のまま**（代替案「この申込には添付しない」への変更は不要）。
- API 契約を仕様の確定形で記載: `DELETE /api/uploads/license` / `{ objectKey, uploadToken }` / 成功 `204` / **理由を区別しない `403`** / **Tier B・C・D は他の公開変更系と同一契約（§4.3 がそのまま適用される）**。
- **「削除は即時に Blob オブジェクトを消す（orphan 回収バッチを待たない）」**を明記（申し送りの指示どおり）。
- IDOR にならない根拠（サーバーは受け取った `objectKey` を信頼せず `uploadToken` から DB を引く）を仕様の記述に合わせて記載。
- **消費済みトークンでは削除できない**（AC-009-10(c)）ことと、送信完了後にこのボタンが存在しないため矛盾しないことを明記。
- **Undo との関係**を明記: Undo は「削除された `objectKey` の復活」ではなく**保持している `File` からの再アップロード**であり、削除 API が即時に消す以上この区別は必須。
- §11 テスト項目 3 に「`DELETE /api/uploads/license` が `{ objectKey, uploadToken }` を伴って呼ばれること」を追加。

## 2. 申し送りに含まれていなかったが、照合の結果として修正した項目

### (A) `receiptNumber` が日次連番のまま残っていた（SPEC-013 / RV-P3D-N01）

**`form-submission.md` §6（完了画面）のワイヤフレームが `20260729-0042` という日次連番を表示していた。** 仕様は **SPEC-013 で `receiptNumber` を ULID 既定に確定**し、日次連番を明示的に廃止している（AC-010-5 に「連続発番した2つから受付件数を推測できない」検証が追加されている）。

**これは D-3 と完全に同型の欠陥である**——訂正済みの仕様に対して UI 設計に旧値が残り、Impl Agent がそれを一次入力にする。かつ受付番号は**完了画面で最も大きく表示する要素**であり、8+4桁 → 26文字はレイアウト設計そのものを変える。

修正内容:
- ワイヤフレームを ULID 例（`01JZK8P4Q7M2NX5R3TVWY6B9CD`）に差し替え。
- **`tabular-nums` を使わない**（英字を含むため無意味）→ **等幅フォント + `letter-spacing`**。
- **Mobile では Display サイズに収まらない**ため **Title サイズ + `overflow-wrap: anywhere`**、または 4文字ごとの視覚的区切り。**区切りを入れる場合、コピーと読み上げの対象は区切りを含まない生の値**であること（`aria-label` に生値、コピーは state の生値）を明記。
- **Clipboard API フォールバック（`<input readOnly>`）は省略不可**（ULID は手入力での書き写しが現実的でない）。
- 電話口での読み上げ負荷という**トレードオフは仕様側で受容済み**である旨と、UI 側の緩和策（コピーボタンを目立たせる / 控えメールに同じ番号を載せる）を記録。
- §9 レスポンシブの「受付番号は `text-display`」を `text-title` + 折返し可に修正。
- §10 テスト項目 16 に「ULID 形式であること」「**コピーした値に視覚的な区切り文字が混入しないこと**」を追加。

### (B) `form-submission.md` §11 I-6 の回答が UI 挙動に影響する点

AC-010-4 の改訂（冪等照合を `idempotencyKey` **かつ** Cookie の `sid` の一致で行い、不一致なら `{ idempotent: true }` のみ返す）は、**UI から見ると「再送で `receiptNumber` が返らないケースが生まれる」**という変化である。回答欄に以下を記録した:

> 自動再試行・リロード後の再送は同一タブ = 同一 Cookie なので通常経路に影響しない。ただし **Cookie が期限切れ（30分）になった状態での再送は `receiptNumber` を受け取れない**ため、その場合は完了画面ではなく §5「保存失敗」相当の再送導線に留め、**受付番号を偽って表示しない**こと。

これを書かないと、`{ idempotent: true }` を成功とみなして**空の受付番号を表示する完了画面**が実装されうる。

### (C) `admin/login.md` が Tier 契約の対象と誤読されうる

`admin/login.md` §が「429応答時に『試行回数が多すぎます』を表示」と書いており、これ自体は正しい（`tech-stack.md` §4.5 の決着注記により**管理者ログインは §4.11 の対象外**で、P2 の実装を維持する）。しかし Tier 契約を横展開する実装者が「429 は禁止されたはず」と読んで待機 UI を持ち込む恐れがあるため、**対象外であることと、その理由（母数が管理者1名でコストが釣り合わない）を1段落で明記**した。

### (D) `<input type="date">` の `max` を年齢下限から算出する記述（`application-form.md` §2.4）

§2.4 が「`min` / `max`（**年齢下限**・上限から算出）」としていたが、SPEC-007 が **判定基準をサーバー受信日（JST）に確定**したため、**クライアントのローカル日付で算出した境界を `max` にすると、サーバー判定では通る正規申込者がピッカー上で入力できなくなる**（日付境界・端末時計のずれ・海外からの入力）。

**`max` は「今日（未来日不可）」に留め、年齢下限は入力を止めずに `AGE_BELOW_MIN` のエラー表示で伝える**ことを明記した。エラーなら利用者は直せるが、**入力できない境界には打つ手がない**。

## 5. 次工程（Impl / Test）が特に見落としやすい点

順不同ではなく、**壊れたときの被害が大きい順**に並べた。

1. **`uploadUrlExpiresIn`(300) と `uploadTokenExpiresIn`(600) を混同しない**（`license-upload.md` §4.2）。混同すると 300秒ごとに 5MB×2 の再アップロードが走り、AC-009-5 が「唯一の帯域防御」と定めた発行数を無駄に消費する。**テスト項目 8 が落ちることで検出できる。**
2. **`sessionStorage` に写真関連値を書かない**（AC-008-3 (e)）。下書き保存が許可されたことで、`values` を丸ごと `JSON.stringify` して保存する実装が最も自然に書けてしまうが、**写真の state が同じストアに入っていれば (e) に抵触する**。写真 state は `useLicenseUpload()` のメモリに分離しておくこと。
3. **Tier の判別を HTTP ステータスのみで行う**（`form-submission.md` §4.2 注記1）。ボディのフィールド有無で成功判定する分岐を1つでも書くと、`200 + challengeRequired` を廃止した意味が消える。
4. **Tier B の4経路で画面表示を分岐させない**。「親切に理由を出す」方向の変更は、bot に判定基準を教えることと等価である。
5. **`retryAfterMs` にクライアント側のジッタ・バックオフを足さない**（サーバーが既に ±20% を加えている）。
6. **送信の自動再試行（復帰時に即再試行）と写真の自動再発行（hidden 中は呼ばない）を、同一の `visibilitychange` ハンドラで同じルールにしない**。
7. **完了画面で `{ idempotent: true }` のみの応答（`receiptNumber` なし）を成功として表示しない**（`form-submission.md` §11 I-6）。
