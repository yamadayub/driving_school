## 1. CR-001 — **クローズ**

### 1.1 更新窓が本番の呼び出し経路から到達可能になったか — **なった**

`app/(public)/apply/page.tsx:78-80`:

```ts
const now = Date.now()
const presented = verifyFormSessionValue(raw, process.env.FORM_SESSION_SECRET ?? '', now)
const hasSession = presented !== null && !isFormSessionRenewable(presented, now)
```

`:93` の `if (!hasSession && !issued)` が **「有効だが失効間近」でも発火する**ようになったので、
`GET /api/form-session` に当該状態の要求が届き、ルート側 `:147` の `isFormSessionRenewable` が
初めて意味を持つ。**判定は正典関数を呼ぶだけ**で、ページ側に「残り時間 < 10 分」のような式は
書かれていない（AC-RL-8 準拠 / 判定の二重管理なし）。

### 1.2 無限リダイレクトが起きない理由 — **実コードで成立している**

3 経路を自分で追跡した。

| 経路 | 追跡 |
|------|------|
| 失効間近 → リダイレクト → 発行成功 | ルートは `newFormSessionPayload({ now: at })` で発行するので `issuedAt = now`。`isFormSessionRenewable` は `issuedAt + MAX_AGE_MS - now < RENEW_BEFORE_MS` すなわち `1_800_000 < 600_000` = **false**。戻り先で `hasSession = true` → `:112` の `hasSession && issued` で `?fs` を落として終了。**ループしない** |
| 発行が拒否された（`rate-limited`） | ルートは 303 に `?fs=1` を付けて返す（`FORM_SESSION_ISSUED_PARAM`）。戻り先は `hasSession = false` だが `issued = true` なので `:93` の `!issued` で止まる。**ループしない** |
| 縮退で印が付いた | 発行自体は成功するので Cookie は届くが `verifyFormSessionValue` は `null`。`hasSession = false` / `issued = true` → 同じく `:93` で止まる。**ループしない** |

「更新窓 < Cookie 寿命」は `form-session-degraded-recovery.test.ts`「更新窓は Cookie 寿命より短い」が
定数レベルで固定しており、**1 経路目の前提が将来崩れれば赤くなる**。依存関係が閉じている。

### 1.3 pin は本物か — **本物である（空振りしない）**

`tests/unit/apply-page-contract.test.ts:184-219` は 2 段構えである。

```ts
const hasSessionExpression = source.match(/const\s+hasSession\s*=((?:[^\n]|\n\s{4,})*)/)
expect(hasSessionExpression![1]).toContain('isFormSessionRenewable')
```

- **import の存在だけを見ていない。** `hasSession` に**代入される式そのもの**を切り出している。
  テスト内のコメントに「`isFormSessionRenewable` を import したまま `hasSession` の式からは外す形が
  素通りする（**実測で確認した空振り**）」と記録されており、**空振りの検算が実施されている**。
- 継続行の取り込みを「インデント 4 以上」に限っているので、次の `const issued`（インデント 2）で
  確実に止まる。「次の `const` まで」のような広い窓を避けた判断も正しい。
- 実ソースに当てると `= presented !== null && !isFormSessionRenewable(presented, now)` が捕まる。

**申し送り 1 の「pin を 1 件足す」がそのまま実行され、しかも空振り検算まで行われている。**

## 4. テスト変更 2 件目の judge（e2e `expect.poll`）

### (a) 弱体化か — **弱体化ではない**

変更は `expect(...).toBe(false)`（瞬間値）→ `expect.poll(...).toBe(false)`（有界時間内の到達）。
重要なのは、**この性質はもともと瞬間値では表現できない**という点である:

- WebKit は `http://localhost` で Secure Cookie を受理しないので `hasSession` は常に false。
- したがってサーバー側の `?fs` 除去（`app/(public)/apply/page.tsx:112` の `hasSession && issued`）は
  **発火しない**（そしてこれは**意図された挙動**である。同 :116-120 が書いているとおり、
  `?fs=1` は Cookie をブロックしている環境で無限ループを止めるために**わざと残している**判定である）。
- 除去はクライアントの `history.replaceState`（`ApplicationForm.tsx` の `useEffect`）だけが担う。
  **`useEffect` はハイドレーション後**に走るので、`getByTestId(...)` の可視化とは順序が保証されない。

つまり旧アサーションは「**ハイドレーションが要素可視化より先に終わる**」という
**保証されていない前提**の上で偶然 green だった。`expect.poll` は
「有界時間内に除去される」という**実際に成立する性質**を書いたものであり、
仕様の記述としてむしろ正確になっている。

### (b) 測りたい性質は保たれているか — **保たれている**

守りたい欠陥は「`?fs=1` が**アドレスバーに残り続ける**」こと（RV-P3B-002）。
`expect.poll` は既定タイムアウト（`expect` タイムアウト）内に false にならなければ失敗するので、
**本物の退行（マーカーが消えない）は依然として赤くなる。** 緩んだのは「いつ消えるか」だけである。

### (c) `expect.poll` が本物の欠陥を隠していないか — **隠していない**

- 「サーバーが `?fs` を落とさない」こと自体は**設計どおり**（Cookie ブロック環境のループ回避）。
  WebKit-on-localhost はその環境を偶然再現しているだけで、製品欠陥ではない。
- クライアント側の除去が失敗するケース（JS 無効）は元々サーバー側で救われない設計であり、
  本テストの変更とは独立である。
- 同ファイルで RV-P3B-018 に対して既に確立した形に揃えており、**その場しのぎの `poll` ではない**。

### CR-001 による退行ではないという判断 — **正しい。自分でも検証した**

- **WebKit**: Secure Cookie が保存されないので `raw === null` →
  `verifyFormSessionValue(null, ...)` は `lib/form-session.ts:227` の `if (!value) return null` で
  即 `null` → `presented === null` の時点で `hasSession = false` が確定する。
  **`isFormSessionRenewable` は短絡評価で呼ばれもしない。** CR-001 の変更は WebKit の挙動に
  影響しえない。
- **Chromium / Firefox**（localhost を secure context として扱うので Cookie は保存される）:
  リダイレクト直後の Cookie は `issuedAt = now` なので `isFormSessionRenewable` は false。
  よって `hasSession` は変更前と同値であり、**リダイレクトのホップ数も増えない**。

したがって 3 ブラウザいずれでも CR-001 は本テストの挙動を変えない。
flaky の原因は**スイート全体の負荷下で顕在化した既存の race** であり、CR-001 由来ではない。

## 5. P3-c2 への申し送り

1. **SEC-067 本体（印による締め出しと自己維持）は未是正のまま P3-c2 へ渡る。**
   監査は「P3-c2 のブロッカーにしない / 重大度は Medium 据え置き / **非 Vercel 配備を選んだ時点で
   High（ブロッカー）へ昇格**」としており、この整理に同意する。
   P3-c2 は `uploads` で同じ Tier B 判定（`verifyFormSessionValue`）を使うので、
   **回復経路（`challengeToken`）の結線を P3-c2 のスコープに明示的に入れること。**
   自己維持は「印付き利用者が回復できる」ようになって初めて切れる——
   `hasVerifiedSession` では原理的に切れないことが実測で確定した。

2. **⚠️ E2E は WebKit でフォームセッション Cookie の経路を一度も通っていない。**
   本 judge の過程で確認した副産物である。WebKit は `http://localhost` で
   `__Host-`（Secure）Cookie を受理しないため、**WebKit の E2E は常に「Cookie 無し」経路**を
   走っている。P3-c2 の `uploads` は Cookie 軸（Tier B 判定）に依存するので、
   **WebKit の E2E は uploads の主要な防御経路を検証しない。**
   `?fs` のテストが `expect.poll` を必要とした理由そのものがこの事実であり、
   **P3-c2 で uploads の E2E を書く前に、E2E を HTTPS で回すか WebKit を明示的に対象外にするかを
   決めること**（黙って「3 ブラウザで green」と記録すると、実際には 2 ブラウザでしか
   測っていない防御を「測った」ことにしてしまう）。

3. `maxBodyBytes` を上げる際は、上げた値で `tests/unit/public-guard-body-stream.test.ts` を回すこと
   （設計文書 §1 の注記。既定値でしか測っていない）。

## 6. 良い点（P3-c1 全体の総括）

- **3 回のテスト検収と 2 回のコードレビューを通じて、指摘された欠陥がすべて同じ型
  （「測っていない継ぎ目」）に収束し、そのたびに一段深い継ぎ目が見つかった**——
  受け口の悪用（REV-P3C1-001）→ 受け口が呼ばれること（NEW-001）→
  呼び出し元がその状態を作ること（CR-001）→ **そもそも到達しない受け口**（監査 §1.5）。
  最後の 1 つは実装側と監査側が独立に見つけ、**どちらも「達成した」と言わずに訂正した。**
- **Impl / オーケストレーターがテストを直さずエスカレーションした**（NEW-004 の達成不能報告）。
  かつ、通すための抜け道（TTL を 9 秒に）を**テストが捕まえられないと知りながら却下した。**
  この 1 件は自動化された網では守れない性質のもので、判断の質がそのまま出ている。
- **訂正の仕方が一貫している。** 誤った記述を消さず取り消し線で残し、隣に実測付きの訂正を置く。
  「何を間違えたか」が次の単位へ引き継がれる形になっている。
