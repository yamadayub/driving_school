### 良い点（先に明記する）

1. **`lib/login-guard.ts` への意味論の切り出しが正しい。** `authorize` が `NextAuth({...})` の
   オブジェクトリテラル内にあり単体テストから読めない、という構造的制約を、
   「判定の意味論だけを純粋な関数モジュールへ出す」形で解いている（`lib/rate-limit.ts` が
   判定と永続化を分けたのと同じ流儀で、モジュール間の一貫性がある）。この切り出しが無ければ
   本レビューで指摘した RV-P25-001 も読み取れなかった。**設計の可検査性が上がっている。**
2. **`verify()`（scrypt）を直列化キューの外に置いた判断が正しい**（`lib/login-guard.ts:87-94`）。
   `serialize` が包むのは store 操作だけで、100ms かかる scrypt はキューに載らない。
   「レート制限の直列化がリクエスト処理を詰まらせないか」という懸念は**成立しない**。
   これは意識的にそうしたのでなければ偶然では成立しない配置である。
3. **`resolveClientIp` の有界性の担保が丁寧**（`lib/http-guard.ts:112-163`）。長さで足切りしてから
   1グループ単位の固定長パターンでのみ正規表現を使う構成で、ReDoS を作り込んでいない。
   `node:net` の `isIP()` を使わなかった理由（middleware/Edge から読める状態を維持し、P3 で
   レート制限を middleware 側へ寄せる選択肢を潰さない）も、将来の選択肢に対する正しい配慮。
4. **`withAdminMutation` の応答生成がファクトリ関数**（`app/api/admin/_guard.ts:44-47`）。
   RV-P2-009 で指摘した「`NextResponse` をモジュールスコープで共有すると body が一度しか読めない」
   問題を、新規コードでは最初から踏んでいない。
5. **E2E PT2-06 が「HTTP ステータス」ではなく「DB の実状態」を検証している**
   （`admin-authz.spec.ts` の各ケースが `withPrisma` で行の有無・title・status を確認）。
   「403 を返しつつ実は処理済み」を検出できる。`test.describe.serial` 指定も入っており、
   `createdId` を共有する設計が `fullyParallel: true` の下でも壊れない。

## 2. 新規指摘事項

### [RV-P25-001] グローバル上限を IP ゲートより前で消費するため、単一ホストが管理者ログインを恒久封鎖できる（SEC-021 の脅威クラスが未解決）

- **種別**: Security（可用性 / ロックアウト DoS）
- **重要度**: **Must Fix**
- **場所**: `lib/login-guard.ts:81-88`（global consume が ip ゲートより前）/ `auth.ts:58`（`LOGIN_GLOBAL_LIMITER` 100回/分）/ `auth.ts:44-50`（閾値の根拠コメント）
- **現状**:

```ts
// lib/login-guard.ts:81-88
if (limiters.global) {
  const global = await limiters.global.consume(LOGIN_GLOBAL_KEY, now)   // ← 全リクエストが先に消費
  if (!global.success) return denied(global.retryAfterMs)
}
const gate = await limiters.ip.peek(ipKey, now)                          // ← IP ゲートはこの後
if (!gate.success) return denied(gate.retryAfterMs)
```

  グローバル軸は**キー非依存の単一バケット**（`LOGIN_GLOBAL_KEY = 'credentials:global'`）で、
  **成功でも解放しない**（`:96-101` の reset 対象は ip / account のみ）。したがって:

  1. 攻撃者が単一ホストから毎分 100 リクエストを `/api/auth/callback/credentials` に投げる。
     CSRF トークンは `GET /api/auth/csrf` で誰でも取得でき、管理者のメールアドレスの知識も不要。
  2. 1分あたり 100 回で `LOGIN_GLOBAL_LIMITER` が枯渇 → 以降のウィンドウ内の**全ログイン試行**が
     `rate-limited` で拒否される。**正規管理者が正しいパスワードを入れても照合されない。**
  3. 攻撃者は毎分投げ続けるだけでよい。**恒久封鎖が成立する。**

  これは SEC-021 が指摘した脅威（「未認証の第三者が管理者ログインを恒久封鎖できる」）と
  **完全に同一のクラス**であり、変わったのは攻撃コスト（5req/15分 + メール既知 → 100req/分 + 知識不要）
  だけである。100req/分 は単一スクリプトで容易に達成できる水準で、実効的な緩和になっていない。
  むしろ**メールアドレスの知識が不要になった分、前提条件は緩んでいる**。

  さらに悪いことに、**IP ゲートで拒否されるリクエストもグローバル枠を消費する**。攻撃者の IP が
  10回/10分の上限に達した後も、そのホストからの 11 回目以降（scrypt を一切実行しない安価な拒否）が
  グローバルカウンタを進め続ける。これは `auth.ts:47-49` に書かれた閾値の根拠

  > 「scrypt 1回 ≒ 100ms なのでこの上限は 1インスタンスあたり最大 10秒/分の CPU に相当する」

  と**実装が食い違っている**ことを意味する。実際には scrypt を1度も走らせないリクエストが
  カウンタの大半を占めうるので、この上限は CPU 消費量の上限として機能していない。
  `security-audit.md` SEC-022 修正方針3 の指定は「**同時実行中の scrypt 数、または認証エンドポイント
  全体の秒間上限**」であり、前者（セマフォ = 自動解放されるので枯渇しない）を採っていれば
  この欠陥は生じなかった。後者を採ったこと自体は許容範囲だが、その場合に生じる可用性のトレードオフが
  評価されていない。

- **改善案**: グローバル枠を「**実際に照合コストを発生させる試行**」だけに課す。順序を入れ替える。

```ts
// 2) IP 軸の照合前ゲート（安価な拒否はここで終わらせ、グローバル枠を消費させない）
const gate = await limiters.ip.peek(ipKey, now)
if (!gate.success) return denied(gate.retryAfterMs)

// 3) IP 軸は「試行」を数える
await limiters.ip.consume(ipKey, now)

// 1') キー非依存のグローバル上限は、verify() に到達する試行だけを数える。
//     こうするとカウンタの意味が「scrypt の実行回数」と一致し、単一 IP が寄与できる量は
//     IP 軸の上限（10回/10分）に縛られる。100回/分を枯渇させるには 100 以上の実 IP が要る。
if (limiters.global) {
  const global = await limiters.global.consume(LOGIN_GLOBAL_KEY, now)
  if (!global.success) return denied(global.retryAfterMs)
}
```

  **この変更で既存テストは全て通る**（コードを読んで確認した。テスト実行は行っていない）:
  - `login-guard.test.ts:356`（IP を毎回変える攻撃）: 各 IP は1回しか使わないので IP ゲートを常に通過し、
    グローバル消費は従来どおり 25 回発生。21〜25 回目が `rate-limited` になる期待は変わらない。
  - `:380`（グローバル拒否では照合しない）: ip limit=100 なのでゲートは通過し、3回目にグローバルが
    枯渇して `verified=false` / `verify` 呼び出し2回。同じ。
  - `:397`（global 未指定）/ `:411`（成功で解放しない）: いずれも影響なし。

  **ただし `docs/review-p25-tests-2026-07-28.md` §T1 は処理順序自体を契約としている**ため、
  実装だけ変えると契約書と食い違う。**契約書（順序表）も併せて更新すること**（Test Agent 案件）。
  加えて、順序を入れ替えても「100 以上の実 IP を持つ攻撃者はログインを封鎖できる」という
  残余リスクは消えない。これはグローバル上限を置く以上避けられないトレードオフなので、
  **「消した」ではなく「残余リスクとして受容した」と `security-audit.md` / `tech-stack.md` に明記**し、
  P3 で申込・チャットに同じ軸を載せるときの判断材料として残すこと。
- **理由**: P2.5 は「是正が持ち込んだ新しい欠陥を、P3 で複製する前に潰す」ための Phase である。
  今回の形のまま P3 で `lib/login-guard.ts` のパターンを申込フォームへ横展開すると、
  **単一ホストが 100req/分 で入所申込の受付を全面停止できる**ことになる。管理ログインの封鎖より
  事業影響が直接的で、しかも「レート制限を入れたせいで受付が止まる」という最も説明しにくい形の
  障害になる。P3 の前にこの意味論を確定させるべき、というのが RV-P2R-001 を Should Fix として
  P2 で見送った際の申し送りの趣旨でもある。

### [RV-P25-002] `unknown` 縮退時に「正しい資格情報は常に通る」という事実に反する記述が3箇所にある（SEC-021 が完全再現する構成）

- **種別**: Security（誤った安全性主張）/ Documentation
- **重要度**: **Must Fix**
- **場所**: `lib/http-guard.ts:84-85`（コメント）/ `docs/tech-stack.md:199-200` / `docs/review-p25-tests-2026-07-28.md` §T2「導かれる契約」3
  （原典は `docs/security-audit.md` SEC-021 の付随節「SEC-021 の修正方針1（成功は常に通す）を適用すれば、この縮退も同時に無害化される」）
- **現状**: 3箇所とも次の主張をしている。

  > 信頼境界の外で全利用者が単一 `unknown` バケットを共有しても、**正しい資格情報は常に通る**ため
  > （SEC-021 の是正）、正規管理者が締め出されることはない。

  **これは誤りである。**「成功は常に通す」が適用されたのは**アカウント軸だけ**で、
  IP 軸は依然として**照合前ゲート**である（`lib/login-guard.ts:87-88`）。したがって
  `resolveClientIp` が `unknown` に縮退した構成では:

  - 誰か（攻撃者でも、単に打ち間違えた利用者でも）が 10 分以内に 10 回失敗すると
    `credentials:ip:unknown` が枯渇する。
  - 以降 10 分間、**正しいパスワードでも `verify()` が呼ばれず `rate-limited` で拒否される**。
  - 成功時の reset（`login-guard.ts:98`）は「成功できた場合」にしか効かないので、
    一度枯渇したら**自力では抜け出せない**（ウィンドウ経過を待つしかない）。

  攻撃コストは 10 リクエスト / 10 分。**元の SEC-021（5リクエスト/15分・メール既知が必要）より安い**。
  つまりこの構成では SEC-021 が是正前と同等以上の形で残っている。

  実際の被害範囲は限定的である: ホスティングは Vercel 集約で確定しており（`tech-stack.md` §1.1）、
  Vercel 上では `VERCEL=1` により per-IP バケットに分離されるので、**本番想定では顕在化しない**。
  影響を受けるのはローカル / `next start` 直公開 / オンプレである。
  それでも Must Fix とする理由は次の2点:
  1. **誤った安全性の主張がコードコメントとして残ることの害**。この監査 → テスト契約 → 実装コメント
     という連鎖の各段で誰も検証しなかった。同じ文言が3箇所にある状態は、P3 で「`unknown` 縮退は
     安全だから気にしなくてよい」という判断を誘発する。P2 のレビューで「コメントと実装が食い違うと
     後任が『対策済み』と誤読する」ことを指摘し、実装側もそれを直した経緯がある。
  2. **`tech-stack.md:208-210`「Vercel 以外へ移す場合の必須作業」の記述が、この誤りの上に立っている**。
     「更新を怠っても fail-closed で、制限が緩む方向には壊れない」は正しいが、
     *締まりすぎる方向に壊れる*（＝全員がログインできなくなる）ことが書かれていない。
     移設判断の材料として不完全である。
- **改善案**: 記述の訂正が最小の Must Fix。3箇所を次の趣旨に書き換える。

  > 信頼境界の外では全利用者が単一 `unknown` バケットを共有する。制限は緩まないが、
  > **IP 軸は照合前ゲートであるため、誰かが 10 回失敗すると 10 分間は正しい資格情報も拒否される**
  > （SEC-021 と同型の締め出しがこの構成でのみ残る）。**Vercel 以外へ配置する場合は、
  > 前段プロキシが XFF を上書きすることを確認したうえで `trustProxy` を必ず有効化すること。**

  コード側の対処を行うなら、`unknown` バケットにだけ緩い上限を割り当てる
  （例: `ip` limiter とは別に「信頼できない発信元用」の limiter を持ち、閾値をグローバル軸相当にする）
  のが素直だが、本番構成では踏まない経路なので**記述の訂正で足りる**と判断する。
  ただし P3 で未認証エンドポイント（申込・チャット）に同じ縮退を適用する場合は話が別で、
  そこでは「誰か1人の連投で全利用者の申込がブロックされる」ことになる。**P3 着手時に必ず再評価すること。**
- **理由**: 「防御が成立する条件」を誤って記録することは、防御が無いことより悪い場合がある。
  実装が正しくても、誤った前提の上に次の判断が積まれるため。

### [RV-P25-003] `login-guard` が `consume` の判定結果を捨てており、並行リクエスト下では IP 上限を超えて scrypt が走る

- **種別**: Design（並行性）/ Security（コスト保護の緩み）
- **重要度**: **Should Fix**（P3 横展開前に対応）
- **場所**: `lib/login-guard.ts:87-91`
- **現状**:

```ts
const gate = await limiters.ip.peek(ipKey, now)     // ① 判定
if (!gate.success) return denied(gate.retryAfterMs)
await limiters.ip.consume(ipKey, now)               // ② 加算（戻り値を捨てている）
const ok = await verify()                           // ③ scrypt
```

  `rate-limit.ts` 側の直列化（`:192-206`）は **1回の `peek` / 1回の `consume` の中**でしか効かない。
  ①と②は別々に直列化キューへ載るため、`count === limit - 1` の状態で N 本のリクエストが同時に来ると、
  **N 本すべてが①を通過**し、②は1本だけ成功して残りは `success: false` を返すが、
  **その結果は捨てられているので N 本すべてが③に進む**。

  RV-P2R-007 の指摘は `RateLimiter` 単体については閉じたが（`rate-limit.test.ts:417` が固定）、
  呼び出し側の2相構造がそのまま残っているため、**「上限超過時は scrypt を走らせない」という
  コスト保護の中核契約が並行下で破れる**。`verify()` は 100ms の CPU を使うので、
  攻撃者は上限境界を狙って同時接続を束ねることで libuv スレッドプールを圧迫できる。
  増幅率は同時接続数に比例し、ウィンドウごとに繰り返せる。
- **改善案**: `peek` を廃して `consume` の結果でゲートする。`consume` は「上限到達済みならカウントを
  進めない」（`rate-limit.ts:234-237`）ので、2相を1相に畳んでも意味論は変わらず、**アトミックになる**。

```ts
// peek → consume の2相をやめ、consume の判定でゲートする（単一の直列化区間に収まる）。
const gate = await limiters.ip.consume(ipKey, now)
if (!gate.success) return denied(gate.retryAfterMs)
```

  逐次実行時の挙動は現行と完全に一致するため、`login-guard.test.ts` の既存ケース
  （:246 の 11回目 `rate-limited`/`verified=false`、:271、:293 のウィンドウ経過）は
  いずれも変更不要である。`RateLimiter.peek` は他に呼び出し元がある（`auth.ts:111-112` のログ）ので
  API 自体は残す。
- **理由**: P3 では未認証エンドポイントに同じ形を横展開する。そこでは同時接続を束ねるのが
  攻撃の基本形になるため、「呼び出し側の2相」は各所に複製された後で直すことになる。
  修正は1行で、いま直すのが最も安い。

## 4. P3 着手可否

### 判定: **条件付きで不可 — RV-P25-001 / RV-P25-002 のクローズ後に着手可**

理由:

- P2.5 の目的は「**レート制限基盤を未認証エンドポイントへ横展開する前に、欠陥ごと複製されるのを防ぐ**」
  ことである（`phase-status.md` §P2.5）。RV-P25-001 は、まさにその**基盤の意味論**に残った欠陥であり、
  横展開すると「単一ホストが申込受付を全面停止できる」形で複製される。P3 の後に直すと、
  修正は 申込 / アップロード / チャットの3〜4箇所に散る。**いま直すのが構造的に最も安い。**
- RV-P25-002 は、`unknown` 縮退の安全性についての誤った前提が3箇所に記録されている状態である。
  P3 では未認証エンドポイントに同じ縮退が適用されるため、この前提の上で設計判断が行われると
  「誰か1人の連投で全利用者の申込がブロックされる」構成を、安全だと信じたまま作ることになる。
- 逆に、**SEC-022 / SEC-023 / SEC-024 は横展開してよい状態にある**。`resolveClientIp`・
  `rateLimitKey`・`createMemoryRateLimitStore({maxEntries})`・`withAdminMutation` は
  いずれも P3 でそのまま再利用でき、作り直しにはならない。RV-P25-003（呼び出し側の2相）だけ
  併せて畳んでおくことを強く推奨する（1行）。

## 5. P3 への申し送り

### 横展開してよいもの（**書き起こさないこと**）

- **発信元 IP の解決**: `lib/http-guard.ts` の `resolveClientIp()`。申込 / アップロード / チャットの
  全レート制限キーはこれを経由する。**`request.headers.get('x-forwarded-for')` を直接読んだ時点で
  SEC-022 の再発**である。
- **レート制限キーの組み立て**: `lib/rate-limit.ts` の `rateLimitKey(prefix, raw)`。
  未認証エンドポイントでは入力（メール・電話番号・トークン）の長さが攻撃者制御なので必須。
- **同一オリジン検証と変更系ガード**: `app/api/admin/_guard.ts` の `withAdminMutation`。
  管理系以外にも使うなら、認可部分を差し替え可能にして `lib/` へ移すこと（現在 `@/auth` に依存）。
- **判定と永続化の分離**: `RateLimitStore` 境界。KV 実装は `createKvRateLimitStore(): RateLimitStore`
  として `lib/kv.ts` に書き、**判定ロジックを複製しない**。その際 `INCR` + `EXPIRE` で
  store 側の原子性を確保すること（プロセス内の直列化は分散環境では効かない）。
- **公開お知らせの述語**: `lib/news-visibility.ts` の `publishedNewsWhere()` / `PUBLISHED_NEWS_ORDER_BY`
  （P2 からの継続申し送り）。`/news` 一覧・詳細は `lib/queries.ts` に関数を足してこれを呼ぶ。
  `findUnique({ where: { id } })` を使うと述語を足せないので `findFirst` を使うこと。

### P3 着手時に必ず判断すること

1. **未認証エンドポイントに「グローバル上限」を置くかどうかを、可用性の観点から明示的に決める。**
   RV-P25-001 で述べたとおり、キー非依存の上限は「1ホストが全利用者を止められる」性質を必ず持つ。
   申込フォームでこれは事業影響が大きい。**scrypt のような高コスト処理の同時実行数セマフォ
   （自動解放されるので枯渇しない）**のほうが、申込・チャットには適している可能性が高い。
2. **`unknown` 縮退の扱い**（RV-P25-002）。未認証エンドポイントで全員が単一バケットを共有すると、
   1人の連投で全利用者がブロックされる。Vercel 前提なら顕在化しないが、
   前提を `VERCEL=1` の1点に依存させ続けてよいかを P3 の設計時に再確認すること。
3. **SEC-023 修正方針3（本番で store 未注入なら fail-fast）を必須化する。**
   `lib/kv.ts` を実装する時点で `lib/env.ts` に入れ、`tests/unit/env.test.ts` に固定する
   （実装ノート §スコープ外の申し送りどおり）。**これを入れないと、本番で KV を設定し忘れても
   レート制限が静かに骨抜きになる**（インメモリはインスタンスをまたがない）。
4. **RV-P2-007（タイムゾーン）**: P2 からの継続。時刻ゲートが有効な今、`datetime-local` の
   ローカル解釈は「予約公開が9時間ずれる」形で本番でのみ出る。申込フォームにも
   生年月日・希望開始月があるため、`lib/format.ts` に JST 変換を用意し `TZ=UTC` でテストしてから
   P3 の入力実装を始めること。既存の `publishedAt` 正規化3箇所も同時に統合する。
5. **SEC-002（CSP）の前倒し**: `phase-status.md` が「P3 と同時に強く推奨」としている。
   個人情報入力フォームで XSS が成立したときの被害が大きいため、本レビューも前倒しを支持する。
6. **RV-P2R-006（Origin の scheme）**: 初回 https デプロイ直後に、お知らせの保存・削除と
   申込の送信を各1回実行し、403 にならないことを確認する（`request.url` が `http` に解決される
   構成では同一オリジンの正規リクエストが全て 403 になる）。

### 本 Phase で得られた教訓（記録）

P2 の教訓は「**テストが green でも本番経路が守られていない**」だった。P2.5 で起きたのは
その変種で、「**red だったテストが全部 green になっても、脅威クラスは閉じていない**」である。

原因は、監査（SEC-021 付随節）が書いた「成功は常に通すのでこの縮退も無害化される」という
**未検証の主張が、テスト契約 → 実装 → ドキュメントへ無検証のまま伝播した**こと。
テスト契約は「アカウント軸を照合前ゲートに使わない」を正しく固定したが、
「**照合前ゲートが1つでも残っている限り、そのゲートの共有バケットは締め出しを生む**」という
一段深い不変条件を立てなかった。

P3 以降の運用として次を追加することを提案する:

> レート制限・ロックアウトを設計するときは、「攻撃者が拒否される条件」だけでなく
> **「正規利用者が拒否されうる条件」を必ず列挙し、テストに書く**。
> 前者だけを検証したテストは、可用性の欠陥を素通りさせる。
