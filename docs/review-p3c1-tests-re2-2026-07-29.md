## 1. NEW-001（Must Fix）— **クローズ**

### 1.1 red が本物であること（依頼事項 1）

追加された 6 件のうち **red は 2 件**で、いずれも**実装が無いことが理由**である。自分で実行して確認した:

| テスト | 結果 | 失敗の実体 |
|--------|------|-----------|
| `:309` 有効な Cookie を提示 → `Set-Cookie` 無しで `/apply` へ | **red** | `expected true to be false`。`app/api/form-session/route.ts:116-122` が `hasVerifiedSession` を渡さないため、無条件に発行している |
| `:368` 通常構成（`trusted=true`）でも同じ | **red** | 同上 |
| `:330` Cookie 無し → 従来どおり発行 | green | 「行き過ぎた修正」の pin |
| `:337` `already-verified` に `Retry-After` を付けない | green | 現状は `issued: true` になるので `!issued` 分岐に入らない。**実装後に初めて意味を持つ pin** |
| `:345` 印付き Cookie の保持者には**発行する** | green | 下記 |
| `:357` 期限切れ・壊れた Cookie にも発行する | green | fail-open の pin |

`:337` は現時点では「別の理由で green」だが、これは red を偽装していない
（設計文書も red を 2 件と正しく申告している）。実装後に `!issued` 分岐へ入って初めて効く pin であり、
**red 件数の水増しをしていない**点で報告は正確である。

### 1.2 テストの中身の判定

`:345`「**印の付いた（`unverified`）Cookie を持つ要求には発行する**」は、
本レビューが指摘していない穴を Test Agent が自分で見つけたものである。

> `hasVerifiedSession` は「Cookie を持っているか」ではなく「**有効な** Cookie を持っているか」である。
> 印の付いた Cookie の保持者に発行を止めると、新しい Cookie を永久に得られず
> **SEC-067 のロックアウトが恒久化する**（直そうとした欠陥を悪化させる）。

これは正しく、かつ重要である。`hasVerifiedSession: presented !== null` という
自然な実装（`verifyFormSessionValue` は印付きに `null` を返す）なら満たされるが、
`readFormSessionCookie(request) !== null`（＝ Cookie の**存在**で判定）と書くと
**SEC-067 が恒久ロックアウトへ悪化する**。その 1 行の差をテストで固定したのは的確である。

`:368`（通常構成でも同じ）で構成による分岐を禁じたのも良い。
「縮退限定の最適化」にすると分岐そのものが次の欠陥の温床になる、という理由付けも妥当である。

## 2. NEW-005（優先指示あり）— **クローズ**

`x-forwarded-for` の左端採用に対し、**env provenance では `x-real-ip` を優先する**という契約が入った。
nginx の標準レシピ（`X-Real-IP $remote_addr` は単一値 / `X-Forwarded-For $proxy_add_x_forwarded_for` は append）
という現実に即した根拠付けで、pin は 4 件:

| pin | 内容 |
|-----|------|
| `:379` | append 構成（`<攻撃者の名乗り>, <前段の実 IP>`）でも攻撃者の値を採らず `x-real-ip` を採る |
| `:405` | `x-forwarded-for` を変えてもバケットが増えない（実 IP に固定される） |
| `:425` | `x-real-ip` が無ければ `x-forwarded-for` を使う（上書き構成を壊さない） |
| `:482` | **`lib/http-guard.ts` のコメントが `append` に言及している**ことをソースで固定 |

最後の 1 件について、Test Agent は自分で空振りを検出して締めている:

> `/append|上書き/` では空振りする。`lib/http-guard.ts:98-99` には既に「上書きすることを確認したうえで」が
> あり、実装前から green になる。**`append` という危険側の語**を要求する形に締め、red を実測した。

**これは前回 REV-P3C1-010 で申し送った規律（空振りしている assertion を green として報告しない）を、
指示されるより先に自分の新規テストへ適用したもの**である。§8 の `log:` 正規表現に続いて 2 例目であり、
このプロジェクトで最も価値のある習慣が定着しつつあると評価する。

残余: 3 つ目の改善案（信頼ホップ数を設定可能にする）は採られていないが、
`x-real-ip` 優先で実用上の穴は塞がる。**採らない判断に同意する。**

## 6. 新規指摘

### [RE2-001] `isFormSessionRenewable` の**結線**を測る pin が無い（NEW-003 の積み残し）

- **種別**: Design（テストカバレッジ）
- **重要度**: Should Fix（**実装フェーズで拾えばよい。差し戻さない**）
- **場所**: `tests/integration/form-session-route.int.ts`（不在）/
  `tests/unit/form-session-degraded-recovery.test.ts:628`
- **現状**: NEW-003 は `isFormSessionRenewable` という**正典関数の契約**を 4 件で固定したが、
  **ルートがそれを呼ぶことを測るテストが無い。** `form-session-route.int.ts` の 6 件は
  「有効（更新不要）」「印付き」「期限切れ」「壊れた値」「無し」を覆っているが、
  **「有効だが失効間近」という 5 つ目の状態だけが抜けている。**

  ルートが `hasVerifiedSession: presented !== null`（更新窓を見ない）と実装しても、
  **6 件すべてが green のまま通る。** その場合 NEW-003 は 1 ミリも効かない——
  これは NEW-001 で指摘した「受け口が呼ばれることを測っていない」と**同じ型**である
  （深刻度は段違いに低く、可用性の劣化にとどまる）。

  加えて `form-session-degraded-recovery.test.ts:628`
  「更新のための再発行を繰り返しても蓄積上界は壊れない」は `hasVerifiedSession: false` を渡しており、
  **通常の発行経路そのもの**である（pin ② の言い換えになっていて、更新窓を経由していない）。
  無害だが、この 1 件は NEW-003 を守っていない。
- **改善案**: `form-session-route.int.ts` に 1 件足す（既存の `:357` と同じ形で書ける）。

  ```ts
  it('失効間近の Cookie を提示した要求には再発行する（更新窓 / NEW-003）', async () => {
    // 更新窓を見ない実装（hasVerifiedSession: presented !== null）でも他の 6 件は green のままなので、
    // この 1 件だけが「ルートが isFormSessionRenewable を呼んでいるか」を観測する。
    const nearExpiry = signedCookieValue({
      ageMs: FORM_SESSION_MAX_AGE_SEC * 1000 - FORM_SESSION_RENEW_BEFORE_MS + 60_000,
    })
    expect(issuesCookie(await get({ headers: { cookie: `${cookieName}=${nearExpiry}` } }))).toBe(true)
  })
  ```

  **この 1 件は現時点で green になる**（ルートは常に発行するため）。red にはならないが、
  「更新窓を見ない実装」を**将来にわたって**捕捉する pin としては有効である。
  red にしたいなら、対になる `:309`（更新不要な Cookie → 発行しない）と併せて
  **2 件で挟む**形になっており、それは既に存在する。
- **理由**: NEW-003 を入れた目的は「P3-c2 の写真アップロード（滞在時間が長い）で
  30 分の失効に当たる利用者を減らす」ことである。結線が抜けると目的が達成されないまま
  「更新窓を入れた」という記録だけが残る。
