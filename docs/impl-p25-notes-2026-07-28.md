## T1 / SEC-021 / RV-P2R-001 — 管理者締め出しの解消

### 新規: `lib/login-guard.ts`

契約どおりのシグネチャ（`createLoginGuard` / `LoginDecision` / `LoginGuardLimiters` /
`LoginAttemptInput` / `LoginOutcome`）で実装した。処理順序も契約そのままである。

```
1. global?.consume('credentials:global', now)  → 超過なら rate-limited / verified=false
2. ip.peek(`credentials:ip:${ip}`, now)        → 超過なら rate-limited / verified=false
3. ip.consume(`credentials:ip:${ip}`, now)
4. const ok = await verify()                   ← 必ず実行する
5. ok  → ip.reset / account.reset して ok / retryAfterMs=0 / verified=true
6. !ok → account.consume(`credentials:email:${normalized}`, now) して invalid-credentials
```

### 意味論の変更点（これが SEC-021 の是正そのもの）

| 軸 | 変更前（P2） | 変更後（P2.5） |
|----|-------------|---------------|
| IP | 照合前 `peek` ゲート + 試行を consume | **変更なし**（唯一のキー付き照合前ゲート） |
| アカウント | **照合前 `peek` ゲート** + 失敗を consume | **失敗の consume のみ**。ゲートに使わない |
| グローバル | なし | **新設**。照合前に consume（成功でも解放しない） |

アカウント軸を照合前ゲートから外したことで、「第三者が N 回失敗させた後でも正規パスワードは通る」
が成立する。アカウント軸自体は**分散攻撃の観測手段**として残した（削除していない）。

### ブルートフォース耐性を失っていない根拠

拒否の判断に使う軸を「攻撃者自身に閉じた軸」（IP / グローバル）へ寄せた。誤ったパスワードの連打は
IP 軸 10回/10分で止まり、**11回目以降は `verify()` を呼ばない**（scrypt を消費させない）。
攻撃者が上限到達後に正しいパスワードを引き当てても照合自体を行わないため通らない
（`tests/unit/login-guard.test.ts` L271 が固定）。「成功は常に通す」が緩めているのは
**アカウント軸だけ**で、IP 軸・グローバル軸の防御は変更前より強い（グローバルは新規追加）。

### 補足: 失敗時の `retryAfterMs`

`invalid-credentials` では常に 0 を返す。アカウント軸が枯渇していても拒否理由はあくまで
「資格情報が違う」であり、待てば通るわけではないため待機時間を返すのは誤誘導になる。
テストは L331 で「拒否されること自体」だけを契約にしており、この選択と矛盾しない。

### `auth.ts` の変更

- アカウント軸の照合前 `peek` ゲート（旧 `auth.ts:84-94`）を削除し、`loginGuard.attempt` に置換。
- `verify` には既存のダミーハッシュ均一化（不在/ハッシュ無しでも同一コストの検証）をそのまま包んだ。
  **応答時間均一化（E-012-1）は維持**している。
- `verify` の戻り値は `boolean` なので、照合できたユーザーは `found.user` という 1 段の
  ホルダで閉包の外へ運ぶ（`let` + 閉包代入だと TS の絞り込みが効かないため）。
- 失敗ログは IP・時刻・試行回数（+ `retryAfterMs`）のみ。メールアドレス全文・パスワードは
  記録しない。試行回数は決定後に両 limiter を `peek` して取得する。

## T2 / SEC-022 / RV-P2R-003 — IP キー導出を信頼できる出所に

### `lib/http-guard.ts` に `resolveClientIp` を追加

契約どおり `ClientIpResolution` / `ClientIpSource` / `ResolveClientIpOptions` を実装。

- 優先順: `x-vercel-forwarded-for` → `x-forwarded-for` → `x-real-ip`。
- `trustProxy` の既定は `process.env.VERCEL === '1'`（**未設定なら false ＝ fail-closed**）。
- `trustProxy=false` のときは**ヘッダを一切読まない**。単一 `unknown` バケットへ縮退させ、
  制限を緩めない。
- 採用値は必ず IPv4 / IPv6 リテラルとして検証する。

### 出力の有界性をどう担保したか

正規表現に長大な入力を渡す前に `value.length > 45`（IPv6 リテラルの最大長）で足切りする。
IPv6 判定は「`::` で分割 → 各グループを固定長パターン `[0-9a-f]{1,4}` で検証 →
末尾の IPv4 記法のみ別扱い」という形にし、**バックトラッキングが起きる正規表現を書いていない**
（ReDoS 回避）。結果として `key` は常に 1〜45 文字となり、攻撃者が任意長文字列を
レート制限キーにする経路（SEC-023 の増幅要因）が断たれる。

### なぜ `node:net` の `isIP()` を使わなかったか

`lib/http-guard.ts` は Edge ランタイム（middleware）からも読める状態に保ちたい。
P3 で未認証エンドポイントのレート制限を middleware 側へ寄せる選択肢を潰さないため、
Node 組み込みモジュールへの依存を持ち込まず自前判定にした。

### グローバル上限の閾値: 100回/分（`auth.ts` の `LOGIN_GLOBAL_LIMITER`）

- **上限の根拠**: scrypt 1回 ≒ 100ms なので、100回/分は 1 インスタンスあたり最大
  10秒/分の CPU に相当する。これを超える認証試行は正規利用では発生しないため攻撃と見なす。
- **正規利用者が到達しないことの確認**: 管理者ログインは 1 日数回の規模。E2E スイート全体
  （82 テスト / 約 35 回のログイン / 1.1 分）でも到達しなかった（実測で 82 pass）。
- 成功では解放しない。解放すると「全体の流量制御」として機能しないため
  （`login-guard.test.ts` L411 が契約化している）。

### `docs/tech-stack.md` への追記（契約 T2 項目5）

§4.5「信頼する HTTP ヘッダと信頼境界（SEC-022）」を新設した（旧 §4.5 環境変数は §4.6 へ繰り下げ）。
どのヘッダを信頼するか、その根拠（Vercel 公式ドキュメントの記述）、信頼が成立する前提
（`VERCEL=1`）、前提が崩れた配置での `unknown` 縮退、Vercel 以外へ移す場合の必須作業を明記した。
変更履歴に 0.2.1 を追加。

## T3 / SEC-023 / RV-P2R-002 / RV-P2R-007 — 回収・件数上限・並行性

### 1. 期限切れの遅延回収

`currentEntry()` が `now >= entry.resetAt` を検出したら `await store.delete(key)` してから
`null` を返す。時刻比較だけで済ませていた従来は、二度と現れないキーが store に常駐し続けていた。

### 2. 件数上限つきインメモリ store

`createMemoryRateLimitStore({ maxEntries })` が `RateLimitStore & { size(): number }` を返す。
既定上限は `DEFAULT_MEMORY_STORE_MAX_ENTRIES = 10_000`（無制限にはできない）。

退避方針は契約どおり「**期限切れ → 最も古い `resetAt`**」の順。ただし 1 件ずつ退避すると
上限到達後は挿入のたびに全走査が走るため、**1 回の退避で `maxEntries` の 1%（最低 1 件）**を
まとめて空ける。`maxEntries=3` のような小さい設定では 1 件ずつと同じ挙動になる。
退避は**新規キーの挿入時のみ**判定する（既存キーの更新では退避しない）。

### 3. キーの正規化と長さ制限: `rateLimitKey(prefix, raw)`

`raw` を trim + 小文字化し、64 文字を超える場合は `sha256(raw)` の先頭 32 文字に畳む。
出力長は `prefix.length + 64` を超えない。**大小文字違いによる回避を塞ぐ**と同時に、
攻撃者がキー長を制御できなくなる。`lib/login-guard.ts` の IP 軸 / アカウント軸のキー組み立ては
すべてこの関数を経由する。

### 4. 同一キー操作の直列化（RV-P2R-007）

`createRateLimiter` 内にキーごとの Promise チェーン（`serialize`）を持ち、
`consume` / `peek` / `reset` をそのキューに載せる。`peek` も期限切れ回収で store を書き換えるため
同じキューに載せている。チェーンは決着後に自動回収する（キュー自体がキー空間の増殖源にならない）。

**採用理由**: 契約の代替案（`RateLimitStore.increment?()` を任意メソッドとして追加）は
`INCR` が上限を超えてもカウントを進めてしまうため「上限到達済みならカウントを進めない」という
既存契約と噛み合わず、テストの無い分岐を増やすことになる。よって**実装は直列化のみ**とし、
KV 実装への要求（`INCR` + `EXPIRE` による原子性）は `RateLimitStore` と `lib/kv.ts` の
doc コメントとして残した。プロセス内の直列化は分散環境では効かないため、この明記は必須である。

### 5. `RateLimitStore` の doc（契約 T3 項目3）

「実装は `resetAt` に対応する TTL を設定**すべき**」「既定インメモリ実装は TTL を持てないため
件数上限（既定 10,000）で止める」「KV 実装では `INCR` + `EXPIRE` の 1 往復に落とす」を明記した。

### 6. RV-P2R-008（任意）

`lib/kv.ts` に「判定ロジックの真実源は `lib/rate-limit.ts`」「P3 で
`createKvRateLimitStore(): RateLimitStore` として**永続化だけ**を担うよう書き直す」
「本番で store 未注入なら fail-fast を `lib/env.ts` に入れる（SEC-023 修正方針3・P3 で必須化）」
を注記した。

## T4 / SEC-024 — JSON 管理 API への Origin 検証

### 共通ラッパ化: **採用した**

`app/api/admin/_guard.ts` に `withAdminMutation<Ctx>(handler, options)` を新設し、
**変更系 5 ハンドラすべて**に適用した。

| ハンドラ | 未認証時 | Content-Type 要求 |
|---------|---------|------------------|
| `POST /api/admin/news` | 401 JSON | `application/json`（不一致 → 415） |
| `PUT /api/admin/news/[id]` | 401 JSON | `application/json`（不一致 → 415） |
| `DELETE /api/admin/news/[id]` | 401 JSON | なし（ボディを持たないため） |
| `POST /api/admin/news/save`（form） | 303 → `/admin/login` | なし |
| `POST /api/admin/news/delete`（form） | 303 → `/admin/login` | なし |

`GET /api/admin/news` にはラッパを適用していない（副作用が無く、Origin 検証は過剰適用になる。
PT2-06 の最終ケースがこれを検出する）。

### なぜ「3 箇所に `isSameOrigin` を足す」ではなくラッパにしたか（判断理由）

1. **監査の指示そのもの**（SEC-024 修正方針3 / P3 着手前の必須前提 B）。SEC-011 の是正が
   form 2 本への手動適用だったからこそ JSON 3 本が漏れた。同じ失敗の再発を「規律」ではなく
   **構造**で防ぐ必要がある。
2. **P3 で変更系ハンドラが増える**（申込 / 画像アップロード / チャット）。手動適用は
   ハンドラ数に比例して漏れる確率が上がるが、ラッパなら「ラッパを通していない変更系がある」
   という 1 点だけをレビューで見ればよい。
3. **評価順序をハンドラ間で統一できる**。従来は form 2 本が「Origin → 認可」、JSON 3 本が
   「認可のみ」とばらついていた。ラッパで `認可 → Origin → Content-Type → 本体` に揃えた
   （契約の指定順）。既存 E2E は未認証クロスオリジンに `[303, 403]` / `[401, 403]` を許容して
   おり、順序の変更で壊れない（実測でも 82 pass）。

### なぜ `lib/http-guard.ts` ではなく `app/api/admin/_guard.ts` に置いたか

ラッパは `@/auth` に依存し、`auth.ts` は Prisma と `getServerEnv()` のトップレベル副作用を持つ。
`lib/http-guard.ts` は `resolveClientIp` / `isSameOrigin` という**純粋な判定**を単体テストから
直接読めることが要件（`tests/unit/client-ip.test.ts` / `tests/unit/http-guard.test.ts`）なので、
認証依存をそちらへ持ち込むと既存テストが Prisma を要求するようになってしまう。
契約も「`lib/http-guard.ts`（または `app/api/admin/_guard.ts`）」と後者を許容している。

### Content-Type 検証の実装

`application/json` と `*/*+json`（`application/merge-patch+json` 等）を許可し、それ以外は 415。
`text/plain` は **CORS セーフリスト値でプリフライトが飛ばない**ため、これを塞がないと
クロスサイトから単純リクエストとして到達できる形が残る（SEC-024 修正方針2）。
