## 1. 前回 Must Fix の逐条判定

### [REV-P3C1-001] `hasVerifiedSession` が SEC-057 を再び開く → **クローズ**

契約は「**枠を消費しない**」から「**発行しない**」（`issued: false, reason: 'already-verified'`）へ
作り直された。これは前回の改善案 (A) そのものであり、**蓄積の経路が構造的に消える**——
新しい Cookie が出ない以上、印の無い Cookie の総数は増えようがない。

追加された 3 本の pin を自分で確認した。**現行実装（`hasVerifiedSession` を無視する）で green** であり、
素朴な実装（`consume` を飛ばす）を入れると red になる:

| pin | 測っているもの | 現行実装での値 | 判定 |
|-----|--------------|--------------|------|
| ① `:499` | `trusted` で 50 回要求 → 発行枚数 ≤ 30 | 30 | ✅ green |
| ② `:514` | 縮退で 200 回要求 → 印なし枚数 ≤ 10 | 10 | ✅ green |
| ③ `:531` | 本番配線での到達数 ≤ 30 | 30 | ✅ green |

§4.1 の実測表（素朴な実装で 50 枚 / 200 枚 / **600 回到達**）は、pin が実際に捕捉することの証拠として
妥当である。**600 回は SEC-057 が測った 60 回の 10 倍**であり、
「SEC-067 を直したつもりで SEC-057 を 10 倍悪化させる」経路が実在したという記述も正しい。

**新しい抜け道の有無（最優先の確認事項）**: 契約そのものには見つからなかった。
`hasVerifiedSession` は要求元自身の Cookie から決まるので他人へ影響できず、
発行しない以上「1 枚を提示し続けて積み上げる」経路も閉じている。
ただし**副作用として 3 件の新規指摘**がある（NEW-002 / NEW-003、および結線の NEW-001）。
いずれも SEC-057 を開く性質のものではない。

### [REV-P3C1-002] `challengePassed` の増幅率が契約にない → **クローズ**

`boolean` を廃止し、**検証済みトークンの識別子**（`challengeToken`）+ 使用済み記録
（`usedChallengeTokens.consume(token, at)`）へ変更。増幅率が**構造的に 1 に固定**された。
追加 3 件の内容も適切である:

- `:349` 同一トークン 200 回 → 印なしは **1 枚だけ**（増幅率そのものを測る）
- `:373` 異なるトークン 5 回 → **5 枚**（「2 枚目以降を一律に弾く」実装＝別の締め出しを禁じる。
  この逆向きの pin を自分で足しているのが良い）
- `:387` 記録の**差し替え口**（複数インスタンスで流用を防ぐには KV 化が要る、という前提を契約に残した）

「boolean を残すと『渡すだけ』で通せるため契約に含めない」（テストヘッダ :88）という判断も正しい。

### [REV-P3C1-003] `TRUST_PROXY=1` + `x-vercel-forwarded-for` 偽装 → **クローズ**

**信頼の出所（provenance）で採用ヘッダを変える**という契約が入り、6 件で固定された。

| 追加 pin | 内容 |
|---|---|
| `:355` | 非 Vercel + `TRUST_PROXY=1` で、攻撃者の `x-vercel-forwarded-for` を採らず前段の `x-forwarded-for` を採る |
| `:381` | `x-vercel-forwarded-for` しか無ければ **unknown へ寄せる**（「他に無ければ仕方なく使う」を禁じる） |
| `:392` | 値を変えてもバケットが増えない（SEC-023 の増幅を断つ） |
| `:414` / `:428` | `VERCEL=1` では従来の優先順位を維持（**行き過ぎた修正**の防止） |
| `:350` | **本番ルートが `trustProxy` を渡していない**ことをソースで pin（provenance を潰す配線の禁止） |

最後の 1 件が効いている。`resolveClientIp(req, { trustProxy: env.TRUST_PROXY })` と書かれると
provenance の区別が消えるという抜け道を、**警告コメントではなくテストで**塞いだのは正しい判断である
（「警告コメントでは 4 度止められなかった」という自己認識と整合している）。
§3 の誤った記述（「制限が強くなる方向にしか動かない」）も訂正されている。

**残る同型の穴が 1 つある**（NEW-005 / Should Fix）。`x-forwarded-for` の**左端採用**は変わっていない。

### [REV-P3C1-005] `news` の相互汚染 → **クローズ**

両ファイルとも「seed 行だけ」を対象にする形に修正され、**機構として**汚染経路が消えている:

## 3. 新規指摘

### [NEW-001] `hasVerifiedSession` の結線が無く、P3-c1 完了時点で SEC-067 は閉じない（**新規 Must Fix**）

- **種別**: Design（スコープ / 記録の正確性）
- **重要度**: **Must Fix**
- **場所**: `docs/test-design-p3c1-2026-07-29.md` §4 結論（:218）/ §12.3（:770-780）/ §12.4、
  `app/api/form-session/route.ts:116-134`
- **現状**: `hasVerifiedSession` / `challengeToken` / `already-verified` を参照しているのは
  **`tests/unit/form-session-degraded-recovery.test.ts` 1 ファイルだけ**である（grep で確認した)。
  結線を測るテストは 1 件も無く、§12.3 は依然「**結線は P3-c2 の UI 設計と同時に確定するのが安い**」としている。

  そのため P3-c1 が完了しても:
  1. `app/api/form-session/route.ts` は `hasVerifiedSession` を**渡さない**ので、
     本番では常に `undefined` ＝ **自己維持の切断は 1 ミリも効かない**。
  2. 同じく `challengeToken` も渡らないので、**回復経路も存在しない**。

  ところが §4 の結論（:218）は
  > **したがって回復経路と自己維持の切断も本単位で閉じる**

  と書いており、**これは達成されない。** さらに §4 の「縮退構成の可用性の評価」表は
  「E2E は縮退構成でしか回らないので、自己維持する枠の枯渇は CI の flaky として残り続ける」ことを
  **本単位で SEC-067 を扱う理由そのもの**にしているが、結線が無ければ**その flaky も直らない**。

  加えて、契約の形が変わったことで**ルートの変更が必須**になった:
  `app/api/form-session/route.ts:124-133` は `!result.issued` の分岐で `result.retryAfterMs` を
  無条件に読む。新しい `{ issued: false, reason: 'already-verified' }` には `retryAfterMs` が無いので、
  ルートを直さなければ `retry-after: NaN` を返す（判別可能な union なので `pnpm type-check` は
  落ちるはずで、silent には壊れない。ただし §12.4 の「不足しているもの」表に**ルートの行が無い**）。

  これは「受け口が在るから結線済みと読める」で 1 度事故を起こした形と同じである。
- **改善案**（どちらか。**(A) を推す**）:

  **(A) `hasVerifiedSession` の結線だけを P3-c1 に入れる。**
  `app/api/form-session/route.ts` が受信 Cookie を `verifyFormSessionValue` で検証して渡し、
  `reason: 'already-verified'` を `Retry-After` 無しの 303 として扱う。
  `tests/integration/form-session-route.int.ts` に 2 件足す:
  「有効な Cookie を持って `GET /api/form-session` → `Set-Cookie` が無く 303」
  「Cookie 無しの要求 → 従来どおり `Set-Cookie` あり」。
  **回復経路（`challengeToken`）の結線は §12.3 のまま P3-c2 に置いてよい**——
  そちらは UI の導線と一体だが、自己維持の切断は UI に依存しない。

  **(B) 結線を丸ごと P3-c2 に置くなら、§4 結論と §11 を訂正する。**
  「P3-c1 は正典関数の契約までを固定する。**SEC-067 は P3-c1 完了時点では未クローズであり、
  結線が入る P3-c2 まで開いたままである**」と明記し、
  `docs/security-audit.md` / `docs/phase-status.md` にも同じ記録を残す。
- **理由**: どちらを選ぶかは工数の判断でよいが、**「閉じる」と書いてあって閉じていない状態だけは
  残してはならない。** 次の監査は §4 の結論を読んで SEC-067 を検収済みとして扱う。
  P3-c1 は「監査が指定した前提項目群」を閉じる単位であり、
  **記録の正確さそのものが成果物**である。

### [NEW-002] `already-verified` の経路が「計数は常に行う」という自己申告の invariant を破る

- **種別**: Design
- **重要度**: Should Fix
- **場所**: `tests/unit/form-session-degraded-recovery.test.ts:451-471`、
  実装側の invariant は `lib/form-session-issue.ts:108`
- **現状**: `lib/form-session-issue.ts:108` は
  > 計数は常に行う（観測手段を失わない）。ゲートに使うのは `trusted` のときだけ。

  と宣言しており、同じ意味論は `lib/public-guard.ts:66-67` にもある。
  新しい契約では「再訪の要求を 20 回繰り返しても、その後の新規来訪者に印が付かない」（:451）を
  満たす必要があるので、**`hasVerifiedSession` の要求では `consume` を呼べない**
  （呼べば `consumedInWindow` が進み、新規来訪者に印が付く）。

  結果として、**有効な Cookie を提示する要求は一切計数されず、上限も掛からない**。
  攻撃者が 1 枚の有効な Cookie で `GET /api/form-session` を無制限に叩けるようになる。
  発行も DB もメールも起きないので実害は小さいが、**この経路だけ観測手段が消える**。
  そして「計数する / しない」を決める pin は**どこにも無い**
  （`:323` の計数 pin は `challengeToken` 経路のみを覆っている）。
- **改善案**: 別キー（例: `apply:fs-revisit:`）で**計数だけ**行う契約にし、pin を 1 件足す。
  無コスト枠のカウンタとは別勘定なので :451 と両立する。

  ```ts
  it('already-verified の要求も計数される（観測手段を失わない / 無コスト枠とは別勘定）', async () => {
    const calls: string[] = []
    const recording: RateLimiter = { consume: (k, at) => { calls.push(k); return inner.consume(k, at) }, ... }
    await issueResult(recording, DEGRADED, { hasVerifiedSession: true })
    expect(calls.length).toBeGreaterThan(0)
    // かつ、無コスト枠のキーではないこと
    expect(calls.every((k) => !k.includes('fs-issue'))).toBe(true)
  })
  ```
- **理由**: この invariant は SEC-021〜SEC-043 の 4 度の再発から得た教訓として明文化されたものである。
  破るなら**意図した例外として記録し、pin で固定する**べきで、
  テストを満たすための副作用として黙って消えてよいものではない。

### [NEW-003] 「有効な Cookie があれば発行しない」は Cookie を**更新しない**ので、長時間の滞在で失効する

- **種別**: Design
- **重要度**: Should Fix
- **場所**: `tests/unit/form-session-degraded-recovery.test.ts:432-449` の契約
- **現状**: Cookie の寿命は 30 分（`lib/form-session.ts:63` `FORM_SESSION_MAX_AGE_SEC = 1_800`）。
  従来は `/apply` を開くたびに新しい Cookie が発行されるので**実質的に更新されていた**が、
  新しい契約では**有効な Cookie がある限り二度と発行されない**。
  したがって「初回訪問から 30 分」で必ず失効し、入力途中の利用者が Tier B に落ちる。

  これは再監査 §5 申し送り 1 が **P3-c2 について名指しした懸念**そのものである:
  > 写真アップロードは申込フォームより**滞在時間が長く、Cookie 寿命（30 分）との競合が起きやすい**。

  つまり SEC-067 の修正が、P3-c2 で顕在化する既知の弱点を**強める方向に働く**。
  失効後は（回復経路が結線されれば）チャレンジで回復できるので恒久ロックアウトではないが、
  **「何もしていない正規利用者が 30 分で 1 回必ず CAPTCHA を踏む」**のは受容の判断が要る。
- **改善案**: `hasVerifiedSession` の意味を「**有効かつ失効間近でない**」に限定し、
  更新窓（例: 残り 10 分未満なら再発行する）を契約に入れて 2 件で pin する。
  再発行が起きるのは 1 枚あたり高々数回なので、蓄積の上界（pin ②）は壊れない。
- **理由**: SEC-067 は**可用性**の指摘であり、その修正が別の可用性の劣化を生むなら
  正味の改善かどうかを判断する材料が要る。現状はその判断が記録されていない。

### [NEW-004] `usedChallengeTokens` の既定実装に上界・TTL の契約が無い

- **種別**: Design（メモリ増幅）
- **重要度**: Should Fix
- **場所**: `docs/test-design-p3c1-2026-07-29.md` §4 の契約（:261-263）
- **現状**: 「省略時は内蔵（メモリ）」とだけ書かれており、**エントリの寿命も上界も規定が無い**。
  `consume(token, at)` が `at` を受け取るので TTL は実装可能だが、**要求されていない**。
  トークンは Turnstile を通過するたびに 1 件挿入されるので、
  攻撃者は CAPTCHA を解いた分だけ**サーバーのメモリにエントリを積める**。

  このプロジェクトは同型の欠陥を既に 3 度扱っている
  （SEC-023 のメモリ増幅 / SEC-031 の退避 / SEC-041 の saturated マーク）。
  `lib/rate-limit.ts` が件数上限と退避を持つのに、新設のキー空間だけ持たないのは一貫しない。
- **改善案**: 契約に「エントリは**チャレンジトークンの有効期間**（Turnstile は 300 秒）で失効し、
  件数上限と退避を持つ」ことを足し、`lib/rate-limit.ts` の退避と同じ形で 1 件 pin する。
- **理由**: 「差し替え口を用意した」ことは既定実装の品質を保証しない。
  **既定で使われるのは内蔵実装のほう**である（SEC-053 の教訓と同じ構図）。

### [NEW-005] `TRUST_PROXY` 有効時の `x-forwarded-for` は依然として**左端採用**で、append 構成では偽装が通る

- **種別**: Design（セキュリティ）
- **重要度**: Should Fix
- **場所**: `lib/http-guard.ts:120`（`raw.split(',', 1)[0]`）/ §3 の provenance 表
- **現状**: NEW-003 で `x-vercel-forwarded-for` は塞がれたが、**同じ攻撃が `x-forwarded-for` で成立する**。
  `resolveClientIp` は**左端**を採る。左端が信頼できるのは「前段が XFF を**上書き**する」構成に限る。
  ところが nginx の最も普及したレシピは

  ```
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # ← append
  ```

  であり、**クライアントが名乗った値が左端に残る**。この構成で `TRUST_PROXY=1` にすると、
  攻撃者は `X-Forwarded-For: 203.0.113.9` を付けるだけで
  NEW-003 で塞いだのと**まったく同じ 3 つの帰結**（バケット無限生成 / `unverified` 印の無効化 /
  被害者 IP を騙ったログイン締め出し）を達成できる。

  `lib/http-guard.ts:98-99` は「前段プロキシが XFF を上書きすることを確認したうえで有効化すること」と
  既に書いており、**運用上の前提**としては明示されている。しかし
  (a) その前提を守らせる仕組みが無く、(b) ソース pin は `TRUST_PROXY` という**文字列の存在**しか見ていない。
  `TRUST_PROXY` を実装したことで、これまで到達不能だった危険が**到達可能になった**。
- **改善案**（安い順）:
  1. env provenance では **`x-real-ip` を `x-forwarded-for` より優先**する。
     nginx の標準レシピでは `X-Real-IP $remote_addr` が単一値で設定され、append されない。
  2. ソース pin を「`TRUST_PROXY` を含む」から
     「**`TRUST_PROXY` と『上書き』の前提の両方に言及している**」へ強め、
     `docs/tech-stack.md` §4.5 にも append 構成の危険を書く。
  3. （重い）信頼するホップ数を設定可能にし、右端から数える。
- **理由**: 「操作方法を提供する」ことと「安全に操作できるようにする」ことは別である。
  MF-003 で `x-vercel-forwarded-for` を塞いだ論理は、そのまま `x-forwarded-for` にも当てはまる。
