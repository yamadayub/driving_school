# UI設計: 管理者ログイン（F-012）

> 準拠: `/DESIGN.md`。認証方式は Credentials（メール+パスワード, Auth.js v5）確定。`AdminUser` は scrypt ハッシュでseed済み。
> 対応要件: `functional-spec.md` F-012, `business-spec.md` US-011
> ルート: `/admin/login`（既存）。`admin-layout.md` のSidebar/Topbarは使わない**専用の最小シェル**。

## ビジュアルコンセプト

- 「事務スタッフが業務中にサッと開いて入る画面」。マーケティング的な演出は一切不要。中央揃えのシンプルなカード1枚で完結させる。
- 誤入力時のフィードバックは明確に、しかし**どちらのフィールドが誤りかは開示しない**（アカウント列挙攻撃対策）。

- ロゴ + サイト名を上部に小さく配置し、管理画面であることを明示（「管理画面」の文言を明記し、公開サイトとの誤操作を防ぐ）。

## フォーム仕様

| 要素 | 種別 | 必須 | バリデーション |
|------|------|------|-------------|
| メールアドレス | input type=email | Yes | RFC準拠形式（クライアント側は形式チェックのみ、認証可否はサーバー判定） |
| パスワード | input type=password | Yes | 空不可（強度チェックは行わない。強度要件はseed時に管理） |
| ログインボタン | submit button | Yes | 送信中disabled |

- Inputは公開サイトと同一の `Inputs` トークン（DESIGN.md §4）: Border `#CBD5E1`、focus `#1D4ED8` + リング、高さ48px、フォントサイズ16px。
- パスワードフィールドに表示/非表示トグル（目のアイコン、`aria-label="パスワードを表示"` / `"パスワードを隠す"`）を付ける（実務ツールとしての基本配慮）。
- 「パスワードを忘れた場合」導線は**本フェーズでは提供しない**（`tech-stack.md` 未決事項#1・REV-020: デモの管理者はシードで作成、パスワードリセットUIはスコープ外）。この判断はこのUI設計時点でも据え置く。

## 振る舞い仕様

**正常系**:
1. メール・パスワードを入力し「ログイン」を押す
2. ボタンは即座に `disabled` + ローディングスピナー表示に切り替わる（二重送信防止）
3. Auth.js Credentials Provider が検証、成功時は `/admin`（または `callbackUrl` があればその遷移先）へリダイレクト

**異常系**（F-012準拠）:

| ケース | 表示 | 振る舞い |
|--------|------|---------|
| E-012-1 認証失敗（メール不在 or パスワード不一致、いずれも同一メッセージ） | カード内、フォーム上部に `role="alert"` で「メールアドレスまたはパスワードが正しくありません」（Danger, `#DC2626`テキスト + `#FEF2F2`背景の帯） | ボタンのdisabledを解除、パスワード欄は空にリセット（メール欄は保持し再入力の手間を減らす） |
| ネットワークエラー | 「通信に失敗しました。時間をおいて再度お試しください」 | 同上 |
| サーバーエラー(5xx) | 「エラーが発生しました。しばらくしてから再度お試しください」 | 同上 |

- **エラーメッセージの詳細を出さない**: 「メールアドレスが存在しません」のような個別メッセージは表示しない（アカウント列挙対策、E-012-1の汎用エラーメッセージを厳守）。
- レート制限（連続失敗時の一時ロック等）はサーバー側の関心事としてここでは規定しない。UI側は429応答時に「試行回数が多すぎます。しばらくしてからお試しください」を表示できるようにエラーメッセージの型だけ用意する。
  - **注意: 管理者ログインは `functional-spec.md` §4.11 の Tier 契約（202/403 challenge/429）の対象外である。** §4.11 は**公開エンドポイント**（`POST /api/applications` / `POST /api/uploads/license` / `POST /api/chat`）に適用され、`auth.ts` のグローバル軸は P2 の実装（固定ウィンドウ + 予約枠。残余リスクを受容済み）を維持する（`tech-stack.md` §4.5 の決着注記）。**したがってここでの 429 は「拒否」でよく、`form-submission.md` §4 の待機 UI を持ち込まない。** 母数が管理者1名であり、締め出しの影響とセマフォ化のコストが釣り合わないための意図的な差である。


## アクセシビリティ

- `<h1>` はロゴ直下の「管理画面」見出し（視覚的に小さくてもDOM上はh1）。
- エラーメッセージ領域は `role="alert"` かつ `aria-live="assertive"`（フォーム再表示のたびに読み上げられるよう、DOM上は常に存在させ内容の有無で表示/非表示を切り替える実装を推奨）。
- ラベルは `<label for>` で明示的に紐付ける（placeholderのみに頼らない）。
- タッチターゲット48px、フォーカスリングは公開サイトと同一トークン。
