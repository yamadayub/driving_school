### P3-a の実装着手可否: **現時点では着手不可。RV-P3D-001 / 002 / 003 の3件を解消すれば着手可**

3件はいずれも「仕様上の決定を1つ下す」だけで閉じる性質のもの（実装作業を伴わない）であり、数時間で解消できる。それ以外の Must Fix は P3-b 以降の着手条件であり、P3-a を止める理由にはしない。**逆に、この3件を決めないまま P3-a を始めると、P3-a の成果物（セマフォ・公開ラッパ・CSP）そのものを作り直すことになる**ため、着手可否を「可」にはできない。

### 良い点（具体的に）

品質は全体として高い。特に以下は、P2/P2.5 の失敗から正しく学んだ結果として評価する。

1. **SPEC-005 の IDOR 是正が構造的に正しい**（`functional-spec.md:1114`）。「認可チェックを足す」ではなく「**認可すべき対象がリクエストに存在しない API 形状そのものを廃止した**」点が本質的に正しい。`objectKey` が信頼境界を越えなくなったので、実装がどう間違えても任意キーの署名は発行できない。AC-018-3（未存在と非所属を同一 404）まで指定しているのも良い。
2. **§4.11 の「軸の分類表」**（`functional-spec.md:1380-1387`）。「ゲートに使ってよい軸／使ってはならない軸」を*性質*（攻撃者自身に閉じるか / 共有か / 第三者が他人を妨害できるか）で分類したのは、SEC-021 → SEC-029 → SEC-038 で3回繰り返した失敗の**一般形を捉えた抽象化**である。申込者属性軸（メール・電話）を「SEC-021 と同型」として明示的に禁止しているのは、まだ起きていない失敗を先回りで潰している。
3. **AC-PII-1 の「例外・スタックトレース経由の混入も対象」**（`functional-spec.md:1413`）。ロガー直接呼び出しだけを見るテストは実際にはザルであり、この一文があるかないかでテスト設計の質が変わる。
4. **`license-upload.md` §6（機微情報としての扱い）**。`next/image` 禁止（`/_next/image` の CDN キャッシュに免許証を乗せない）、`FileReader` DataURL ではなく `createObjectURL`（`JSON.stringify`・エラーレポート経由の流出面を減らす）、確認画面でサムネイルを再表示しない（ショルダーハック）——いずれも「言われたから書いた」ではなく脅威から演繹されている。11項目のうち #11「スクリーンショット抑止は行わない（できない）」と正直に書いている点も含めて信頼できる。
5. **`form-submission.md` §4** が条件1'-1 に対する UI 側の回答として過不足なく、しかも §11 の申し送り I-1（202 が API 仕様に無い）/ I-3（CSP と Turnstile を同一作業単位で）/ I-6（`idempotencyKey` の照合が発信元非依存）を**自分から挙げている**。本レビューの指摘のうち3件は Designer が既に発見していたものである。
6. **`business-spec.md` §2.3 の保持期間**が、法定年数の丸写しでも「とりあえず1年」でもなく、教習期限9ヶ月＋検定という**業務サイクルから逆算**され、かつ「教習原簿は別系統なので Web 側を法定年数まで持たない」という重複保持の否定まで書かれている。免許証写真を申込本体より意図的に短くした判断も正しい（下記 A-4）。

## A-5. 保持期間の妥当性（`business-spec.md` §2.3）

**業務実態・APPI の観点では妥当。** 根拠が業務サイクルに紐づいており、監査で説明できる形になっている。

- **申込3年**: 教習期限9ヶ月＋検定・本免で最長約1年 → 卒業証明の再発行相談・再入所照会を1〜2シーズン分。妥当。過剰でも過少でもない。
- **問い合わせ1年**: 収集項目が少なく目的が回答に限定される。妥当。
- **免許証写真を DONE+30日 / 最長180日と、申込本体（3年）より意図的に短くした判断は正しい。** 保持期間は「データの重要度」ではなく「利用目的の達成時期」と「漏えい時の被害」で決めるべきで、写真は (a) 窓口で原本確認する時点で目的を達し、(b) 漏えい時の被害が本人確認書類一式として突出する。両方の理由が §2.3 に書かれている。この分離ができている点を評価する。
- **実装可能性**: 未紐付け24時間（`UploadToken.expiresAt` 起算）と受信180日（`createdAt` 起算）は計算可能。**しかし「DONE から30日」は計算不能**——`Application` に status 遷移日時のフィールドが無く、`updatedAt` は他の更新でも動くため代用できない（RV-P3D-008）。
- **バッチの起動方式が未定義**（RV-P3D-007）。Vercel Cron を想定するなら Hobby は1日1回で AC-PII-8「1日1回以上」は満たせるが、**cron が叩く Route Handler は認証が無ければ公開の削除エンドポイントになる**。この論点が仕様のどこにも無い。
- **「受付から14日以内に削除」は運用ルールであり自動化対象外**という整理は妥当（バッチ不要）。ただし管理画面に期限が見えないと守れない（RV-P3D-N04）。

# B. フェーズ分割の妥当性

## B-1. 順序と依存の切り方: **方向は正しい**

基盤 → 送信経路 → 写真 → 管理閲覧という依存の向きは一方向に切れており、判断理由5点はいずれも妥当。特に「CSP は /apply 公開と同時が要求なのでフォーム完成後に足すのでは順序が逆」（理由4）と「写真を送信経路から切ると INQUIRY が先に完結する」（理由5）は、単なる作業分割ではなく**監査単位としての設計**になっている。分割の意図そのものは支持する。

## B-2. 「F-010 の完了は P3-a と P3-b の両方が通ってから」: **守れる構造になっている**

この約束自体は明示され、phase-status と spec-p3-update の双方に書かれている。P3-b 単独で F-010 完了と宣言しない、という一文が両方にあるので運用可能。

## B-3. **分割によって脅威が単位間の隙間に落ちる箇所が3つある**

これが本セクション最大の問題であり、Must Fix 3件に対応する。

1. **P3-a の完了条件が P3-b/P3-c/P4 の成果物に依存している**（RV-P3D-003）。`phase-status.md:176` は P3-a の完了条件を「AC-RL-1〜10 / AC-010-10〜15」としているが:
   - AC-RL-3 の検証（同一 Cookie の4回目が拒否される）には **AC-008-4 のフォームセッション Cookie 発行**が必要 → P3-b
   - AC-RL-6（送信間隔下限）には **フォーム表示時刻**が必要 → P3-b
   - AC-RL-5 / AC-010-14 の対象に `chat:` / `POST /api/chat` が含まれる → **P4**
   - AC-010-15（CSP を /apply 公開と同時）の /apply は → P3-b

   **P3-a は自分の完了条件を満たせない。** このまま進めると「実質的に達成できない条件を、達成したことにして次へ進む」という、P2.5 で 2 回起きた文書と実態の乖離が再発する。
2. **CSP を P3-a で確定するが、許可すべきオリジンは後続単位で増える**（RV-P3D-010）。Turnstile（`challenges.cloudflare.com`、P3-b）、Blob の PUT 先ホスト（`connect-src`、P3-c）、郵便番号解決（サーバー経由にする設計なので `connect-src` は不要、`application-form.md:199`）。P3-a の監査で「CSP 投入済み・`script-src` に `'unsafe-inline'` 無し」と記録しても、P3-b で Turnstile を足した瞬間にその証跡は最終ポリシーを表さなくなる。Designer が I-3 で同じ懸念を挙げている。
3. **P3-b で作った送信経路の検証が P3-c で無効化されうる**（RV-P3D-S04）。P3-b では「送信 = 1リクエスト」だが、P3-c で写真が入ると (a) 発行 API 呼び出しが増え、(b) `license-upload.md` §4.2 の**期限直前の自動再発行がタブを開いている限り無限に回る**。P3-a で「正規利用者が到達しない」と実測して確定した閾値（AC-RL-9）は、この再発行ループを知らずに測った値になる。**正規利用者が自分で自分をレート制限に掛ける**経路が単位間の隙間に落ちている。

# 指摘事項

## Must Fix

### [RV-P3D-001] セマフォの実体（配置・リース・Vercel 実行モデル）が未決定で、AC-RL-1 と AC-010-13 が両立するか判定できない — **P3-a ブロッカー**

- **種別**: Design
- **重要度**: Must Fix
- **場所**: `docs/functional-spec.md:1393`（AC-RL-1）/ `docs/functional-spec.md:713`（AC-010-13）/ `docs/tech-stack.md` §4.5 決着注記
- **現状**:
  > AC-RL-1: 公開エンドポイントの全体流量制御は…「**同時実行数を上限とするセマフォ**」で実装する（処理完了で自動解放されるため枯渇せず…）。上限到達時は (a) 待ち（最大 5秒）→ (b) …劣化応答

  この記述には、実装を一意に決めるために必要な3つの情報が無い。
  1. **セマフォの状態をどこに置くか**。プロセス内（インスタンスローカル）なら Vercel の N インスタンスに対して N 倍の同時実行を許すことになり、「全体流量制御」にならない。KV に置くなら、それは単一ホットキーへの読み書きであり、**AC-010-13（SEC-034: グローバル軸がスループットの単一障害点にならない）と正面から緊張する**。
  2. **解放の保証**。「処理完了で自動解放されるため枯渇せず」は、プロセスが完了する場合にのみ成立する。サーバーレスのタイムアウト・クラッシュ・デプロイ中断では `release` が呼ばれず、KV 実装では**パーミットが永久に漏れてセマフォが枯渇する**——つまり AC-RL-1 が主張する「枯渇しない」性質が、実装形態によっては成立しない。
  3. **「最大5秒の待ち」のコスト**。待っている間も Function インスタンスは占有され課金される。過負荷時に待たせると、同時実行インスタンス数がむしろ増える（保護したい資源を余計に消費する）方向に働きうる。
- **改善案**（仕様に以下を追記して決着させる。実装ではなく決定を先に下す）:
  - セマフォは **KV 上のリース付きカウンタ**とする。`acquire` は `INCR` + `EXPIRE`（TTL = 想定最大処理時間 × 2、例 20秒）で行い、`release` は `DECR`。**`release` が呼ばれなくても TTL でパーミットが自然回復する**ことを AC に書く（「プロセスが異常終了した場合でも、TTL 経過後にパーミットが回復することをユニットテストで固定する」）。
  - AC-010-13 との関係を明記する: セマフォキーは**エンドポイント別に分割**（`sem:applications` / `sem:uploads` / `sem:chat`）し、さらに必要なら固定シャード数 K で分散（`sem:applications:{0..K-1}` をランダム選択）する。これにより単一ホットキーにならない。**「セマフォは `serialize` を経由しない」ことを AC-010-13 の検証対象に含める**。
  - 待ち時間の上限を 5秒から**2秒程度**に見直すか、「待ちは1回だけで、超えたら劣化応答（拒否ではない）へ移る」ことを明記する。Function の最大実行時間との関係も tech-stack に記録する。
- **理由**: P3-a の主要成果物がこのセマフォである。実装形態が決まらないまま着手すると、「プロセス内で実装 → 全体流量制御になっていないと監査で指摘 → 作り直し」または「KV で実装 → AC-010-13 の直列化テストで落ちる → 作り直し」のどちらかが高確率で起きる。**加えて「枯渇しない」という AC-RL-1 の主張自体が、リースを設計しない限り事実にならない**——これは「文書に事実と異なる記述が入り、それが次工程の入力になる」（P2.5 の教訓3）の再発である。

### [RV-P3D-002] 混雑・劣化時のワイヤ契約が3文書で3通りに分かれている — **P3-a ブロッカー**

- **種別**: Design / Bug
- **重要度**: Must Fix
- **場所**: `docs/functional-spec.md:1393`（AC-RL-1）/ `docs/functional-spec.md:684-689`（F-010 Error Responses）/ `docs/ui-design/form-submission.md:208-216`（§4.2 Tier 表）/ `docs/ui-design/application-form.md:77` / `docs/ui-design/license-upload.md:159-160`

### [RV-P3D-004] フォームセッション Cookie 軸は「送らなければ消える」ゲートであり、SEC-038 と同型の穴が残っている

- **種別**: Design（Security）
- **重要度**: Must Fix
- **場所**: `docs/functional-spec.md:1395`（AC-RL-3）/ `docs/functional-spec.md:1383`（軸の分類表）/ `docs/functional-spec.md:490`（AC-008-4）/ `docs/functional-spec.md:1398`（AC-RL-6）/ `docs/ui-design/form-submission.md:187-192`（§3.4）
- **現状**: 条件1'-3 は「`trusted=false` で per-source ゲートが消えるため別軸を必ず併用」を要求し、AC-RL-3 は Cookie 軸 + Turnstile + 送信間隔下限の3つを併用するとしている。しかし:
  1. **Cookie 軸は攻撃者が Cookie を送らなければ存在しない。** 仕様のどこにも「有効なフォームセッション Cookie を持たないリクエストをどう扱うか」が書かれていない。素直に実装すると「Cookie が無ければ Cookie 軸のカウントが無い = 素通り」になる。AC-RL-3 のテスト（**同一 Cookie** からの4回目が拒否される）は green になるが、攻撃者は同一 Cookie を送らない。
  2. **Cookie を送る場合でも、発行が無制限なら軸として機能しない。** `GET /apply` を叩くたびに新しい Cookie が手に入るなら、Cookie 軸は「1リクエストあたり1往復増える」程度のコストしか課さない。Cookie の**発行**に対する流量制御が仕様に無い。
  3. **送信間隔下限はクライアント値に依存している。** `form-submission.md:192` は「マウント時刻はクライアント値なので単独では信頼できない。サーバー側は『セッション Cookie の発行時刻』など自前の基準を別に持つべきだが、それは実装/セキュリティ側の設計に委ねる」と明示的に**未解決のまま委譲している**。仕様側にも受け皿が無い。
  4. **さらに AC-RL-6（3秒未満は静かに拒否）と `form-submission.md` §3.4（拒否せず Tier B へ降格させるだけ）が矛盾している。**

  結果として、条件1'-3 が要求する「必ず併用する3軸」のうち、実際に攻撃者にコストを課すのは **Turnstile 1つだけ**になる。
- **改善案**（§4.11 に追記）:
  - **フォームセッション Cookie を必須にする。** サーバー署名付き（`AUTH_SECRET` 由来の別鍵）で `issuedAt` を含め、`HttpOnly` / `Secure` / `SameSite=Lax` / 30分。**Cookie が無い・壊れている・期限切れのリクエストは「素通り」ではなく Tier B（`403 { challenge: "interactive" }`）へ落とす。** 拒否ではないので条件1'-1 に抵触しない。
  - **Cookie の発行経路（`GET /apply` のレスポンスヘッダ付与）自体を発信元軸で制限する。** 上限は緩くてよい（例: 発信元あたり 30回/10分）。**目的は Cookie 軸を「タダで無限に増やせない」状態にすること**であり、正規利用者は到達しない。
  - **送信間隔はサーバーが持つ `issuedAt`（Cookie 内の署名済み値）と受信時刻の差で判定する。** クライアントのマウント時刻は使わない。これにより (3) が閉じ、Cookie 軸と送信間隔軸が同一の信頼済みタイムスタンプを共有する。
  - **AC-RL-6 を「3秒未満は Tier B へ降格」に統一**し、F-008 境界値表の「下限未満は bot 判定」と `form-submission.md` §3.4 を揃える。「静かに拒否」はハニーポットのみに残す（それも RV-P3D-006 参照）。降格に統一する理由は Designer の指摘が正しいため——下書き復元で確認画面へ一気に飛ぶ正当な経路が存在する。
  - **AC-RL-3 のテストを「同一 Cookie の4回目が拒否される」だけにしない。** 追加で「**Cookie を送らないリクエストが素通りしない**（Tier B になる）」「**Cookie を毎回捨てて新規取得する攻撃者が、Cookie 発行の制限に到達する**」の2本を必須にする。
- **理由**: これは P2.5-b で監査者が発見した SEC-038 と**まったく同じ形**の欠陥である。SEC-038 は「予約枠の判定基準が `cleanSource`（その発信元の1回目か）であって、攻撃者の新品 IP は常に予約枠を引ける」——つまり**防御の前提が「攻撃者が選ばない選択肢」に依存していた**。今回の Cookie 軸も「攻撃者が Cookie を送り続ける」ことを前提にしている。phase-status の教訓「テストが green でも脅威が閉じていない」を、設計段階で潰しておくべき箇所。

- **改善案**: 冪等照合を「`idempotencyKey` **かつ**フォームセッション Cookie（または発信元キー）の一致」で行うか、一致しない場合は `{ idempotent: true }` のみを返し **`id` / `receiptNumber` を返さない**。前者を推奨（RV-P3D-004 で Cookie を必須化するため実装コストが小さい）。AC-010-4 に検証を1行追加する。
- **理由**: Designer の指摘が妥当。修正コストが小さく、P3-b で実装する箇所そのもの。

### [RV-P3D-S07] `UploadToken`（consumed=true）と「対応記録」のライフサイクルが AC-PII-7 の対象外
- **場所**: `docs/functional-spec.md:1419-1420`（AC-PII-7 / 8）/ `prisma/schema.prisma:241-252`
- **現状**: AC-PII-8 は **未消費**の `UploadToken` を消すが、**消費済み（申込に紐付いた）行の削除がどこにも無い**。`UploadToken.objectKey` は AC-PII-1 で「全体をログに出してはならない」とされる程度に機微な値であり、それが**写真本体が消えた後（DONE+30日）も申込と同じ3年間 DB に残る**。AC-PII-7 の対象は `Application` / `LicensePhoto` / Blob のみ。
- **改善案**: AC-PII-7 の対象に **`UploadToken`** を追加する（「対応する Blob オブジェクトが削除された時点で、消費済み `UploadToken` 行も削除する」）。少なくとも「`expiresAt` 経過 + 消費済みの行は写真削除と同時に消す」と書けば、判定は `expiresAt` インデックスで引ける。
- **理由**: 最小限保持の原則（§2.3）の対象は「写真」ではなく「写真に到達しうる情報」である。

### [RV-P3D-S08] 「対応記録を個人非特定で残す」（business §2.2.4）に対応する機能要件が無い
- **場所**: `docs/business-spec.md:179` / `docs/functional-spec.md` F-017（該当記述なし）
- **現状**: 業務仕様は「対応記録（請求の受付・本人確認の結果・対応日）は、削除対象の申込データそのものとは別に、**個人を特定しない形**（受付番号・種別・日付のみ）で残す」と定めるが、F-017 の `DELETE` はレコードを消すだけで記録を残さない。US-018 の受け入れ条件にも無い。
- **改善案**: F-017 に「`DELETE` 実行時に `receiptNumber` / `type` / 実行日時 / 実行者 `adminUserId` のみを持つ削除記録を残す」を追加し（新エンティティ or 追記専用ログ）、AC-017-4 に検証を追加する。**記録に個人情報を含めないこと**（AC-PII-1）も併記。デモとして重すぎるなら「本デモでは対応記録の永続化は範囲外とする」と business §2.2.4 側に注記して整合させる——どちらでもよいが、**業務仕様に書いてあって機能仕様に無い状態を残さない**こと。
- **理由**: 「削除したこと」を証明できないと、APPI 対応の実効性を後から示せない。かつ business ↔ functional の片側だけに要求がある状態は、次の仕様更新で必ず取りこぼされる。

### [RV-P3D-S09] F-008 に API 仕様セクションが無く、フォームが叩く3つの経路が仕様に登録されていない
- **場所**: `docs/functional-spec.md:419-497`（F-008 に API仕様の節が無い）/ `docs/ui-design/application-form.md:172,199` / `docs/functional-spec.md:490`（AC-008-4）
- **現状**: UI 設計は以下を前提にしているが、いずれも仕様に記述が無い。
  1. **フォームセッション Cookie の発行**（`GET /apply` のレスポンス。AC-008-4 に「サーバーが発行する」とはあるが、経路・署名・検証方法が未定義。RV-P3D-004 と対）
  2. **`GET /api/courses` の再利用**（F-002 のもの。取得失敗時は `ErrorState` を出しフォーム全体は落とさない、という良い設計）
  3. **郵便番号 → 住所の解決**（サーバー Route Handler 経由。外部 API をクライアントから叩かない判断は正しい）。**これは未認証の公開 GET エンドポイントであり、ユーザー入力をキーに取る**が、レート制限の対象になるか（§4.11 は「変更系」を対象としている）が未定義。
- **改善案**: F-008 に API 仕様の節を新設し、3経路を登録する。郵便番号解決は「デモ範囲では京都府内の内包データで解決し外部通信を行わない」（`application-form.md:199`）ことを明記すれば、レート制限は軽い扱いで足りる（DB/外部 I/O を伴わないため）。**外部 API を呼ぶ実装に変える場合は §4.11 の対象に含める**ことを条件として書いておく。Designer S-4 への回答も兼ねる。
- **理由**: 「仕様に無い公開エンドポイント」は、AC-010-14 のルート列挙テストの網からも漏れる。

### [RV-P3D-S10] マジックバイト検証（AC-009-3/4）のストレージ I/O を、`consumed` 更新のトランザクション内に入れない旨の明示が必要
- **場所**: `docs/functional-spec.md:569-572`（AC-009-3 / 4 / 6）
- **現状**: AC-009-6 は「`consumed` の更新は申込保存と**同一トランザクション**で行う」、AC-009-3/4 は「格納済みオブジェクトの先頭バイト列を読む」「実サイズを再取得する」。素直に読むと、**トランザクション内でストレージへのネットワーク I/O を行う実装**になりうる。写真2枚で往復4回、モバイル起因の遅延を含むと長時間トランザクションになり、コネクション枯渇の原因になる。
- **改善案**: AC-009-3/4 に「**実体検証はトランザクション開始前に完了させる**。トランザクション内で行うのは `UploadToken` の条件付き更新（`WHERE consumed=false`）と `Application` / `LicensePhoto` の作成のみ」と明記する。検証と消費の間の TOCTOU は、`objectKey` が予測不能かつトークンが単回使用であるため実務上問題にならない（この理由も併記すると Test Agent が納得できる）。
- **理由**: 実装レビュー（P3-c の Phase 7）で必ず出る指摘を、設計で先に潰しておくほうが安い。

### [RV-P3D-S11] Blob 削除成功 → DB 削除失敗の逆方向の不整合が未定義
- **場所**: `docs/functional-spec.md:1065`（F-017 APPI 削除経路）/ `docs/functional-spec.md:1418`（AC-PII-6）
- **現状**: 「Blob 削除 → 成功後に DB 削除」の順序と、Blob 失敗時のロールバック（409）は正しく定義されている（回収不能な孤児を作らないという理由も正しい）。しかし**Blob は消えたが DB 削除に失敗した場合**の扱いが無い。この状態では `LicensePhoto` 行が実体の無い `objectKey` を指し、F-018 の署名発行が失敗する（管理者から見ると原因不明のエラー）。
- **改善案**: AC-017-4 に (c) を追加。「Blob 削除成功後の DB 削除失敗時は 500 を返し、**再実行で完了できる**こと（Blob 削除は既に消えているオブジェクトに対してもエラーにならない＝べき等であること）を結合テストで検証する」。AC-PII-7 の「バッチはべき等」と同じ性質を、手動削除経路にも要求する。
- **理由**: 順序を決めたことで「片側だけ消える」ケースの片方は塞がったが、もう片方は残っている。再実行で収束するなら実害は無いので、**べき等性を明記するだけで閉じる**。

### [RV-P3D-S12] 環境変数一覧に `TURNSTILE_SITE_KEY` / フォームセッション署名鍵 / `CRON_SECRET` が無い
- **場所**: `docs/tech-stack.md` §4.6
- **現状**: `TURNSTILE_SECRET`（サーバー検証用）はあるが、**ウィジェット描画に必要なサイトキー**（`NEXT_PUBLIC_TURNSTILE_SITE_KEY`）が無い。フォームセッション Cookie の署名鍵（`AUTH_SECRET` 流用可否）、`CRON_SECRET`（RV-P3D-007）も同様。
- **改善案**: §4.6 に3つを追加し、`lib/env.ts` の本番 fail-fast 対象に含めるかを明記する（`CRON_SECRET` は必須、`NEXT_PUBLIC_TURNSTILE_SITE_KEY` も /apply 公開時は必須）。**Cookie 署名鍵は `AUTH_SECRET` を直接使わず HKDF 等で用途別に導出する**ことを推奨（鍵の用途分離）。
- **理由**: P3-a で `lib/env.ts` を触るので、そのとき一緒に入れるのが最も安い。

### [RV-P3D-S13] F-018 の「その管理者が閲覧してよい対象か」の *その管理者* が未定義（単一ロール前提の明示が必要）
- **場所**: `docs/phase-status.md:137` / `docs/functional-spec.md:1121`（AC-018-2）
- **現状**: phase-status の要求は「`auth()` に加え『その管理者が閲覧してよい対象か』を毎回サーバー判定」。AC-018-2 はこれを「`photoId` が `applicationId` に属するか」に落としている——これは**リソース間の所有関係**の判定であり、**管理者と申込の間の認可**ではない（現状 `AdminUser` にロール・校舎スコープが無く、全管理者が全件を見られる）。IDOR の主要経路は塞がっているので実装は妥当だが、**要求と実装の対応関係が文書上ずれている**。
- **改善案**: F-018 に「**本デモの認可モデルは単一ロールであり、認証済み管理者は全申込を閲覧できる**。したがって『閲覧してよい対象か』の判定は (a) 認証済みであること、(b) `photoId` が経路の `applicationId` に属すること、の2点で構成される。校舎別スコープ等の細粒度認可は本デモの範囲外」と明記する。**併せて署名発行 API のアクセスログ（AC-018-5 の `applicationId` / `photoId` / `adminUserId`）を必須にする**——細粒度認可が無い以上、事後追跡が唯一の抑止になる。
- **理由**: 監査時に「毎回サーバー判定していない」と誤判定されるのを防ぐ。かつ受容した制約は明示しておくのが P2.5 の教訓（受容した残余リスクは定量化して記録する）に沿う。

## Nice to Have

### [RV-P3D-N01] `receiptNumber` の日次連番は当日の受付件数を第三者に漏らす
`'YYYYMMDD-NNNN'`（`functional-spec.md:725`）は、受付番号を1つ受け取った利用者に**その日の申込件数**を推測させる。将来「受付番号で照会」機能を足すと列挙の入口にもなる。仕様は ULID も許容しているので、**ULID を既定にする**ことを推奨（AC-010-5 は一意性しか要求していないので変更コストはゼロ）。表示上の読みやすさが必要なら、受付番号とは別に人間向けの短縮表示を持つ。

### [RV-P3D-N02] `style-src` の現実解を tech-stack に明記する
RV-P3D-010 で触れたとおり、Next.js のクリティカル CSS inline により `style-src 'unsafe-inline'` は実務上避けられない見込み。AC-008-1 は `script-src` のみを対象としているので仕様違反ではないが、**「CSP を入れた」の意味を過大に報告しない**ため、tech-stack に明記しておくとよい。

### [RV-P3D-N03] 同意日時の格納先を明示する
§2.3.1 #6 は「同意の記録（`privacyConsent` **と同意日時**）」を保持対象としているが、スキーマに同意日時のフィールドは無い。実質 `createdAt` と同一なので**「同意日時は `createdAt` をもって代替する」と明記すれば足りる**。フィールドを増やす必要はない。

### [RV-P3D-N04] 削除要求の「14日以内」を管理画面で可視化する
§2.2.4 の 14日は運用ルールでバッチ対象外という整理は妥当だが、**期限が画面に出ないと守れない**。F-017 の一覧に「削除請求として受け付けた問い合わせ」の期限バッジを出す案を P3-d の Nice to Have として残しておくとよい（デモの見栄えにも効く）。

### [RV-P3D-N05] AC-RL-9 の実測手順をテンプレ化しておく
「正規利用者が到達しないことを実測で示す」は P3-a の完了条件だが、**何をもって実測とするかが人によってぶれる**。最低限「(a) 1申込あたりの総リクエスト数（写真2枚 + 再発行 + 冪等再送を含む最悪ケース）、(b) 同一世帯/同一学校 LAN から同時に申し込む想定人数、(c) それらが閾値の何%に収まるか」の3点を書式として先に決めておくと、P3-a の監査が短くなる。

# D. 横断的所見

## D-1. 仕様 / UI 設計 / セキュリティ制約の三者整合

**方針レベルでは三者が一貫している**（拒否ではなく待ち / PII を出さない / 写真は最も機微 / 最小収集）。矛盾は全て**契約レベル**（どの HTTP ステータス・どのフィールド・どのステップ番号・どのストレージ）に集中している。これは Spec Agent と Designer が**同日に並行して**成果物を書き、相互参照が閉じないまま完了したことに起因する（`functional-spec.md` 00:28 / `application-form.md` 00:31 / `license-upload.md` 00:34 / `spec-p3-update` 00:34）。実際、Designer の申し送り S-1〜S-6 のうち **spec v0.3.0 が回答しているのは S-7（保持期間）のみ**である。

# E. Test Agent への申し送り

実装着手後、テスト設計時に特に注意すべき点。

1. **AC の ID をテスト名に使う**運用（`spec-p3-update` §5）は維持すること。ただし **AC-008-2 だけはステップ番号で書かれているため、フィールド名ベースに読み替える**（RV-P3D-S01 が解決するまでの暫定）。
2. **「テストが green」を完了条件にしない AC が3本ある**（AC-RL-1 / AC-010-11 / AC-018-2）。これらは**攻撃者の視点で書く**こと:
   - AC-RL-1: 「セマフォ上限中でも正規リクエストが待機後に成功する」だけでなく、**「`release` が呼ばれずにプロセスが落ちた後、TTL 経過でパーミットが回復する」**を必ず入れる（RV-P3D-001）。
   - AC-RL-3: 「同一 Cookie の4回目が拒否される」に加えて、**「Cookie を送らない」「毎回新しい Cookie を取る」の2パターン**を必ず入れる（RV-P3D-004）。これが無いテストは P2.5 と同じ「green だが閉じていない」状態を作る。
   - AC-018-2: 申込A の photoId を申込B の経路で要求 → 404 に加えて、**「存在しない photoId」との応答が本文・ヘッダ・ステータス・応答時間まで区別できない**ことを確認する（タイミング差で存在が漏れないか）。
3. **AC-010-14 のルート列挙テストは、ハードコードした期待ルート一覧との比較にしないこと。** `app/api/**/route.ts` を走査し「`POST`/`PATCH`/`DELETE` を export するモジュールは全て所定のラッパを経由する」形で書く。**新しいルートを追加したときに、テストを書き換えなければ落ちる**のが正しい設計。ハードコード一覧だと P3-c で新ルートを足しても green のまま通る。
4. **PII 非エコーバックのテストは「レスポンス JSON 全体の文字列検索」で書く**（`functional-spec.md:1414` の指定どおり）。フィールドを個別に見ると、zod の `input` やスタックトレース経由の混入を見逃す。E2E 側も `page.getByRole('alert')` のテキストに対して同じ検索を行う（`application-form.md:689`）。
5. **ログのテストはロガーをスパイし、引数を再帰的に文字列化して検索する。** `logger.error(err)` のように例外オブジェクトを渡す経路が最も漏れやすい（AC-PII-1 が明示的に対象としている）。
6. **保持期間の境界値テストは純関数に対して行い、`Date` をモックする**（AC-PII-5）。`statusChangedAt` が導入されるまでこのテストは書けない（RV-P3D-008）ので、P3-d の着手前に解決されているか確認すること。
7. **E2E の待機はアニメーション完了に依存させない**（`application-form.md:686`）。ステップ識別は `data-testid="apply-step-<stepId>"`、送信状態は `data-submission-state`、写真スロットは `data-state` を使う。**進捗バーの幅で判定しない。**
8. **待機UI（Tier C/D）の E2E は実時間を待たない。** `CI=1` のときだけサーバー側 `Retry-After` を 1〜2秒に固定できるフックを用意する（`form-submission.md:428`）。60秒待つテストは書かない。
9. **`role="alert"` の単一性**は P2 で確立済み（`next-route-announcer` 無効化）。ただし本フォームでは `FormErrorSummary` と送信エラーが同時に出ない設計になっているので、**同時に出ないこと自体をテストする**（設計の前提が壊れたら検知できるように）。
10. **結合テストで DB 件数まで見る AC が多い**（AC-010-1 / 3 / 4、AC-009-6）。「エラーが返った」ではなく「**レコードが作られていない**」を必ず assert すること。P2 でこの型の取り違えが実際に起きた。
