### P3-a の実装着手可否: **着手不可。ただしブロッカーは新規指摘 1件のみ（RV-P3DR-001）**

前回の3ブロッカー（RV-P3D-001 / 002 / 003）は、**002 は完全に閉じ、001 と 003 は「決定は下されたが決定の中身に欠陥が残った」状態**である。うち 003 の残件は P3-a の成果物を作り直させる性質ではない（完了報告の書き方の問題）。

**着手を止める理由は RV-P3DR-001 の1件だけである**: 確定したセマフォ機構（`INCR` + `EXPIRE` によるキー単位 TTL）は、**AC-RL-1 が「枯渇しない」の成立条件として名指しした「`release` が呼ばれなくてもパーミットが回復する」という性質を、負荷がかかっている状況では提供しない**。しかも **AC-RL-11(a) のテストは、この壊れた実装に対して green になる**。これは前回 RV-P3D-001 で指摘した欠陥の再発であり、かつ P2.5 の教訓「テストが green でも脅威が閉じていない」の再生産である。`lib/semaphore.ts` は P3-a の中核成果物なので、この決定を直さずに着手すると作り直しになる。

**解消に必要なのは仕様上の決定を1つ差し替えることだけ**（機構を「キー単位 TTL カウンタ」から「パーミット単位のリース」へ変更し、AC-RL-11(a) の検証条件を書き換える）で、実装作業は伴わない。他の新規指摘は P3-a の着手条件にしない。

### 良い点（具体的に）

差し戻し対応の質は高い。特に以下は評価する。

1. **RV-P3D-002 の閉じ方が正しい。** 「仕様を正として UI を直す」ではなく「**出来の良かった `form-submission.md` §4.2 を正として仕様側を全て書き換えた**」という判断（`functional-spec.md:768`）は、権威ではなく品質で真実源を選んでおり正しい。実際に5箇所を照合したが、Tier A/B/C/D のステータス・本文形状・契機の列挙まで完全に一致していた。`200 + challengeRequired` は**成果物から完全に消えている**（残存は前回レビュー本文と対応記録の引用のみ）。`license-upload.md` §4.3（`docs/ui-design/license-upload.md:207`）に **202 の受け側が新設**されたのも、指摘していなかった穴を Designer が自分で見つけて塞いだものである。
2. **AC-RL-1 から無条件の主張が消えている**（`functional-spec.md:1504`）。v0.3.0 の「処理完了で自動解放されるため**枯渇せず**」が削除され、「**実装形態が決まらない限り「枯渇しない」という性質は事実にならないため**」という但し書き付きで実体が確定された。主張の書き方としては模範的である（機構の選択が誤っているのは別問題であり、RV-P3DR-001 で扱う）。
3. **AC-010-14 のルート列挙テストが走査型として指定されている**（`functional-spec.md:792`）。「`app/api/**/route.ts` をファイルシステム上で走査」「**既知ルートのハードコード一覧との比較にしてはならない**」「新しいルートを追加したときに、テストを書き換えなければ落ちるのが正しい設計」まで書かれており、要求の**趣旨**（P2 の「テスト対象の取り違え」の再発防止）が実装形態のレベルで固定されている。ラッパの割り当て（`/api/cron/**` → `withCronAuth` / `/api/admin/**` → `withAdminMutation` / それ以外 → `public-guard`）自体を列挙対象にしたのも正しい。
4. **`phase-status.md:255` の運用上の歯止め**——「**P3-a の完了報告で (2) の条件を『達成』と書いてはならない。報告してよいのは構造の存在まで**」。これは指摘していない。「達成できない完了条件は達成したことにする運用に化ける」という診断に対して、条件の分割だけでなく**報告の書き方まで縛った**のは、対症療法ではなく原因への対処である。
5. **RV-P3D-009 が Designer 側で実際に閉じている。** `license-upload.md:131-152` の応答例は2フィールドになり、「**単一の `expiresIn` フィールドは存在しない**」という否定形の注記まで入った。さらに §11 テスト項目8として「**300秒経過時点で自動再発行が発火しないこと**」「単一の `expiresIn` を読むコードが存在しないこと」が追加されており、**混同したらテストで落ちる**状態になっている。文書を直すだけで終わらせなかった点を評価する。
6. **Designer が申し送り外で2件を自主検出した判断は、どちらも妥当かつ必要だった。** (a) `receiptNumber` の ULID 化は完了画面の**最大表示要素**のレイアウトを変える（8+4桁 → 26文字）ため、UI 側で拾わなければ D-3 と完全に同型の欠陥になっていた。`tabular-nums` を使わない・コピー値に視覚的区切りを混入させない・`aria-label` は生値、という帰結まで詰めている。(b) `admin/login.md:68` の「Tier 契約の対象外」明記は、**429 禁止規則の過剰適用**（管理者ログインに待機 UI を持ち込む）を防ぐもので、契約を横展開する実装者が実際に踏む経路である。どちらも「言われたことだけやる」を超えている。
7. **受容した制約が過大報告になっていない。** S08（`business-spec.md:182`「監査証跡としての永続性は保証されない」+「実運用開始時には追記専用テーブルを設けること」）、S13（`functional-spec.md:1201`「細粒度認可が無い以上、事後追跡が唯一の抑止」）、§4.7（`style-src 'unsafe-inline'` を許容し「**CSP を厳格にした」と過大に報告しない**ため明記する、と目的まで書いている）——いずれも「受容した」だけでなく**何を失ったか**と**いつ返済するか**が書かれている。

# B. 新規指摘

## Must Fix

### [RV-P3DR-001] 確定したセマフォ機構（`INCR` + `EXPIRE`）はパーミット単位のリースではなく、AC-RL-1 が成立条件として名指しした「TTL による回復」が負荷時に成立しない — **P3-a ブロッカー**

- **種別**: Bug（設計）
- **重要度**: Must Fix
- **場所**: `docs/tech-stack.md:270-283`（セマフォの実体・確定）/ `docs/functional-spec.md:1504`（AC-RL-1 (b)）/ `docs/functional-spec.md:1514`（AC-RL-11(a)）
- **現状**: 確定内容は次のとおり。

  | 項目 | 確定値 |
  |------|--------|
  | `acquire` | `INCR` + `EXPIRE(TTL)` |
  | `release` | `DECR`（0 未満にクランプ） |
  | TTL | 20秒（`maxDuration` 10秒 × 2） |

  そして AC-RL-1 は「**実装形態が決まらない限り「枯渇しない」という性質は事実にならないため**」実体を確定する、と述べ、AC-RL-11 は「**`release` が呼ばれなくても TTL でパーミットが自然回復する**ことが「枯渇しない」の成立条件」と明記している。

  **問題は、TTL が「パーミット」ではなく「カウンタキー全体」に付いていることである。** この構造では、実装は次の2通りにしかならず、**どちらも AC-RL-11 が要求する性質を提供しない**。

  1. **`EXPIRE` を毎 `acquire` で無条件に発行する場合**（記述どおりの素直な実装）: `EXPIRE` は TTL を毎回 20秒へリセットする。したがって**リクエストが 20秒未満の間隔で到着し続ける限り、キーは永久に期限切れにならない**。`release` が呼ばれずに漏れたパーミット（サーバーレスのタイムアウト・クラッシュ・デプロイ中断——AC-RL-11 自身が「実在する」と認めている経路）は**回復せず累積する**。しかも**タイムアウトは高負荷時に集中して起きる**ため、漏れの発生と TTL が効かない条件が同じ状況で重なる。累積がやがて上限に達すると、**セマフォは恒久的に枯渇し、以後すべての公開送信が Tier C（202）を返し続ける**。「拒否ではなく待ち」にしたはずが「永久に順番が来ない待ち」になり、条件1'-1 が守ろうとした「正規利用者を締め出さない」が最も悪い形で破れる。
  2. **`EXPIRE ... NX` 相当（TTL 未設定時のみ設定）にする場合**: キーは生成から 20秒後に**在庫ごと消える**。処理中のリクエストのパーミットも同時に忘れられるため、境界の前後で**同時実行上限を超えて受け入れる**（最大 2倍）。さらにその後に到着する正当な `release` は新しいカウンタを `DECR` し、0 クランプによってカウントが実態より小さくなる方向へ壊れる。

  **決定的なのは、AC-RL-11(a) のテストがこの欠陥を検出しないことである。** 「`acquire` 後に `release` を呼ばず TTL を経過させると、次の `acquire` が成功する」を素直に書くと、テストは**他のトラフィックが無い状態**で単一キーを放置する。実装 (1) はこの条件では green になる。**green だが脅威は閉じていない**——P2.5 の SEC-038 とまったく同じ構造であり、この設計レビューの一連のプロセスが防ごうとしてきた失敗そのものである。
- **改善案**（仕様上の決定の差し替え。実装作業は伴わない）:
  - **`tech-stack.md` §4.5 の `acquire` / `release` / TTL 行を、パーミット単位のリースへ置き換える。** 具体的には ZSET を使う:
    - `acquire`: (1) `ZREMRANGEBYSCORE sem:<ep>:<shard> -inf <now>` で**期限切れパーミットを掃除**、(2) `ZCARD` が上限未満なら (3) `ZADD sem:<ep>:<shard> <now+TTL> <permitId>`。`permitId` はリクエストごとの乱数。(1)〜(3) は Lua（`EVAL`）1本にまとめて原子性を確保する。キー自体にも保険の `EXPIRE`（TTL × 2 程度）を付けてよいが、**回復の責任は score に持たせる**。
    - `release`: `ZREM sem:<ep>:<shard> <permitId>`。**`permitId` を持つので二重 `release` は自然に冪等**になり、「0 未満にクランプ」という後付けの補正（`DECR` では原子的に書けない）が不要になる。
    - **この形なら、トラフィックが継続していても期限切れパーミットは次の `acquire` の (1) で必ず回収される**——AC-RL-11 が要求する性質が、負荷の有無に依存せず成立する。
  - **AC-RL-11(a) を書き換える**: 「TTL 経過でパーミットが回復する」ではなく「**セマフォが上限まで埋まった状態で、`release` されないパーミットの期限が過ぎた後、`acquire` が継続的に到着している状況でもパーミットが回復する**」ことを検証対象にする。テストは「上限まで acquire → release せず → 時刻を TTL 経過まで進める → **その間も acquire を試行し続ける** → 期限経過後の acquire が成功する」という形にすること。**トラフィックが無い状態で放置するテストは書かない**（それが (1) を green にする書き方である）。
  - AC-RL-11(c)（二重 release でカウンタが負にならない）は、リース方式では「**同一 `permitId` の二重 `release` が他のパーミットを解放しない**」に読み替える。
  - `tech-stack.md` の変更履歴行（`:11`）にも `INCR`+`EXPIRE` が記録されているため、併せて更新すること。
- **理由**: P3-a の中核成果物は `lib/semaphore.ts` である。確定した機構をそのまま実装すると、(a) 主張した性質を持たないものが出来上がり、(b) それを検証するはずの AC が green になり、(c) 発見は Security 監査の実測（「監査者自身が条件1' の3脅威を再現できないこと」）まで遅れる。その時点での修正は `lib/semaphore.ts` の作り直しと **AC-RL-9 の再実測**を伴う。前回 RV-P3D-001 で「実装形態が決まらないまま着手すると作り直しになる」と述べた状況が、**形態は決まったが中身が誤っているという形で残っている**。

### [RV-P3DR-006] シャード K=4 における「同時実行上限」の意味（全体か、シャードあたりか）が未定義で、AC-RL-9 の実測が解釈依存になる

### [RV-P3DR-009] AC-RL-12(c)（ジッタ検証）が仕様上フレーキーになる書き方になっている
- **場所**: `docs/functional-spec.md:1515`（AC-RL-12 (c)）

# D. Test Agent への申し送り（P3-a）

前回レビュー §E の11項目は引き続き有効。**P3-a に固有の追加**を以下に示す。番号は前回からの通し。

12. **セマフォのテストは「トラフィックが無い状態で放置する」形で書かない**（RV-P3DR-001）。AC-RL-11(a) は、**上限まで埋めて `release` せず、その間も `acquire` を試行し続けたうえで**、期限経過後に成功することを検証すること。放置型のテストは、TTL がキー全体に付く壊れた実装に対しても green になる。**これは「P2.5 の教訓を書いたのに同じ型の欠陥が入った」ケースの3例目**（SEC-038 / RV-P3D-004 に続く）であり、テスト設計側が最後の防波堤になる。

13. **時刻とランダムは必ず注入する。** セマフォの TTL・待ち 2秒のポーリング・`retryAfterMs` のジッタ・Cookie の `issuedAt` は、すべて実時間や `Math.random()` を直読みしない形で実装させ、テストから制御すること。`lib/rate-limit.ts` は既に「時刻は必ず注入できる」を設計原則にしており（`MemoryRateLimitStoreOptions.now` のコメントに、実時刻と注入時刻の不一致で退行が検出できなくなった SEC-035 の実例がある）、**セマフォと `lib/form-session.ts` にも同じ原則を適用させること**。実時間 20秒を待つユニットテストは書かない。

14. **ジッタの検証は「2回取って値が違う」で書かない**（RV-P3DR-009）。N 回サンプルして「相異なる値が2つ以上」かつ「全サンプルが基準の ±20% 内」を見る。前者だけだとフレーキー、後者だけだとジッタ 0 でも通る。

15. **ルート列挙テストは、P3-a の時点で「対象0〜1件でも意味がある」形にする。** 走査が0件を返したときに **green にしてはならない**（対象が見つからないのはテストの故障であって合格ではない）。「`app/api/**/route.ts` を走査して少なくとも1件見つかること」を先に assert してから、各モジュールのラッパ経由を検証すること。**この1行が無いと、走査のグロブを間違えた瞬間にテストは永久に green になる**——P2 の「テスト対象の取り違え」を、走査型テスト自身がやってしまう経路である。

16. **`withCronAuth` のテストは「404 が返る」だけで終えない**（AC-PII-10）。「**DB・Blob に一切変更が無い**」まで見ること（AC-PII-10 が明示している）。P2 で「エラーが返った」を検証して「レコードが作られていない」を見なかった型の取り違えが実際に起きている。加えて、**`CRON_SECRET` の比較が定数時間であること**（タイミング差でトークンが漏れない）も P3-a の対象に含めるとよい。

17. **CSP のテストは「ヘッダが存在する」で終えない。** `script-src` に `'unsafe-inline'` が**無い**ことを、ディレクティブをパースして検証する（部分文字列検索だと `style-src 'unsafe-inline'` に引っかかる／逆に見逃す）。**`style-src` の `'unsafe-inline'` は許容されている**ので（`tech-stack.md` §4.7）、両者を混同しないこと。P3-a の検証対象ページは **`/`**（`/apply` は未存在）。

18. **P3-a では「まだ書けないテスト」を空ファイルや `it.skip` で置かない。** `phase-status.md` (2) の8条件は P3-b 以降で書く。**`it.skip` が並ぶと「テストがある」ように見えて実際には何も守っていない**状態になり、完了報告の解像度が下がる。書かないか、`describe` ごと後続単位に置くこと。

19. **`lib/form-session.ts` の署名検証テストには「他鍵で署名されたトークン」を必ず入れる**（AC-RL-13）。改竄・期限切れだけだと、**署名検証を一切していない実装**でも期限チェックだけで一部が green になる。`AUTH_SECRET` から HKDF 導出した別ラベルの鍵で署名したものが弾かれることまで見ると、鍵の用途分離（`tech-stack.md:335`）も同時に固定できる。
