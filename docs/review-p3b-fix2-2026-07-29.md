## 3. 指名された 3 点への明示的判定

### Q1. E2E アサーションの変更（`#turnstile-slot iframe` の個数 → hidden input の value 非空）

**判定: 妥当。テストの弱体化ではない。承認する。**

- **検出力は狭まっていない。** `cf-turnstile-response` の value が非空になるのは
  「ウィジェットが描画され、実行され、トークンがクライアント側の DOM に届いた」ときだけである。
  逆に iframe の存在は**必要条件にすぎず十分条件ではない**（iframe があってもトークンが取れない状態は成立する）。
  したがって **token 非空 ⟹ ウィジェットは描画されている**であり、新アサーションは旧アサーションを含む。
- **RV-P3B-001 が名指しした事故（「本番では全送信が Tier B(403)」）の成否を決めるのは、
  iframe の個数ではなくトークンがクライアントへ渡るかである。** 見る対象を
  **Cloudflare の実装詳細から契約へ移した**変更であり、テスト設計として正しい方向である。
- **2 度の壊れ方を両方捕まえることを確認した。** (1) `ready()` throw → `renderWidget` 未実行 →
  hidden input 自体が無い → `inputValue()` が reject → `.catch(() => '')` で `''` → 赤。
  (2) `cf-turnstile` クラスによる先取り → hidden input はあるが value 空 → 赤。
  **`.catch(() => '')` が (1) を拾う設計になっている**点まで含めて妥当である。
- ⚠️ **ただし、変更理由として書かれた根拠の一部は採用しない。** 追補 §2 は
  「テスト用サイトキー `1x00000000000000000000AA` はチャレンジ UI（iframe）を描画しない」と書くが、
  このキーは Cloudflare が **visible（可視ウィジェット）** として提供しているものであり
  （`.env:37` で使用中）、iframe を描画しないという主張は**確認できていない**。
  本判定は**この根拠に依らず**、上の 3 点だけで承認している。
  **この一文を「確定した事実」として後続の文書へ引き継がないこと。**

### Q2. flaky 1 件（`RV-P3B-002 リロード後もCookieが無ければ必ず再発行される`）の扱い

**判定: P3-c 着手のブロッカーにしない。Test Agent の宿題として起票する（RV-P3B-018）。**
**ただし、追補 §4 の推定原因は誤りである。** 正しい機構を下に書くので、それに基づいて直すこと。

**追補 §4 の推定（`FORM_SESSION_ISSUE_LIMIT`=30 を使い切って Cookie が発行されない）は成立しない。**
`lib/form-session-issue.ts:110-112` は **`!result.success` かつ `clientIp.trusted` のときだけ** `issued:false` を返す。
E2E は縮退構成（`VERCEL !== '1'` → `trusted:false` / `lib/http-guard.ts:108-114`）で走るので、
**30 回枠を使い切っても発行は止まらない**（止めないことは `form-session-route.int.ts:185-194` が
「縮退構成では 40 回目も発行が続く」として明示的に固定している契約でもある）。
枠切れで Cookie が出ないという事象は、この構成では起こりえない。

**実際に起きているのはこうだと考える（連鎖は 1 本しかない）:**

1. 縮退構成の発信元キーは**全要求で共有の `unknown` 単一バケット**である（`lib/http-guard.ts:109-113`）。
   E2E は 3 ブラウザ分の `/apply` 遷移をこの 1 つのバケットに集めるため、
   **無コスト枠 `FORM_SESSION_FREE_ISSUE_LIMIT`(10) を早々に超える**。
2. 以後に発行される Cookie は **`unverified: true`** が付く（`form-session-issue.ts:129`）。
3. `app/(public)/apply/page.tsx:55-56` の `hasSession` は `verifyFormSessionValue` の結果であり、
   印の付いた Cookie に対して **`null` を返す**（`form-session.ts:216`）→ **`hasSession` は false**。
4. その結果、**RV-P3B-002 のサーバー側修正（`hasSession && issued` のときだけ `?fs=1` を剥がす /
   `page.tsx:88-91`）が発火しない。** URL は `?fs=1` を付けたままハイドレーションを待つ。
5. `page.tsx:78-82` のコメントが「クライアントの `replaceState` だけでは足りない」と
   書いたそのレースが**そのまま残る**。テストが `replaceState` の完了前に
   `context.clearCookies()` → `reload()` を撃つと、`/apply?fs=1` が要求され、
   サーバーは「発行は試み済み」と判断して**再発行しない** → Cookie 無し → 赤。リトライでは間に合って緑。

**したがってこれは「E2E の実行環境の癖」ではなく、修正の効き方が構成に依存していることの現れである。**
実害の評価: 本デモの想定配備は Vercel（`trusted:true`）で印は付かないため
**本番では起きない**。縮退構成でも、影響はハイドレーション完了前にリロード／ブックマークした
利用者に限られ、クライアント側の `replaceState` が数百 ms 後に URL を正す。よって**受容可能**であり、
P3-c を止める理由にはならない。

**Test Agent への宿題（RV-P3B-018）**:
`context.clearCookies()` の前に **`?fs` が URL から消えたことを待ってから**リロードする。
```ts
await expect.poll(() => new URL(page.url()).searchParams.has('fs')).toBe(false)
await context.clearCookies()
await page.reload()
```
これはテストを弱めない——「fs が消えること」は同 describe の別テストが独立に固定しており、
本テストが見たいのは**その後に必ず再発行されること**だからである。
**追補 §4 の「env で E2E だけ枠を緩めない」という原則には全面的に同意する。** その形は採らないこと。

### Q3. 残余リスク（縮退構成で発行窓あたり 11 人目以降が Tier B。CAPTCHA では抜けられない）

**判定: 受容する。ただし下の 3 条件を満たすことを条件とする（3 つとも既に満たされている）。**

1. **本デモの想定配備（Vercel / `trusted:true`）では印が一切付かない。**
   `form-session-issue.ts:129` の `!clientIp.trusted &&` を実物で確認し、
   `form-session-issue-cost.test.ts:258-265`（通常構成の到達数は `SOURCE_LIMIT` のまま）が
   これを退行から守っていることも確認した。
2. **出口が実装されている。** RV-P3B-009（Tier B が 2 回続いたら電話番号）が同一単位で入っており、
   「離脱以外の行き先が無い」状態にはならない。**受容の実質的な根拠はここである**
   ——CAPTCHA で抜けられないこと自体より、抜け道が画面に無いことのほうが問題だった。
3. **代替（閾値の引き上げ / 発行時にも Turnstile を課す）はいずれも割に合わない。**
   前者は上界 20 未満の制約で効果が薄く、後者は `GET /api/form-session` を対話的にする＝
   設計変更であり、この単位で入れるべきではない。

**条件として次を P3-c に申し送る:**
- **P3c-1（既出）を守ること**——`uploads` にも同じ形でコストを課す際、**出口（代替導線）も一緒に運ぶこと**。
  コストだけを転用して出口を落とすと、Q3 の受容根拠 2 が P3-c で消える。
- **Vercel 以外へ配備する場合は `trustProxy` を必ず有効化する**（`docs/tech-stack.md` §4.5 の既存の申し送り）。
  これは運用条件として `docs/phase-status.md` に残すこと。

- **現状**: 推定原因が「発行枠 30 を使い切って Cookie が発行されない」となっているが、
  縮退構成では発行は止まらない（§3-Q2 に機構を書いた）。**誤った原因が記録に残ると、
  次に同じ赤を見た者が発行枠を疑って env を緩める方向へ動く**——追補自身が禁じた形である。

- **理由**: フレーキーなテストは放置されると全体が信用されなくなる。原因が分かっている今が最も安く直る。

### [RV-P3B-019] 送信が成功する経路を通す E2E が 1 本も無く、SEC-057 の修正でその追加が難しくなった
- **種別**: Test / Design
- **重要度**: **Must Fix（P3-c の内側で解消すること。P3-b の再検収と P3-c の着手はブロックしない）**
- **場所**: `tests/e2e/playwright/` 全体（`/api/applications` へ POST するテストは 0 本）
- **現状**: RV-P3B-001 は「単体・結合・E2E・型検査・ビルドのすべてを通過した」欠陥だった。
  今回その再発は **(a) ソース走査ユニット (b) トークン取得の E2E** の 2 層で塞いだが、
  **「送信が実際に 201 になる」ことを通しで見るテストは依然として 0 本**である。
  さらに SEC-057 の修正により、E2E が走る縮退構成では**発行窓あたり 11 枚目以降の Cookie に
  未検証の印が付く**（§3-Q2 の連鎖 1〜3）。E2E スイートは共有 `unknown` バケットを使うため、
  **スイートの序盤で枠を使い切り、以降の全コンテキストが「送信すれば必ず Tier B」の状態になる**。
  つまり**今の構成のままでは送信成功の E2E は原理的に書けない**。
- **改善案**（P3-c の設計判断として扱うこと。env で枠を緩める形は採らない）:
  1. 送信を伴うシナリオを**単一のコンテキスト／単一ファイルに集約**し、窓あたりの発行回数を抑える、または
  2. `CI=1` の既存フックの側に、**縮退構成でのみ有効な決定論的な発信元キー**（テストごとに分離される軸）を
     与える形を検討する——「上限を緩める」のではなく「軸を分ける」形なら本番の緩和経路にならない。
  3. どちらも採れないなら、**結合テスト（`applications.int.ts` 系）で送信成功の経路を明示的に固定し、
     E2E ではやらないことを文書に書く**。決めずに次の単位へ持ち越さないこと。
- **理由**: P3-c は**送信経路の上に写真アップロードを載せる**単位である。送信が通ることを
  誰も通しで見ていない土台の上に経路を足すと、RV-P3B-001 と同じ形の欠陥が
  「全レイヤ green のまま本番で機能不成立」として再び通る。**P3-b の教訓が回収されるのはここである。**

### [RV-P3B-020] `data-*-callback` 属性が機能上は死んでいる（契約としては残す）
- **種別**: Maintainability
- **重要度**: **Nit**
- **場所**: `components/apply/ApplicationForm.tsx:766-772`
- **現状**: コンテナから `cf-turnstile` クラスを外したため api.js の暗黙レンダリングは走らない。

- **理由**: 次の実装者が「属性が本番経路だ」と誤読すると、明示 `render()` の側を安全だと思って壊す。

### [RV-P3B-021] Tier B の意味論が文書と実装でずれている
- **種別**: Design / Documentation
- **重要度**: **Should Fix**
- **場所**: `docs/ui-design/form-submission.md` §4.11 系の Tier 定義 / テスト側の文言

## 5. なぜ RV-P3B-019 があっても Approve なのか

前回の差し戻しは「**テストが無いまま承認しない**」という一線で出したものだった。今回それを適用すると
RV-P3B-019（送信成功の通し E2E が無い）は Reject 相当に見えるが、そうしない理由を明記する:

1. **RV-P3B-019 は P3-b の修正が作った欠落ではない。** 送信成功の E2E は P3-b 以前から 0 本で、
   前回の Must Fix 6 件にも含まれていない。**修正の再検収でスコープを広げるのは、
   差し戻しを終わらせない形**であり、レビューとして不健全である。
2. **P3-b が閉じるべきだった穴は塞がっている。** RV-P3B-001 が「全レイヤ green で機能不成立」だった
   原因（クライアント結線を見るテストが 0 本）は、ユニット 5 本 + E2E 2 本で塞がれた。
3. **RV-P3B-019 は P3-c のスコープに構造的に属する。** 解決には E2E の実行構成に関する設計判断
   （軸の分け方）が要り、それは写真アップロードの E2E をどう書くかと**同じ判断**である。
   別々に決めると必ず食い違う。
4. ただし **P3-c の計画に RV-P3B-019 を明示的に載せること**を Approve の条件とする。
   `docs/phase-status.md` と P3-c の計画ファイルの両方に、P3c-1 と並べて記載すること。
