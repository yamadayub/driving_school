# 1. Must Fix

## RV-P3DR2-001 — AC-RL-11(a) の「上限まで取り切る」が K=4 + power of two choices と両立しない

### 何が壊れていたか

AC-RL-11(a) は「**上限（`perShardLimit`）までパーミットを取り切り**」と書いていた。
一方、同じ改版で確定した AC-RL-15(b) により**全体容量は `perShardLimit × K`（K=4）**である。
つまり `perShardLimit` 件を取得しても**容量の 1/4 しか埋まらない**。この状態で TTL を経過させて `acquire` すると、
**期限切れの回収が一切行われていなくても空きシャードが見つかって成功する**。

- (a) は**掃除の有無に関わらず green** になる（＝検証したい性質を一切見ていない）。
- (d)（掃除を消すと (a) が落ちる）**も同時に成立しなくなる**。(d) は RV-P3DR-001 の再発を検知する最後の網だが、
  **網そのものが (a) に依存している**ため、(a) が空振りすると (d) も「落ちない＝確認できた」と誤読される。

加えて「取り切る」の手順自体が power of two choices の下では自明でない。
「`acquire` が失敗するまで繰り返す」と書くと、**4シャード中3つが満杯でも失敗確率は 50%** なので、
**満杯でないのに満杯と判定するフレーキーなテスト**になる。

### 下した決定

改善案の 3 案（1: `SEMAPHORE_SHARDS = 1` を注入 / 2: 固定シードの注入乱数で `perShardLimit × K` 件 / 3: 連続 M 回失敗で判定）のうち、
**案1 を既定、案2 を許容、案3 を禁止**とした。

- **案1 を既定にした理由**: **回収の性質はシャード数に依存しない**（`ZREMRANGEBYSCORE` は各キーに対して働く）。
  したがって単一シャードで検証しても検証力は落ちず、シャード選択の確率性が完全に消えるため**決定的**になる。
  AC-RL-15(b) が `semaphoreTotalLimit() = perShardLimit * SEMAPHORE_SHARDS` を公開する以上、シャード数は既に注入可能な形になっている。
- **案2 を許容した理由**: 「複数シャードでも回収が働く」ことを見たい場合の逃げ道を塞ぐ必要はない。ただし**固定シード必須**とした。
- **案3 を禁止した理由**: 確率的であり、AC-RL-12(c) で「**たまに落ちるテストは無視されるようになる**」と書いたばかりの禁止理由がそのまま当てはまる。
  同じ文書内で一方を禁止し他方を許容すると、禁止理由のほうが空文化する。

さらに**レビューが求めた「(a) が空振りしていないことの前提」を、(d) の手順ではなく (a) 自身の手順（④）に置いた**。

- **理由**: (d) は「実装差し替えで1回確認する」**手順**であって自動テストではない（前回自分で残余リスクとして記録した性質）。
  空振り検知を (d) 側に置くと、**自動で回り続ける歯止めにならない**。④ を (a) の中に置けば、
  **毎回のテスト実行で「本当に満杯だったか」が assert される**。(d) の側には「④ の証跡を先に残す」ことだけを要求した。

### 修正後の AC-RL-11(a)（要旨）

> **①** 「上限まで取り切る」とは**セマフォ全体を満杯にすること**であり、`perShardLimit` 件の取得ではない（理由＝容量の 1/K しか埋まらず常に green になる、を本文に明記）。
> **②** 満杯にする方法は**このテストに限り `SEMAPHORE_SHARDS = 1` を注入する**を既定とする。複数シャードなら AC-RL-15(c) の注入乱数を**固定シード**で使い `perShardLimit × SEMAPHORE_SHARDS` 件を取得する。
> **③** **「`acquire` が失敗するまで取る」で満杯を判定してはならない**（power of two choices では全シャード満杯でなくても失敗しうるためフレーキーになる）。
> **④** 時刻を進める前に、**リース期限前の追加 `acquire` が失敗することを assert する。この assert を省略してはならない**（省略すると最後の `acquire` が「回収されたから成功した」のか「もともと空きがあったから成功した」のか区別できない）。
> **⑤** `release` を呼ばずに注入時刻を TTL 経過まで進める間、`acquire` を継続的に発生させ続け（期限前は失敗し続けることも見る）、期限経過後の `acquire` が成功する。

**(d) の修正**: 「**(d) を行う前に (a) の ④ が存在し通っている証跡を残す**」を追加。
併せてレビュー §A-1 (4) と §D 23 が指摘していた「掃除の間引き実装」の禁止を (d) に取り込み、
**空きが無くて失敗した `acquire` の直後にも期限切れパーミットが消えていること**を1本で固定するよう追記した
（レビュー本体では明示されていない禁止だが、(d) が確率的にしか検知しないため AC 化した）。

## RV-P3DR2-002 — 「同時実行上限を超えて `acquire` が成功しない」の受け入れ条件が無い

### 何が壊れていたか

AC-RL-1 / AC-RL-11 が要求していたのは「待機後に成功する」「429 でなく 202」「期限切れが回復する」「`release` の局所性・冪等性」の4種類だけで、
**「同時に有効なパーミット数が上限を超えない」ことを直接検証する条件が1つも無かった**。
これはセマフォの**存在理由そのもの**であり、しかも `tech-stack.md` の訂正注記が旧機構の欠陥として
**「同時実行上限を最大2倍超過」**を名指ししている——**仕様が「これは欠陥である」と書いた性質に、検出する AC が無い**状態だった。

### 下した決定: レビューの改善案をそのまま採らず、3点構成にした

レビューの改善案は **(e) = 「満杯時の追加 `acquire` が全失敗」＋「TTL 境界をまたいでも総数が上限を超えない」＋「並行 `+10` 件で成功数がちょうど上限」** だった。
**この案をそのまま AC にすると、レビュー自身が挙げた楽観方式を落とせない**と判断したため、構成を変えた（§3 の自己点検で詳述）。

確定した (e) は次の3点で、**すべてを必須**とした。

| # | 内容 | 落とせる壊れた実装 |
|---|------|------------------|
| **(e-1) 振る舞い** | (a) と同じ手順（②③④）で全体を満杯にした状態で、**期限前**の追加 `acquire` が全失敗。`Promise.all` で `semaphoreTotalLimit() + 10` 件を同時 `acquire` したとき**成功数がちょうど上限** | Lua 内で `ZCARD` 判定を忘れている実装（1回の `EVAL` だが上限を守らない） |
| **(e-2) 構造** | 1回の `acquire` が KV クライアントへ発行する**ZSET を読み書きするコマンドが1回だけ**（呼び出しを記録するフェイク KV クライアントで固定）。**`SCRIPT LOAD` / `NOSCRIPT` からの `EVAL` フォールバックは数えない** | 掃除・判定・追加を別コマンドで発行する実装（＝楽観方式） |
| **(e-3) 濃度の最大値** | フェイク KV クライアントが**各コマンド境界で全シャードの ZSET 濃度の合計を記録**し、**最大値が `semaphoreTotalLimit()` を超えない**。**TTL 境界をまたぐ注入時刻の系列**でも見る | 同上（超過の瞬間を直接観測する） |

**(e-2) に `evalsha` の carve-out を入れた理由**: 「クライアントへの発行が1回」と素直に数えると、
**正しい `evalsha` 実装が `NOSCRIPT` フォールバックで2回発行する場合に誤って落ちる**（false red）。
false red は false green と同じくらい早く無視されるようになるので、**「ZSET を読み書きするコマンドの回数」**という数え方に確定した。

# 3. AC 修正後の自己点検（「この AC を素直に読むと、壊れた実装が green になるか」）

**点検方法**: 修正後の AC 本文だけを入力として素直にテストを書いたと仮定し、
**(i) 正しい実装が green になるか**、**(ii) 具体的な壊れた実装が red になるか**を1件ずつ突き合わせた。

## 3.1 AC-RL-11(a)(d)

| 素直に書いたテストの相手 | 判定 | 根拠 |
|------------------------|------|------|
| **正しい実装**（掃除 → 判定 → 追加を1回の `EVAL`）| ✅ **green** | ④ の期限前 `acquire` は満杯なので失敗する。⑤ の期限後 `acquire` は掃除で空きが出るので成功する |
| **掃除（`ZREMRANGEBYSCORE`）を省いた実装** | ✅ **red** | `SEMAPHORE_SHARDS = 1` で満杯にしているため、掃除が無ければ `ZCARD` は `perShardLimit` のまま下がらず、⑤ の最後の `acquire` が失敗する |
| **キー単位 TTL（`EXPIRE` を毎 `acquire` で発行）型の実装** | ✅ **red** | ⑤ が「継続的に `acquire` を発生させ続ける」ことを要求するため TTL が毎回リセットされ、注入時刻をいくら進めてもキーが期限切れにならず最後の `acquire` が失敗する |
| **掃除を「N 回に1回」に間引いた実装** | ✅ **red**（確率的でなく決定的に） | (d) に足した「**失敗した `acquire` の直後にも期限切れが消えていること**」で落ちる。(a) 側だけだとフレーキーになるため条件を分けた |
| **テスト作者が `perShardLimit` 件だけ取得してしまう**（前回の欠陥の再現）| ✅ **書けない／書いても silent green にならない** | ① ② が禁止しているが、**仮に無視して K=4 のまま `perShardLimit` 件で書いても、④ の「期限前の追加 `acquire` が失敗する」assert が失敗する**（空きシャードがあるので成功してしまう）。**空振りが silent green ではなく red として顕在化する**——これが ④ を必須にした核心である |
| **テスト作者が「失敗するまで取る」で満杯判定する** | ✅ **禁止済み。破っても silent green にはならない** | ③ が禁止。破った場合は ④ が確率的に失敗する（フレーキー）ので、少なくとも「気づかれずに green」にはならない |

**結論**: (a) を素直に読んで書いたテストは、**空振りした場合に green ではなく red になる**。
前回の欠陥は「空振りが green で表れる」ことだったので、その経路は閉じている。

## 3.2 AC-RL-11(e)

| 実装 | (e-1) | (e-2) | (e-3) | 総合 |
|------|-------|-------|-------|------|
| **正しい実装**（1回の `EVAL` で掃除 → 判定 → 追加）| green | green | green | ✅ **green（false red なし）** |
| **楽観方式**（`ZADD` → `ZCARD` → 超過なら自分を `ZREM`。**別コマンドで発行**）| **green**（成功数はちょうど上限になる）| ✅ **red** | ✅ **red** | ✅ **red** |
| **1回の `EVAL` だが Lua 内で `ZCARD` 判定が無い** | ✅ **red**（並行 `+10` の成功数が上限を超える）| green | ✅ red | ✅ **red** |
| **正しい `evalsha` 実装で `NOSCRIPT` フォールバックが起きる** | green | green（**carve-out により**）| green | ✅ **green（false red を回避）** |

**ここが今回の点検で最も重要な発見**: **レビューの改善案どおりに (e) を書いていたら、楽観方式を落とせなかった。**
レビュー案は「満杯時の追加 `acquire` が全失敗」「TTL 境界をまたいでも総数が上限を超えない」「並行取得で成功数がちょうど上限」の3つだったが、
**楽観方式は超過した側が後から自分を `ZREM` するので、成功数はちょうど上限になる**。
一瞬の超過は**成功数からは観測できない**——だから (e-2)（構造）と (e-3)（濃度の最大値）を足した。

同時に **(e-2)(e-3) だけでも不十分**である（「1回の `EVAL` だが判定を忘れている」実装は (e-1) でしか落ちない）ため、**3点すべてを必須**とした。
この「なぜ1つでは足りないか」は AC 本文にも書いた（理由が無いと後で「1つでいいのでは」に戻るため。AC-RL-12(c) と同じ扱い）。

**注意して排除した false red**: (e-2) を「クライアントへの発行回数が1回」と素直に数えると正しい `evalsha` 実装が落ちる。
**false red は false green と同じ速さで無視されるようになる**ので、数え方を「ZSET を読み書きするコマンドの回数」に限定した。

# 4. `EVAL` 実現可能性の確認結果（RV-P3DR2-006 / 着手前の唯一の「作り直し」リスク）

レビューが「**唯一「着手後に機構ごと作り直し」になりうる経路**」とした確認を実施した。

| 確認項目 | 結果 | 根拠 |
|---------|------|------|
| **採用する KV クライアント** | **`@upstash/redis` に確定。`@vercel/kv` は採用しない** | **Vercel KV はサービスとして提供終了**しており、既存ストアは 2024年12月に Upstash Redis へ移行済み、新規は Marketplace 経由で Redis プロバイダを入れる形になっている（<https://vercel.com/docs/redis>）。`tech-stack.md` v0.2.0 の「レート制限=Vercel KV(Upstash Redis)」は**実体としては Upstash Redis を指す**ものとして読む旨を §4.5 に記録した |
| **`eval` を提供するか / 複数キーを渡せるか** | **✅ 提供する。渡せる** | `@upstash/redis` は `redis.eval(script, keys, args)` を提供し、`keys` は `string[]`（<https://upstash.com/docs/redis/sdks/ts/commands/scripts/eval>）。REST 経由でも Lua スクリプトは単一の実行単位として処理される |
| **複数キーを渡す際の制約** | **クラスタ構成では同一スロットが必要（`CROSSSLOT`）。ハッシュタグで解決** | Redis Cluster では複数キーコマンドのキーが同一ハッシュスロットに無いと `CROSSSLOT` エラーになる。`{}`（ハッシュタグ）内だけがスロット計算に使われるため、**エンドポイント名を `{}` に入れる**ことで K 個のシャードが必ず同一スロットに載る。単一ノード構成では制約自体が生じない |

**結論: 機構ごとの作り直しは発生しない。** 代替案（楽観方式）へ落ちる分岐には入らない見込み。

**Impl Agent への注意**: 依存を実際に追加する時点で**実物に対して1回再確認**すること（本確認は公式ドキュメントに基づくもので、
インストールした版のシグネチャそのものを叩いたわけではない）。`phase-status.md` の P3-a 行にその旨を書いた。
代替案へ落ちる場合は、**AC-RL-11(e)（特に (e-2)(e-3)）が楽観方式を落とす条件になっている**ため、
**受容を `tech-stack.md` に記録し (e) を書き換えてから**実装すること（この依存関係を §4.5 に明記した）。
