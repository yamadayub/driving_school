## 2. Must Fix の閉鎖検証（詳細）

### 2.1 脅威クラスは本当に閉じたか — 「別の軸へ移っただけ」でないことの確認

前回の失敗は「アカウント軸で塞いだ締め出しがグローバル軸へ移動した」ことだった。同じ誤りを繰り返さないため、
**現行実装で拒否を生みうる全軸を列挙し、単一発信元がそれぞれを枯渇させられるか**を検査した。

| 拒否を生む軸 | 該当コード | 単一発信元で枯渇できるか | 枯渇時に誰が拒否されるか |
|---|---|---|---|
| IP 軸（`trusted=true`） | `:131-136` | **できる**（10回/10分） | **その発信元だけ**（＝攻撃者自身に閉じている。設計どおり） |
| IP 軸（`trusted=false`） | `:131`（consume のみ） | 枯渇しても**ゲートしない** | 誰も拒否されない（失敗時のラベルが変わるだけ） |
| アカウント軸 | `:170`（失敗時 consume） | できる | **誰も拒否されない**（ゲートに使わない。SEC-021 の是正が維持） |
| グローバル軸 | `:148` | **できない**（IP ゲート通過分のみ = 発信元あたり最大 10/10分。100 に達するには 10 発信元以上） | 全員。ただし予約枠が残る |
| 予約枠 | `:153` | **できない**（`cleanSource` は「その IP 軸ウィンドウの 1 回目」のみ = 発信元あたり実質 1/10分） | 全員（＝残余リスク） |

**単一発信元が枯渇させられる軸は IP 軸だけで、それは攻撃者自身にしか作用しない。**
したがって「攻撃ベクタが別の軸へ移動した」形にはなっていない。閉じたのは**単一発信元による締め出し**であり、
残るのは**分散枯渇**（120 超の独立発信元）で、これは軸の移動ではなく**攻撃前提条件の質的な変化**である。

なお `cleanSource` の弁別が有効なのは「攻撃者は自 IP 軸を消費する」ためだが、
**1 発信元あたり 1 リクエストずつ投げる攻撃者は全員が `cleanSource` を満たす**。
Impl はこれを §6.2 で正しく認識し、「予約枠は攻撃者に必要な IP 数を増やすだけで、ゼロにはしない」と書いている。
**この認識が正しいことが、受容の妥当性を担保している**（＝「予約枠で解決した」と誤認していない）。

### 2.2 Impl §6 の実測の妥当性検証（スクリプト出力を信用しない）

Impl の自己検証はスクリプト実行の出力であり、そのままでは検証にならない。
**軸設定の一致**と**各シナリオの結果がコードから導けるか**を独立に確認した。

- **軸設定**: 実装ノート §6 冒頭の「ip 10回/10分・account 5回/15分・global 100回/分・globalReserve 20回/分」は
  `auth.ts:66-69` と**完全に一致**。テストヘルパ `createProductionGuard()`（`login-guard.test.ts:504-518`）が
  account を 100 に緩めているのに対し、§6 は本番値 5 を使っており、**テストより本番に忠実**である。
- **シナリオA**（SEC-029 手順の再現 / 単一 IP 120 リクエスト）: `:131` で 11 回目以降は `gate.success=false` →
  `:136` で `denied` → `:148` に到達しない。よって global は 10 しか進まず、scrypt も 10 回。
  別 IP の管理者は `cleanSource=true`・global に 90 の余裕 → `verify()` → `ok`。**PASS 判定は正当**。
  かつ SEC-029 が記録した攻撃手順（`security-audit.md:938-944`）と**同じ入力**（単一 IP・120 リクエスト）を使っている。
- **シナリオB-1**（100 発信元で global 100/100・予約枠は残る）: 各発信元 1 回なので IP ゲートは通過、
  global が 100 で枯渇。管理者は `cleanSource=true` → `:153` の予約枠（0/20）→ `ok`。導出可能。
- **シナリオB-2**（120 超の発信元）: 予約枠も 20/20 → `:154` で `denied`。**締め出し成立**。導出可能で、
  **Impl が PASS と書かなかったのは正しい**。
- **シナリオC**（SEC-030 縮退）: `trusted=false` なので `:136` を通過し `verify()` 実行 → `ok`。
  誤った資格情報が `invalid-credentials` を返している点は §6.3 の副作用（RV-P25B-002 で判定）。
- **シナリオD**（縮退時 CPU DoS / 500 リクエスト中 scrypt 120）: `cleanSource` は縮退時 常に true（`:141`）なので
  全リクエストが予約枠を引ける → 上限は `global(100) + reserve(20) = 120`。導出可能。
  **縮退でゲートを外したことが CPU DoS の抜け穴になっていない**ことを確認した。
- **シナリオE**（`trusted=true` のブルートフォース耐性）: 11 回目以降は正解パスワードでも `verified=false`。
  `:131-136` から導出可能。**総当たり抑止が維持されている**。

**結論: §6 の実測はシナリオ選択・軸設定・PASS 判定のいずれも正当である。**

### 2.3 受容の判断は妥当か（P2 デモの文脈で）

妥当と判断する。理由:

- 攻撃前提が「120 超の独立した発信元を 1 分間維持」に上がった。P2 デモ（管理者 1 名・非公開の管理画面）に対して
  この規模の資源を投じる攻撃者は想定に含めなくてよい。
- 構造的な解（scrypt セマフォ）は**アーキテクチャの変更**であり、P2.5-b（差し戻し修正）のスコープを明確に超える。
  ここで無理に入れると、P2.5 で起きた「契約を検証しないまま実装が進む」型の事故を再発させる。
- **かつ、受容が「判断」として記録され、P3 の再評価が義務として書かれている**（`tech-stack.md:247-249`）。
  受容の最大のリスクは「受容した事実が忘れられること」だが、その経路は塞がれている。

## 3. 新規指摘事項

### [RV-P25B-001] 共有軸で拒否された試行が IP 軸を消費するため、正規利用者の「予約枠の資格」が失われ、攻撃終了後もロックが尾を引く

- **種別**: Design（可用性）
- **重要度**: **Should Fix**（P3 で対応。P2.5-b のブロッカーにしない）
- **場所**: `lib/login-guard.ts:131`（IP 軸の consume）と `:147-156`（グローバル/予約枠の判定）の順序
- **現状**: `ip.consume` は**グローバル軸の判定より前**に実行される。したがって
  `verify()` に一度も到達せずグローバル軸/予約枠で拒否された試行も、**その発信元の IP 枠を 1 消費する**。

  実装ノート §1 は「攻撃者に有利には働かない（攻撃者の枠が減るだけ）」としているが、
  **これは攻撃者側しか見ていない**。正規利用者側では次が起きる（残余リスクの攻撃が進行中の場合）:

  1. 管理者の 1 回目の試行 → `cleanSource=true` → 予約枠を引こうとするが枯渇 → `denied`。
     **このとき IP 軸は 1 消費されている。**
  2. 管理者の 2 回目以降 → `cleanSource` が **false** になり（`:141`）、`:152` で予約枠を引く資格を失う。
     以後 **IP 軸のウィンドウ（10 分）が明けるまで、予約枠は一切引けない**。
  3. 10 回リトライすると自分の IP 軸が枯渇し、**攻撃が止まった後も最大 10 分間**
     `:136` で拒否され続ける（グローバル軸のウィンドウは 1 分で明けるのに、である）。

  すなわち「共有軸の枯渇 → 発信元軸の枯渇 → 正しい資格情報の拒否」という**軸をまたいだ経路**で、
  不変条件 5.（`:27-28`）が間接的に破れる。残余リスクの攻撃が前提なので新たな脅威ではないが、
  **被害の持続時間を攻撃期間より長くする**点が受容範囲の外にある（受容したのは「窓ごと止まる」ことであって
  「攻撃終了後も 10 分止まる」ことではない）。
- **改善案**: 「IP 軸は `verify()` に到達した試行を数える」に意味を揃える。`consume` の返り値でゲートする
  構造（RV-P25-003）は維持したいので、拒否確定時に**取り消す**のが素直:

```ts
// lib/rate-limit.ts に追加（KV 実装では DECR に対応する）
refund(key: string, now?: number): Promise<void>
```

```ts
// lib/login-guard.ts — グローバル/予約枠で拒否が確定した時点で IP 枠を返す
if (!cleanSource || !limiters.globalReserve) {
  await limiters.ip.refund(ipKey, now)   // verify() に到達しなかった試行は数えない
  return denied(global.retryAfterMs)
}
```

  攻撃者に返却されても不利益はない（その試行では scrypt を消費できていないため）。
  副次的に、`auth.ts:48-54` が主張する「グローバル軸のカウンタ = scrypt 実行回数」と同じ整合が
  **IP 軸にも**成立し、2 つの軸の意味が揃う。
- **理由**: P3 では同じ構造を申込・チャットへ横展開する。未認証経路では「攻撃が止まったのに
  正規利用者が入れない時間が残る」ことの説明コストが管理ログインより桁違いに高い。
  修正は数行で、`refund` は KV 実装（`INCR`/`DECR`）とも自然に対応する。

### [RV-P25B-002] 縮退時に `ip.reset()` が共有 `unknown` バケットを全員分クリアする（Impl §6.3 への判定）

- **種別**: Design（観測性）/ Security（悪用可能性の評価）
- **重要度**: **Should Fix**（悪用不可。P3 で 1 行修正）
- **場所**: `lib/login-guard.ts:163`（`await limiters.ip.reset(ipKey)`）
- **判定**: **悪用可能ではない。P2.5-b としては許容してよい。ただし P3 で修正すべき。**

  Impl が「再監査で扱いを判断されたい」としている件について、次のとおり判定する。

  **悪用可能性: 無し。** 縮退時（`trusted=false`）に共有バケットが担う役割は
  (a) 失敗時のラベル（`:175-177` の `rate-limited` / `invalid-credentials`）と (b) 計数・観測のみで、
  **照合前ゲートには使われない**（`:136`）。したがってバケットがクリアされても
  - scrypt の実行量は変わらない（コスト保護は `global + globalReserve` = 120回/分。`login-guard.test.ts:864-888` が固定）
  - 誤った資格情報が通るようにはならない（`verify()` の結果は独立。fail-open しない）
  - 攻撃者はクリアを**誘発できない**（管理者の認証成功が必要で、それができるなら攻撃は不要）

  なお `docs/security-audit.md:987-989` は旧実装について「共有バケットでは正規ログインの成功が
  攻撃者の消費分まで解放する＝緩む方向にも壊れる」と指摘していた。**旧実装ではこれが実害だった**
  （バケットがゲートだったため、解放は制限の解除を意味した）。現行では同じ挙動が残っているが、
  ゲートでなくなった結果として**実害が消えている**。SEC-030 の当該指摘は実質的に無害化されている。

  **それでも修正すべき理由**: T2-DECISION は選択肢 (C)（ゲート廃止）ではなく (A)（計数のみ）を、
  **「観測は分散攻撃の検知に要る」**という理由で選んでいる（`review-p25b-tests` §T2 選択理由）。
  現行の `reset` は、その唯一の存在理由である観測記録を**管理者が 1 回ログインするたびに消す**。
  選択の根拠を実装が部分的に無効化している状態であり、意味論の一貫性の問題として直すべきである。
- **改善案**（1 行）:

```ts
if (ok) {
  // 縮退時の ipKey は「自分のバケット」ではない。他人の計数まで解放しない（観測を保つ）。
  if (trusted) await limiters.ip.reset(ipKey)
  await limiters.account.reset(accountKey)
  return { outcome: 'ok', retryAfterMs: 0, verified: true }
}
```

  ただし `login-guard.test.ts:800-822`（T2-b）は「12 回失敗 → 失敗が `rate-limited`」を検証しており、
  この経路に成功ログインを挟まないため**既存テストは変更不要**である（コード読解で確認。テストは実行していない）。
  修正時は「縮退時に成功しても共有バケットの計数が残る」を新規テストで固定すること。
- **理由**: 「観測のために計数を残す」と決めた設計が、実際には観測を残さない。
  P3 で `trusted=false` の縮退が未認証エンドポイントへ広がると、分散攻撃の検知手段が
  「誰か 1 人が成功するたびに消える」状態になる。

### [RV-P25B-003] 縮退時の予約枠は「予約」として機能しない（文書に書かれていない）

- **種別**: Documentation / Design（前提の明示）

### [RV-P25B-004] store の時刻ソースと limiter の `now` は独立で、ずれても検出されない

### [RV-P25B-005] 縮退構成では発信元あたりの推測回数制限が完全に消える（120回/分・ロックアウト無し）

## 7. P3 への申し送り

### 7.1 残余リスクをどう扱うべきか（最重要）

**「そのまま横展開してはならない」というのが本レビューの立場である。** 管理ログインでは受容できたが、
未認証エンドポイントでは受容の前提が変わる:

| 観点 | 管理ログイン（P2.5-b で受容） | 未認証エンドポイント（P3） |
|---|---|---|
| 正規利用者の母数 | 1 名 | 全訪問者 |
| 締め出しの意味 | 管理者が窓ごとログインできない | **申込・チャットがサービス停止** |
| 攻撃の動機 | 低い（得るものが無い） | 高い（同業妨害・営業妨害が成立する） |
| 検知 | 管理者本人がすぐ気付く | **誰も気付かない**（訪問者は「壊れている」と思って離脱する） |

したがって P3 では次の順で判断すること:

1. **グローバル軸をセマフォ（同時実行数の上限）へ置き換えるかを最初に決める。**
   固定ウィンドウのカウンタを共有軸の照合前ゲートに使う限り、分散枯渇による締め出しは構造的に消えない。
   セマフォは処理完了で自動解放されるため枯渇せず、過負荷時の症状が「拒否」ではなく「待ち」になる。
   **未認証経路ではこちらが正しい**（SEC-022 修正方針3 の第一候補 / `tech-stack.md:244-249`）。
2. 共有軸をどうしても残す場合は、**「正規利用者が拒否されうる条件」を先に列挙してテストに書く**
   （P2.5 の教訓。攻撃者が拒否される条件だけを検証したテストは可用性の欠陥を素通りさせる）。
3. 申込・チャットには、IP 以外の軸（Turnstile トークン・セッション Cookie）を併用して
   共有軸への依存度を下げること。`trusted=false` の配置ではこれが唯一の実効的な発信元識別になる。

### 7.3 本 Phase で得られた教訓（記録）

P2 の教訓は「テストが green でも本番経路が守られていない」、P2.5 は「red が全部 green になっても脅威が閉じていない」だった。
**P2.5-b で有効に働いたのは、完了条件を「テストが green か」から
「攻撃シナリオが実測で再現しなくなったか」へ移したこと**である（fix-plan の申し送り）。
実際、Impl の §6.2 は「テストは全部 green だが、このシナリオは PASS と書けない」という形で
**テストが捉えていない残余を自ら報告している**。これはテスト green だけを見ていたら出てこない記述である。

もう 1 つ、今回初めて機能した仕組みがある。**誤りを「訂正」ではなく「取り消し線 + 誤りであった事実」として残したこと**である
（`review-p25-tests-2026-07-28.md:95-103,150-166`）。誤りを黙って書き換えると、後任は
「なぜこの契約がこうなっているか」を再発見できず、同じ誤りを再生産する。
**P3 以降も、契約や監査の記述を訂正するときは、旧記述と誤りの理由を残す形を続けること。**
