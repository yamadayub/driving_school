### RV-P3D-001 — セマフォの実体を決着させる ✅

**反映先**: `functional-spec.md` §4.11 AC-RL-1（全面書き換え）/ **AC-RL-11 新設** / AC-010-13 の拡張 / `tech-stack.md` §4.5「セマフォの実体（確定）」新設 / §6 #2

**採用した案**（レビューの改善案をそのまま採用。表は `tech-stack.md` §4.5 が真実源）:

| 項目 | 確定値 | なぜそれか |
|------|--------|-----------|
| 状態の置き場所 | **KV 上のリース付きカウンタ** | プロセス内だと Vercel の N インスタンスに対して N 倍の同時実行を許し、「全体流量制御」という主張が成立しない |
| acquire / release | `INCR` + `EXPIRE(TTL)` / `DECR`（0 未満にクランプ） | 原子操作。`lib/kv.ts` の store を再利用（AC-RL-8 の「判定を複製しない」と整合） |
| **TTL** | **20秒** = 公開ハンドラの `maxDuration`（**10秒**）× 2 | **`release` が呼ばれなくても TTL でパーミットが回復する**ことが「枯渇しない」の成立条件 |
| キー | エンドポイント別 + **固定シャード K=4**（`sem:{applications\|uploads\|chat}:{0..3}`）| 単一ホットキーを避け、AC-010-13（SEC-034）と両立させる |
| 直列化 | **`serialize` を経由しない** | AC-010-13 の検証対象に**明示的に追加した** |
| 待ち | **最大2秒・1回だけ**（100〜200ms ジッタ付きポーリング）→ Tier C（202） | レビュー指摘のとおり 5秒は長すぎる（待機中も Function インスタンスを占有・課金され、過負荷時に保護したい資源をむしろ消費する）。`maxDuration` 10秒に対して 2秒 |

**「事実になる形で書く」ための措置（P2.5 の教訓3 への直接対応）**:
- AC-RL-1 から「処理完了で自動解放されるため**枯渇せず**」という**無条件の主張を削除**し、**成立条件（KV リース + TTL）を併記した形に書き換えた**。
- **AC-RL-11 を新設**し、TTL 回復を**テストで固定する対象**にした: (a) `release` を呼ばずに TTL 経過でパーミットが回復する、(b) release がシャード単位で行われ他シャードを減らさない、(c) 二重 release でカウンタが負にならない。
- **TTL(20秒) と `maxDuration`(10秒) の依存関係**を `tech-stack.md` §4.5 に記録した（`maxDuration` を伸ばすときに TTL を伸ばさないと、処理中のパーミットが早期回復して同時実行上限を超過する）。この依存を書かないと、後から `maxDuration` を変えた人が静かに壊す。

**却下した案**: 「プロセス内セマフォ（インスタンスローカル）」— 全体流量制御にならない。「KV の単一キー」— AC-010-13 と正面衝突する。「待ち 5秒」— 上記のとおり。

### RV-P3D-002 — 混雑・劣化時のワイヤ契約を1つに統一 ✅

**反映先**: `functional-spec.md` §4.11「**混雑・劣化時のワイヤ契約（Tier 表 — 唯一の真実源）**」新設 / **AC-RL-12 新設** / AC-RL-1 の 429 禁止条項を修正 / F-010 API 仕様 Error Responses（SPEC-010）/ F-009 API 仕様 Error Responses / E-010-2・E-010-3・E-010-3b / F-010 境界値表

**採用した契約**（`form-submission.md` §4.2 の Tier 表を正とした。Designer の設計が最も出来が良く、条件1'-1 の意図を正しく実装できる形になっていたため）:

| Tier | 契機 | 応答 |
|------|------|------|
| A | 余裕あり | `201` / `200`（冪等再送） |
| B | Cookie 不在・不正 / 送信間隔下限未満 / ハニーポット非空 / Turnstile 未検証 / 逼迫の兆候 | `403 { challenge: "interactive" }` |
| C | **セマフォ（共有軸）**の上限、待ち上限内に空かず | `202 { retryAfterMs }` |
| D | **発信元軸・フォームセッション軸**（攻撃者自身に閉じた軸）の窓上限 | `429` + `Retry-After` + `{ retryAfterMs }` |

**下した決定**:
- **`200 + challengeRequired` は採らない**（AC-RL-1 の旧記述を廃止）。理由: `200` は既に「冪等再送で既存レコードを返す」に割り当て済みで、同じ 200 に「作成されなかった」意味を重ねると、クライアントは**ボディのフィールド有無で成功判定する**ことになる。「利用者の入力を絶対に失わせない」ことを最優先する経路で、成功判定を最も壊れやすい形にするのは避けるべき。
- **AC-RL-1 の禁止条項を「共有軸の枯渇のみを理由に 429 を返してはならない」と明記**した。Tier D の 429 は per-source 軸に対するものであり抵触しない——この区別が無いと、実装者は「429 は一切禁止」と読んで Tier D も 202 にしてしまう。
- **`Retry-After` / `retryAfterMs` は必ずサーバーが返し、±20% のジッタを含む**（Designer I-2 の thundering herd 懸念への回答）。
- **Tier B の本文は `{ challenge: "interactive" }` のみ**とし、降格理由を区別できないようにした（bot に判定基準を教えない、という「静かに拒否」の目的をここで回収している）。
- **`CI=1` かつ非本番でのみ `retryAfterMs` を 1〜2秒に固定できるテストフック**を仕様に含めた（Designer の申し送りと Test Agent 申し送り 8 への回答。60秒待つ E2E を書かせない）。

**Designer 申し送り I-1（「202 を返す経路が API 仕様に無い」）への回答**: **その指摘が正しく、API 仕様側を直した**。F-010 / F-009 の Error Responses に 202 / 403 challenge / 429 + Retry-After を Tier 対応で記載した。

## 2. その他の Must Fix

### RV-P3D-004 — フォームセッション Cookie が「送らなければ消える」ゲート ✅

**反映先**: **AC-RL-13 新設** / AC-RL-3 全面書き換え / AC-RL-6 全面書き換え / AC-008-4 / §4.11 軸の分類表 / F-010 境界値表

**下した決定**（レビューの改善案を全面採用）:
1. **Cookie を必須にする**。サーバー署名付き（`FORM_SESSION_SECRET`。`AUTH_SECRET` を直接使わず HKDF 等で用途別に導出）で `issuedAt` を含め、`HttpOnly` / `Secure` / `SameSite=Lax` / 30分。**Cookie が無い・壊れている・期限切れは「素通り」ではなく Tier B へ落とす**（拒否ではないので条件1'-1 に抵触しない）。
2. **Cookie の発行経路（`GET /apply`）自体を発信元軸で 30回/10分に制限**する。上限は緩くてよく、目的は「タダで無限に増やせない」状態にすること。
3. **送信間隔はサーバーが持つ `issuedAt` と受信時刻の差で判定**する。クライアントのマウント時刻は使わない（受け取っても無視）。これで Cookie 軸と送信間隔軸が**同一の信頼済みタイムスタンプを共有**する。
4. **AC-RL-6 を「3秒未満は Tier B へ降格」に統一**し、`form-submission.md` §3.4 との矛盾を解消した。「静かに拒否」はハニーポットにも残さない（RV-P3D-006）。
5. **AC-RL-3 のテストを3本必須にした**: 同一 Cookie の4回目が Tier D / **Cookie を送らないリクエストが素通りせず Tier B** / **毎回 Cookie を取り直す発信元が発行制限に到達する**。

**なぜここまで書くか**: SEC-038 は「防御の前提が**攻撃者が選ばない選択肢**に依存していた」欠陥だった。今回の Cookie 軸も「攻撃者が Cookie を送り続ける」ことを前提にしており、まったく同型である。テストが green になっても脅威が閉じない状態を設計段階で潰した。

### RV-P3D-005 — AC-008-3 と下書き保存の衝突 ✅（**ポリシーを決定**）

**決定: AC-008-3 を改訂し、`sessionStorage` の条件付き利用を明示的に許可する**（UI 設計側を潰さない）。改訂後:

> `localStorage` および Cookie への書き込みは**禁止**。`sessionStorage` は以下を**全て**満たす場合に限り許可: (a) タブを閉じると失われる、(b) **自動復元せず**明示操作で復元する、(c) 常時「今すぐ削除する」導線がある、(d) 送信成功・完了画面到達・破棄操作で `removeItem` される、(e) **免許証写真に関わる値（`objectKey` / `uploadToken` / プレビュー URL / `File`）を保存しない**。E2E で (b)(d)(e) を検証。

- **(e) は絶対に緩めない**。`uploadToken` は「このオブジェクトを自分の申込に紐付ける」資格情報で、共有端末に残ると後続利用者が他人の免許証画像を自分の申込に紐付けられる（`license-upload.md` の指摘が正確）。
- **却下した代替案**: 「AC-008-3 を維持して下書き復元を落とす」。`form-submission.md` が指摘するとおり `idempotencyKey` をリロード後に維持できないと二重登録が起きるため、その場合も `idempotencyKey` だけの例外が必要になり、「sessionStorage 全面禁止」は結局成立しない。この整理も仕様に書いた。

### RV-P3D-006 — ハニーポットと汎用エラーの両立不能 ✅（**ポリシーを決定**）

**決定: 「静かに拒否」をやめ、Tier B（`403 { challenge: "interactive" }`）へ降格する**（SPEC-012）。

- サーバーが正常応答と区別できない応答を返すなら、クライアントは汎用エラーを出す判断材料を持たない——**論理的に両立しない**ので、どちらかを捨てるしかない。
- 「静かに拒否」を捨てた理由: (1) bot はほぼ Turnstile を通過できないので**防御効果は維持される**、(2) 誤検知された人間は1タップで通過でき**原因不明の失敗に遭わない**（パスワードマネージャの自動入力・支援技術利用者の a11y 事故を仕様として固定しない）、(3) **Tier B は混雑・Cookie 不在でも返るためハニーポット固有のシグナルにならず**、「bot に判定基準を教えない」という当初の目的も維持される。
- AC-010-3 を「レコードを作らず・**自動返信メールも送らず**・Tier B を返す。結合テストで DB 件数0とメール送信0を検証」に改め、E-010-2 も更新した。
- Designer I-5（ハニーポット検出時のログに入力値を残さない）を **AC-PII-1 の対象に追加**した。

### RV-P3D-008 — `statusChangedAt` の不在 ✅

**反映先**: `prisma/schema.prisma`（`statusChangedAt DateTime?` + `@@index([status, statusChangedAt])`）/ `functional-spec.md` `Application` 型（SPEC-014）/ §4.8 データモデル一覧 / §4.9 インデックス戦略 / AC-PII-5 全面書き換え / AC-017-7 新設 / `business-spec.md` §2.3.1 #3 の起算点

- **`doneAt` ではなく `statusChangedAt` を選んだ理由**: DONE → IN_PROGRESS の差し戻しがあるため、「DONE になった日時」だけでは差し戻し後の状態を表現できない。「status が変わった日時」なら、差し戻しでタイマーがリセットされる（＝対応が完了していないので写真を消さない）という**意図した挙動が自然に出る**。
- 判定純関数のシグネチャを仕様に書いた: `shouldDeletePhotos({ createdAt, status, statusChangedAt, now })` / `shouldDeleteApplication({ type, createdAt, now })`。
- **境界値6本を AC-PII-5 に明記**: 30日ちょうどは削除しない / 30日+1秒で削除 / DONE でない申込は 180日 / `statusChangedAt` が null でも 180日経路で必ず削除される / 差し戻しでリセットされる / 申込3年・問い合わせ1年。
- **マイグレーションは作成していない**（本タスクの制約。P3-d 着手時に生成する）。`npx prisma validate` は通ることを確認済み。

### RV-P3D-010 — CSP のオリジンが後続単位で増える ✅

**仕様側は既に確定済み**（`functional-spec.md` F-009）。UI 設計側に訂正前の記述が残っている。**Impl Agent は UI 設計を実装の一次入力にするため、このまま進むと `expiresIn` 単一フィールドで実装される可能性が実際にある。**

### D-4【RV-P3D-006】ハニーポットの応答が Tier B に変更 — `form-submission.md` §3.3

- 仕様を「**静かに拒否**」から「**Tier B（`403 { challenge: "interactive" }`）へ降格**」に変更した（SPEC-012）。**Designer の「汎用エラーとする」判断の意図（誤検知時に利用者が気づける）は採用され、より良い形に置き換わった**——利用者は「原因不明のエラー」ではなく **CAPTCHA を1タップして通過できる**。
- §3.3 を「ハニーポット検出時は Tier B の可視 CAPTCHA へ遷移する（汎用エラー表示ではない）」に更新すること。§3.2 の Tier B UI をそのまま再利用できる。
- **Tier B の表示は降格理由を出さない**こと（混雑・Cookie 不在・送信間隔・ハニーポットで同一の見た目にする）。

### D-5【RV-P3D-004】送信間隔・Cookie 不在時の UI — `form-submission.md` §3.4

- §3.4 が「マウント時刻はクライアント値なので単独では信頼できない。サーバー側は自前の基準を別に持つべきだが、それは実装/セキュリティ側の設計に委ねる」と**未解決のまま委譲していた**点は、**仕様側で受け皿を用意した**: 送信間隔は**フォームセッション Cookie 内の署名済み `issuedAt`** で判定する（AC-RL-6 / AC-RL-13）。UI はクライアント側のマウント時刻を**送信しなくてよい**。
- §3.4 の「拒否せず Tier B へ降格させるだけ」という Designer の判断が**そのまま採用**され、AC-RL-6 を「静かに拒否」から書き換えた（下書き復元で確認画面へ一気に飛ぶ正当な経路が存在する、という指摘が正しかったため）。
- **Cookie が無い状態で送信された場合の UI**（Tier B）を §3 に追記すること。プライベートブラウジングや Cookie ブロックの利用者が到達しうるため、「もう一度お試しください」ではなく **CAPTCHA を出して通す**導線であることを明示する。

### D-6【RV-P3D-S04】自動再発行の上限と非表示タブでの停止 — `license-upload.md` §4.2

**仕様（SPEC-009 / AC-009-11）で確定した内容を UI 設計に反映すること**:
1. **自動再発行は1スロットあたり最大3回**。到達後は自動再発行を停止し、「送信時に写真の再添付をお願いする」縮退表示へ（写真は任意項目なので送信自体は救済できる、という §4.2 の方針と整合する）。
2. **`document.visibilityState === 'hidden'` の間は再発行しない。** `visibilitychange` での復帰時に期限切れなら Failed 表示へ遷移する。
3. この2点の UI 状態（再発行上限到達 / 復帰時 Failed）を §4.2 の状態遷移に追加すること。

### D-7【RV-P3D-S03】「削除する」ボタンの実体 — `license-upload.md` §5

- **Designer S-5 の提案（`DELETE /api/uploads/license`）を採用した**（SPEC-011）。UI 文言は「**削除する**」のままでよい（実際に消えるため、文言変更は不要）。
- API 契約: `DELETE /api/uploads/license` に `{ objectKey, uploadToken }` を送る。成功は `204`。失敗は理由を区別しない `403`。Tier B/C/D の契約は他の公開変更系と同一。
- §5 に「削除は即時に Blob オブジェクトを消す（orphan 回収バッチを待たない）」旨を追記すること。

### D-8【RV-P3D-S01 / S02】F-008 の Step 番号・年齢下限 — `application-form.md`

- **S-1（F-008 の Step 表更新）: 対応済み。** F-008 の Step 表を UI 設計の確定構成に更新した（SPEC-006）。UI 設計側の変更は不要。
