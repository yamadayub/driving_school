## 1. オーケストレーターによるテスト変更 1 件の judge（最優先）

### 対象
`tests/unit/form-session-degraded-recovery.test.ts`「使用済みトークンの記録は有効期間で失効する」（NEW-004）

### (a) テストの弱体化か — **弱体化ではない。むしろ精度が上がっている**

旧: `isUnmarked(afterExpiry.cookieValue)`（= 固定 `NOW = ISSUED_AT + 10_000` で検証）
新: `verifyFormSessionValue(afterExpiry.cookieValue, SECRET, expiredAt)`（= **発行時刻と同じ時刻**で検証）

`verifyFormSessionValue` が `null` を返す条件は 3 つある:

| 条件 | 実装 | 旧テストでの状態 |
|------|------|----------------|
| 署名が合わない（＝**印が付いている**） | `lib/form-session.ts:249` | **これが測りたい性質** |
| `issuedAt > now`（時計偽装） | 同 :284 | **必ず成立してしまう**（発行 `ISSUED_AT+301_000` / 検証 `ISSUED_AT+10_000`） |
| `now - issuedAt > MAX_AGE_MS` | 同 :285 | 該当せず |

旧テストは 3 条件のうち 2 つ目に**常に**捕まるので、**測りたい 1 つ目が一度も評価されない**。
新しい形は 2 つ目・3 つ目を無効化し、**残る差分が「印の有無」だけ**になる。
1 つの assertion が 1 つの性質だけを見る形になったので、**厳格化である**。

### (b) 測りたい性質が保たれているか — **保たれている**

「TTL を跨いだら同じトークンでも初回扱い（＝印が付かない）」を、以下の順で測っている:

1. 無コスト枠を使い切る（`exhaustFreeQuota`）→ 以降の発行には**必ず印が付く**状態を作る
2. 同一トークンを TTL 経過後に再提示
3. 発行時刻で検証して **`null` でない**＝ 印が付いていない＝ **記録が失効していた**

前提（1）があるので、この assertion が通るのは記録が失効した場合だけである。
**別の理由で green になる経路は無い。**

### (c) Impl の「達成不能」判定と抜け道の却下 — **どちらも妥当**

- **達成不能の判定**: 正しい。上表のとおり、失効が完璧に実装されていても旧テストは red のままだった。
  **Impl がテストを書き換えず、根拠を添えて上げた**のは指示どおりの正しい振る舞いである。
  「テストが通らないからテストを直す」は本プロジェクトが繰り返し警戒してきた圧力であり、
  それに屈せず**エスカレーションした**点は評価する。
- **`CHALLENGE_TOKEN_TTL_MS ≤ 9_000` の却下**: 正しい。TTL を 9 秒にすると同一トークンを
  9 秒ごとに再提示でき、10 分窓で 1 トークンあたり最大 66 枚 = **増幅率 66**。
  REV-P3C1-002 が構造的に 1 へ固定した性質が壊れる。
  しかも `CHALLENGE_TOKEN_TTL_MS ≤ 300_000` の pin は 9_000 でも green なので、
  **テストは этот 抜け道を捕まえられない**——Impl の判断だけがそれを止めた。良い判断である。

### 変異検証について — **的確な変異である**

`if (expiresAt > at) return false` → `if (true) return false` は
`if (expiresAt !== undefined)` の**内側**にあるので、初回のトークンには影響しない
（`expiresAt === undefined` → ブロックを飛ばして `true` を返す）。
したがって影響を受けるのは「一度見たトークンの再提示」だけであり、
回復経路の 3 件も増幅率 1 の 1 件も green のまま、**当該 1 件だけが red になる**。
報告どおりであり、変異の当て方として正確である。

### 自分の見落としの記録

**この欠陥は 3 回目のテスト検収（`review-p3c1-tests-re2-2026-07-29.md`）で私が見逃した。**
NEW-004 のテストを読んで「TTL 経過後に初回扱いへ戻る設計も、siteverify 側が期限切れトークンを
拒否する以上、増幅にはならない」と評価したが、**`isUnmarked` の固定時刻が
`issuedAt > now` に必ず当たる**ことに気付いていなかった。
テストの「意味」を読んで「実行結果」を確かめなかったのが原因である。

## 3. 指摘事項

### [CR-001] 更新窓（NEW-003）が**本番の呼び出し経路から到達不能**で、記録が「結線まで完了」になっている

- **種別**: Design（デッドコード / 記録の正確性）
- **重要度**: **Must Fix**（ただし修正は 2 行 + pin 1 件。または記録の訂正 1 行）
- **場所**: `app/(public)/apply/page.tsx:55-56, 69` / `app/api/form-session/route.ts:147` /
  `docs/impl-p3c1-notes-2026-07-29.md:714`
- **現状**: `GET /api/form-session` の**唯一の呼び出し元**は `app/(public)/apply/page.tsx:71` である
  （`grep` で全走査。他に参照は無く、`fetch` 経由の呼び出しも無い。
  仮にあっても `isNavigationRequest` が false になり :117 で早期 return する）。

  その呼び出しは `:69` の `if (!hasSession && !issued)` に守られており、`hasSession` は

  ```ts
  const hasSession = verifyFormSessionValue(raw, secret, Date.now()) !== null   // :55-56
  ```

  すなわち **更新窓を見ていない**。したがって:

  > **有効だが失効間近**の Cookie を持つ利用者は `hasSession = true` になり、
  > **`/api/form-session` へ一度もリダイレクトされない。**
  > ルート側の `isFormSessionRenewable`（:147）は**この状態の要求を受け取ることが無い。**

  結果として `FORM_SESSION_RENEW_BEFORE_MS` / `isFormSessionRenewable` は
  **本番では一度も true にならない**。RE2-001 の結合テストはルートへ直接
  失効間近の Cookie を渡すので green になるが、**呼び出し元がその要求を作らない。**

  これは NEW-001 で指摘した「受け口が呼ばれることを測っていない」の**一段深い版**である
  （ルートまでは結線され、その手前で止まっている）。

  **⚠️ 私の round-2 の前提には誤りがあったので訂正する。** NEW-003 で
  「従来は `/apply` を開くたびに新しい Cookie が発行されるので**実質的に更新されていた**」と書いたが、
  `:69` は**無効な Cookie のときだけ**リダイレクトするので、
  **有効な Cookie が更新されないのは P3-c1 以前からの挙動**である。
  したがって本件は**退行ではない**——「入れたはずの改善が効いていない」だけである。
  この点で深刻度は下がるが、**記録が「結線まで完了」と述べている**ことは変わらない。

- **改善案**（どちらでもよい）:

  **(A) 呼び出し元を直す（2 行 + pin 1 件）。**

  ```ts
  // app/(public)/apply/page.tsx
  const now = Date.now()
  const presented = verifyFormSessionValue(raw, process.env.FORM_SESSION_SECRET ?? '', now)
  const hasSession = presented !== null && !isFormSessionRenewable(presented, now)
  ```

  無限リダイレクトは起きない——リダイレクト後は新しい Cookie（更新不要）が出るので
  次の評価で `hasSession = true` になる。発行が拒否された場合も `?fs=1`（`issued`）が付くため
  `:69` の `!issued` で止まる。**判定は正典関数を呼ぶだけ**なので AC-RL-8 も守られる。
  pin は `tests/unit/apply-page-contract.test.ts` にソース検査を 1 件足すのが安い
  （`hasSession` の式が `isFormSessionRenewable` を通ること）。

  **(B) 結線しないと決めるなら、記録を訂正する。**
  実装記録 :714 の「更新窓（NEW-003）: **結線まで完了**」を
  「**正典関数とルートまで実装。呼び出し元（`/apply`）は未結線のため現状は不活性**」に改め、
  `docs/test-design-p3c1-2026-07-29.md` と P3-c2 の申し送りにも同じ記録を残す。

- **理由**: どちらを選ぶかは工数の判断でよいが、**「完了」と書いてあって動いていない状態だけは
  残してはならない。** 次の単位（P3-c2 = 写真アップロード）は再監査 §5 が
  「滞在時間が長く Cookie 寿命 30 分との競合が起きやすい」と名指しした領域であり、
  そこで「更新窓は入っているはず」と読まれると、**存在しない防御を前提に設計される。**

### [CR-002] `verifyFormSessionValue` のコメントが、実装していない検査を「している」と書いている

- **種別**: Maintainability
- **重要度**: Should Fix
- **場所**: `lib/form-session.ts:249-264`
- **現状**:

  ```ts
  if (!signatureMatches(sign(payloadPart, secret))) {
      // 印は payload ではなく**署名鍵のラベル**で表されている（SEC-068）ので、
      // 未検証ラベルでも一致しないかを確かめる。一致すれば「印の付いた正規の値」、
      // どちらとも一致しなければ「偽造・改ざん・鍵違い」——**どちらも `null`** を返す
      return null
  }
  ```

  コメントは「**未検証ラベルでも一致しないかを確かめる**」と述べているが、
  実装は `sign(payloadPart, secret, true)` を**一度も計算していない**。
  平文ラベルで一致しなければ即 `null` を返すだけである。

  **振る舞いとしては正しい**（印付きも偽造も `null` になり、攻撃者に区別されない）。
  問題はコメントが実在しない検査を記述していることで、
  将来「印の付いた正規の値」を識別したくなった人（例: メトリクスで Tier B の内訳を取りたい）が
  **既にその判別ができると誤読する**。
  このプロジェクトは「文書と実装の食い違い」を **SEC-069（Medium）**として一度払っており、
  同じ形をセキュリティ関数の内部コメントに残すべきではない。
- **改善案**: コメントを実装に合わせる。例:

  > 印は署名鍵のラベルで表されている（SEC-068）ので、**平文ラベルで一致しない値は
  > 「印の付いた正規の値」か「偽造・改ざん・鍵違い」のどちらかである。
  > 両者を区別する必要が無い**（どちらも Tier B へ落とす）ため、
  > 未検証ラベルでの再検証は行わない——区別しないこと自体が、
  > 攻撃者に応答から状態を読ませないことでもある。

- **理由**: 実装より**強い**ことを書いたコメントは、次の読み手にとって偽の保証になる。

### [CR-003]（Nit）使用済みトークン記録の退避は「未失効のトークン」も落としうる

- **場所**: `lib/form-session-issue.ts:136-146`
- 件数上限に達したとき、期限切れを優先して落としたうえで、なお埋まっていれば**挿入順で最古**を落とす。
  落とされたトークンは（TTL 内でも）次回「初回」として扱われるため、**増幅率が 1 を超えうる**。
  ただし成立させるには `CHALLENGE_TOKEN_MAX_ENTRIES = 10_000` 件の**有効な**トークンを
  300 秒以内に投入する必要がある（＝ CAPTCHA を 1 万回解く）ので、
  **1 枚余分に得るより素直に 1 回解くほうが安い**——実質的に悪用不能である。
  `lib/rate-limit.ts` の退避と同じトレードオフでもある。
  **指摘は「直せ」ではなく、この評価をコメントに 1 行残しておくと次の監査が同じ検討を繰り返さずに済む**、という提案である。

### [CR-004]（Nit）`already-verified` の計数は `issueLimiter` を共有している

- **場所**: `lib/form-session-issue.ts:225`
- 別キー（`apply:fs-revisit:`）だが **limiter インスタンスは発行用と同じ**なので、
  上限 30 / 窓 10 分という設定を暗黙に共有している。計数専用（結果を見ない）なので実害は無いが、
  「再訪の計数にとって 30 という上限値は意味を持たない」ことが読み取りづらい。
  将来 limiter の上限を変える人が、再訪カウンタへの影響を検討してしまう。
  1 行のコメント（「上限値は使わない。キー空間を分けるためだけに同じ limiter を通す」）で足りる。

## 4. 良い点

  `COURSE_FK_FIELD_PATTERN = /(^|[^A-Za-z])courseId([^A-Za-z]|$)/` は、

  （2 本目の外部キーで誤分類になる）に対する実装として正確である。
  判別できない `P2003` を 500 に残す方針も守られている。
- **`lib/cron-auth.ts:140-143`**: シークレット未設定を**計数しない**理由
  （「fail-closed で全要求が 404 になるので上限が即座に埋まり、上限到達ログが実際の攻撃と
  区別できなくなる」）は、契約に書かれていない判断だが**正しい**。
  観測を目的とする機能で、観測をノイズで潰さない配慮ができている。
- **`lib/env.ts` の `TRUST_PROXY`** が `z.enum([...]).optional().transform(...)` で、
  受理値を 4 つに限定したうえで `errorMap` に**なぜ黙って false に倒さないか**を書いている。
  起動時 fail-fast の理由が実行時メッセージに載る形は良い。
- **HKDF ラベルによる SEC-068 の実装**は、payload を 1 バイトも変えずに印を隠しており、
  後方互換（既存形式の Cookie / 手組み Cookie に依存する結合テスト）を壊していない。
  設計文書が「実装方法は指定しない」とした箇所で、**最も安い正解**を選んでいる。
