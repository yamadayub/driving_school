# 1. Must Fix

## RV-P3DR-001（P3-a ブロッカー）: セマフォ機構をパーミット単位のリースへ差し替え ✅

### 何が壊れていたか（受け入れた指摘）

前回確定した `acquire` = `INCR` + `EXPIRE(TTL)` / `release` = `DECR` は、**TTL がパーミットではなくカウンタキー全体に付く**。実装は2通りにしかならず、どちらも AC-RL-11 が「枯渇しない」の成立条件として名指しした性質を提供しない。

1. **`EXPIRE` を毎 `acquire` で発行**: TTL が毎回リセットされ、**リクエストが TTL 未満の間隔で到着し続ける限りキーは永久に期限切れにならない**。`release` されずに漏れたパーミットが累積し、上限に達すると**セマフォが恒久枯渇して全公開送信が Tier C(202) を返し続ける**。**漏れの主因（Function タイムアウト）は高負荷時に集中する**ため、漏れの発生と「TTL が効かない条件」は同じ状況で重なる。「拒否ではなく待ち」が「**永久に順番が来ない待ち**」になる＝条件1'-1 の目的が最悪の形で破れる。
2. **`EXPIRE ... NX`**: キーが在庫ごと消え、**同時実行上限を最大2倍超過**する。

**最も重要な点**: AC-RL-11(a) を素直に（無負荷で放置して）書くと、**実装 1 に対してテストは green になる**。P2.5 の SEC-038 と同一構造であり、この一連の設計レビューが防ごうとしてきた失敗そのもの。

### 下した決定

**機構を ZSET によるパーミット単位のリースへ差し替える**（レビューの改善案どおり）。

| 項目 | 確定 |
|------|------|
| 状態 | KV 上の **ZSET**（`member` = `permitId`（リクエストごとの暗号論的乱数 ≥128bit）/ `score` = リース期限のエポック ms） |
| `acquire` | **Lua（`EVAL`）1本で原子的に**: (1) `ZREMRANGEBYSCORE <key> -inf <now>`（期限切れ掃除）→ (2) `ZCARD <key> < perShardLimit` 判定 → (3) `ZADD <key> <now+TTL> <permitId>`。成功時 `{ key, permitId }` / 空きなしで `nil` |
| `release` | `ZREM <key> <permitId>` |
| TTL | 20秒（= `PUBLIC_HANDLER_MAX_DURATION_SEC × 2`。**定数から導出**） |
| キーの `EXPIRE` | 保険として `TTL × 2` を付けてよいが、**回復の責任は負わせない** |
| `now` | **呼び出し側が渡す**（Lua 内で `TIME` を読まない＝テストから時刻注入可能。Test 申し送り13） |

**この形が成立条件を満たす理由**: 期限切れの回収が**キーの寿命ではなく `acquire` の第1ステップ**で行われるため、**トラフィックが継続していても**（＝漏れが最も起きやすい高負荷時でも）期限切れパーミットは次の `acquire` で必ず回収される。

**副次的に閉じたもの**: `permitId` を持つため**二重 `release` が自然に冪等**（2回目は 0 件削除）になり、`DECR` 方式で必要だった「0 未満にクランプ」という後付け補正（原子的に書けない）が**不要になった**。「他のパーミットを誤って解放する」ことも構造的に起きない。

### AC-RL-11 の書き換え（テストが壊れた実装を green にしないため）

- **(a)**「**上限まで取り切り、いずれも `release` しない → 注入時刻を TTL 経過まで進める間、`acquire` の試行を継続的に発生させ続ける → 期限経過後の `acquire` が成功する**」へ書き換えた。**「無負荷で放置する」形で書いてはならない**と AC 本文に明記した（禁止理由付き）。
- **(c)**「二重 `release` でカウンタが負にならない（0 クランプ）」→「**同一 `permitId` の二重 `release` が他のパーミットを解放しない**」へ読み替えた。
- **(d) を追加**: 「`acquire` から期限切れ掃除（`ZREMRANGEBYSCORE`）を取り除くと (a) が落ちる」ことを実装差し替えで1回確認する。**テスト自身が「何を検出できるか」を検証する**条項であり、RV-P3DR-001 の再発（＝green だが守っていない）を検知する最後の網として入れた。

### 反映先

`functional-spec.md` AC-RL-1(b)(c) / AC-RL-11 / AC-010-10（**レート制限の `INCR`+`EXPIRE` はセマフォとは別物**と注記）/ AC-010-13(a)（原子性は `EVAL` で確保）、`tech-stack.md` §4.5 の表全面差し替え + **訂正注記**（旧機構がなぜ破れるかを残した）+ **変更履歴 `:11` の `INCR`+`EXPIRE` 記述に取り消し線と差し替え先を明記** + §6 #2、`phase-status.md` の RV-P3D-001 行と P3-a 完了条件 (1)。

## RV-P3DR-002（P3-b ブロッカー）: 冪等照合用 `sid` の保持場所 ✅ — **案(A) を採用**

### 決定: `Application.sessionIdHash String?` を追加する（SPEC-017）

- 値は `sid` 生値ではなく **HMAC-SHA256(`sid`, `FORM_SESSION_SECRET` から HKDF で導出した照合専用ラベルの鍵)** の hex。**比較は定数時間**。作成時に書き、以後更新しない。
- **`null` は「不一致」として扱う**（`null` を「誰とでも一致」にしない）。これを書かないと、値を持たない行に対して第三者が `receiptNumber` を引ける穴が空く。
- 検証条件を AC-010-4 に4本追加（同一 Cookie で `receiptNumber` が返る / 別 Cookie では `{ idempotent: true }` のみ / **Cookie 無しは AC-RL-13(b) により先に Tier B で止まり冪等照合に到達しない** / `sessionIdHash` が `null` の行では返らない）。

### 案(B)（KV に短期ウィンドウ）を却下した理由

1. 「同じ申込に関する事実」が DB と KV に分かれ、**TTL 切れという第3の状態**が増える。TTL 切れ後の再送に何を返すかを新たに仕様で決める必要がある（分岐が増える）。
2. その分岐が **UI 側の記述にも波及する**。`ui-design/form-submission.md` §11 I-6 は「Cookie 期限切れ後の再送では `receiptNumber` を受け取れないので**受付番号を偽って表示しない**」と書いており、**(A) ではこの記述がそのまま正しいまま**である（Cookie が切れていれば AC-RL-13(b) で先に Tier B になり、冪等照合に到達しない）。(B) では「Cookie は有効だが KV の窓が切れた」という**新しい経路**が生まれ、UI 側に1行の追加を強いる。
3. **マイグレーションのコストが実質ゼロ**である。`statusChangedAt`（未作成・P3-d 予定）と**1回のマイグレーションにまとめられる**ため（レビュー RV-P3DR-011 が指摘したとおり）。

**＝(A) は「決めるべきことが1つ（保持場所）で済み、既存の UI 記述を無効化しない」案である。** これが決め手。

### 反映先

`prisma/schema.prisma`（フィールド + コメント）/ `functional-spec.md` AC-010-4・`Application` 型・**SPEC-017 の判断記録**・§4.8 データモデル一覧・§4.9 インデックス戦略（**`sessionIdHash` にインデックスは張らない**——検索キーではなく `idempotencyKey` で引いた1行に対する照合値であるため）・AC-PII-1（`sid` / `sessionIdHash` をログ禁止項目に追加）/ `business-spec.md` §2.3.1 #7 / `phase-status.md`（(2) の表と DB ドリフト注記）。

**マイグレーションは作成していない**（担当範囲外の指示 + `statusChangedAt` とまとめる方針のため）。作成時期を「**P3-b 着手前**」と `phase-status.md` に確定した。

## RV-P3DR-004: `403` の共用と Tier 判別ルール ✅（**Spec 側の契約判断を確定。UI 側は Designer へ申し送り**）

### 決定1: Tier 判別に使ってよいのは「ステータス」と「`challenge` フィールドの有無」の2つ

§4.11 の契約ルールに **7 を新設**した。

- `403` + `challenge` あり → **Tier B** / `403` + `challenge` なし → **Tier ではない失敗**（`uploadToken` 検証失敗・写真の紐付け失敗 = E-009-4/5）/ `202` → C / `429` → D。
- **ルール1（`200` の中身で成功/失敗を分けない）が禁じているのは成功系ステータスの多義化であって、失敗系ステータス内の判別ではない**——この区別を書かないと、**正しい実装が「ステータスのみで判別せよ」というテストに落とされる**（レビューの指摘どおり）。
- **`challenge` を持たない 403 に CAPTCHA を出してはならない**（解いて再送しても同じ 403 が返る**抜けられないループ**になる）と明記。
- AC-RL-12 に **(e)** を追加し、「Tier B は必ず `challenge` を含み、非 Tier の 403 は必ず含まない」をラッパ単体テストで固定する。
- F-010 / F-009（POST・DELETE）の API 仕様の 403 行に「**`challenge` を含まない**」を明記した。

### 決定2: Tier B を `428 Precondition Required` へ変える案は**却下**

- 意味論としては 428 のほうが正確である（「先に満たすべき条件がある」）ことは認める。
- しかし **403 は RV-P3D-002 の対応で仕様・UI の5箇所を一致させた直後**であり、ステータスを変えると同じ5箇所を再度動かす。**得られる利益（非 Tier の 403 と衝突しない）は決定1で同等に閉じられる**ため、変更コストに見合わない。
- **ただし「決定1 が守られない実装では 428 案のほうが安全だった」ことは仕様に記録した**（無条件に「403 で問題ない」とは書かない）。歯止めは AC-RL-12(e)。

## RV-P3DR-005: TTL ↔ `maxDuration` の依存をコードで表現する ✅

**AC-RL-15(a) を新設**。`PUBLIC_HANDLER_MAX_DURATION_SEC`（=10）を単一定数として定義し、各公開 Route Handler の `export const maxDuration` と `SEMAPHORE_TTL_SEC` の**両方をそこから導出**する。**ユニットテストで `SEMAPHORE_TTL_SEC === PUBLIC_HANDLER_MAX_DURATION_SEC * 2` と各ハンドラの `maxDuration` 一致を固定**し、片方だけ変えたら落ちるようにする。

指摘の核心（**文書に書くことは「届く場所に置く」ことの代用にならない**）を AC 本文の理由として書いた。`tech-stack.md` §4.5 の該当行にも同じ理由を残した。

## RV-P3DR-006: シャードあたり上限の定義 ✅

**AC-RL-15(b)** と `tech-stack.md` §4.5 で確定:

- **上限は `perShardLimit`（シャードあたり）として定義する。エンドポイント全体の同時実行上限は `perShardLimit × K`。**
- **`semaphoreTotalLimit()` を公開**し、AC-RL-9 の実測記録には**両方の値**を書く（どちらの意味かが読み手に依存しない）。`tech-stack.md` §6 #2 にも換算して記録する旨を追記した。
- **power of two choices を採用**（AC-RL-15(c)）: 1回の `acquire` で2シャードを候補にし、掃除後の `ZCARD` が小さい方へ `ZADD` する。**採否を決めよという指摘に対し「採る」を選んだ理由**: 同じ Lua スクリプトに `KEYS[1] KEYS[2]` を渡すだけでコストがほぼ増えないのに対し、採らない場合は「偏りにより実効容量が公称を下回ることを受容する」と書く必要があり、**受容する理由が無い**（偏りが生む症状は「正規利用者を無用に待たせる」＝条件1'-1 が減らそうとしているもの）。乱数源を注入し固定シードで決定的に検証する。

## RV-P3DR-007: `SemaphoreStore` は `RateLimitStore` と別抽象 ✅

**AC-RL-8 を書き換えた**（新 ID は作らず、本来この条件が意味していたことを明確化する形にした）:

- 本条件が禁じているのは「**判定ロジックの複製**」であって「新しい抽象を作ること」ではない。
- **セマフォは `SemaphoreStore`（`acquire(...) / release(key, permitId)`）という別インタフェースを持ってよく、持つべきである**。理由は、現行 `RateLimitStore` が `get/set/delete` + `{ count, resetAt }` という**「減らないカウンタ」前提の抽象**で `release` を表現できないため（`lib/rate-limit.ts:26-49`）。
- **共有してよいのは KV クライアントと接続設定のみ**。この区別を `lib/kv.ts` の真実源コメントに1行残すことを条件に含めた（レビュー時に確認できる場所に置くため）。

## RV-P3DR-008: `tech-stack.md:257` の無条件の主張 ✅ — **確実に潰した**

「（処理完了で自動解放されるので**枯渇せず**、…）」を次へ書き換えた:

- 「（**パーミット単位のリースとして設計した場合に限り**処理完了・**リース期限の満了**で解放され…。**成立条件は下記「セマフォの実体（確定）」であり、無条件には成立しない**）」

## RV-P3DR-009: ジッタ検証のフレーキーさ ✅

| **D-5** | `form-submission.md` §11 I-6 | **RV-P3DR-002 は案(A)（`Application.sessionIdHash`）を採用したため、I-6 の記述は変更不要**（Cookie が期限切れなら AC-RL-13(b) で先に Tier B になり冪等照合に到達しない＝「受付番号を偽って表示しない」がそのまま正しい）。**確認だけお願いしたい。**（案(B) を採っていれば「Cookie は有効だが冪等ウィンドウが切れた」経路の追記が必要だった。これは案(A) を選んだ理由の1つでもある。） |

# 6. 自己点検（「そのテストの書き方だと壊れた実装が green になる」形になっていないか）

今回の指摘の核心が**受け入れ条件の書き方そのもの**だったため、追加・変更した各 AC を同じ観点で点検した。

| AC | 壊れた実装が green になる書き方だったら？ | 対処 |
|----|--------------------------------|------|
| **AC-RL-11(a)** | 無負荷で放置 → キー単位 TTL の壊れた実装が green（**今回の指摘そのもの**） | 「`acquire` を継続的に到着させ続けたまま」を条件に組み込み、**放置型を禁止と明記**。さらに **(d) で「掃除を消すと落ちるか」を1回確認**する条項を追加した |
| **AC-RL-11(c)** | 「カウンタが負にならない」は、そもそも `release` を実装していなくても green になりうる | 「**同一 `permitId` の二重 `release` が他のパーミットを解放しない**」＝**解放の対象が特定されていること**を見る形に変えた |
| **AC-RL-12(c)** | 「2回取って同値でない」→ ジッタ 0 でも運良く green / 粗い実装で頻繁に赤（フレーキー化して無視される） | N=20 + **±20% レンジ**の2条件にした。前者だけだとフレーキー、後者だけだとジッタ 0 でも通る（レビューの指摘どおり） |
| **AC-RL-15(a)** | 「TTL は 20秒」とだけ書くと、`maxDuration` を変えても**テストは 20秒のまま green** | **`SEMAPHORE_TTL_SEC === PUBLIC_HANDLER_MAX_DURATION_SEC * 2`** という**関係**を固定した（値ではなく関係を検証する） |
| **AC-RL-15(c)** | 「power of two choices である」は実装を読まないと分からない | **乱数源を注入し、固定シードで「候補2つのうち空きの多い方が選ばれる」**を決定的に検証する形にした |
| **AC-010-4（新4条件）** | 「別 Cookie では返らない」だけだと、**`sessionIdHash` が `null` の行**という抜け道が残る | **(d)「`null` の行では返らない」を明示**し、`null` を「不一致」と定義した |
| **AC-RL-12(e)** | 「ステータスのみで判別」だと、正しい実装（`challenge` で分岐）が落ちる | 判別に使ってよい入力を**2つに限定**し、「Tier B は必ず `challenge` を含み、非 Tier の 403 は必ず含まない」を**サーバー側の出力に対して**固定した（クライアント実装に依存しない位置に置いた） |

**残る懸念（記録）**: AC-RL-11(d)（「掃除を消すと落ちるか」の確認）は**手順であって自動テストではない**ため、実施されたかどうかは完了報告の記述に依存する。自動化するならミューテーションテストが要るが、本デモの範囲を超えると判断した。**P3-a の Security 監査で「監査者自身が条件1' の3脅威を再現できないこと」を実測する**際に、**「セマフォを上限まで埋めて `release` せず、負荷をかけ続けた状態で正規リクエストが通るか」を実測項目に含める**ことを申し送る（テストではなく実測で二重に押さえる）。
