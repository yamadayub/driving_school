## 2. 発見した矛盾と訂正（3件）

### SPEC-003: 署名付きPUT URL と uploadToken の有効期限が単一フィールドに混在していた

- **矛盾**: F-009 の API レスポンスは `expiresIn: 300` の1フィールドのみだったが、同じ F-009 の境界値表は「uploadToken 有効期限: 数分（暫定10分）」としていた。300秒と600秒のどちらが uploadToken の寿命なのか仕様から決まらない。
- **なぜ問題か**: 300秒を採ると、写真格納後 5分以内に申込を送信し終えないと写真が捨てられる（ステップ式フォームの残りを5分で終える前提になる）。600秒を署名URLに適用すると、署名URLの露出時間が要求（短期失効・5分目安）を超える。**どちらに寄せても片方の要求を破る。**
- **訂正**: 別物として分離。**署名付きPUT URL = 300秒**（格納操作そのものの猶予）、**uploadToken = 600秒**（格納後、申込送信までの猶予）。レスポンスを `uploadUrlExpiresIn` / `uploadTokenExpiresIn` の2フィールドに変更し、両方を確定値とした。

### SPEC-004: F-010 の境界値「同一IPからの送信 N回/時」が SEC-032・条件1'-3 と矛盾していた

- **矛盾**: 境界値表は制限軸を IP 単独としていたが、Security 監査は「**IP 単独軸に依存しない**」（SEC-032）「`trusted=false` では per-source ゲートが消えるため**別軸を必ず併用**」（条件1'-3 / SEC-038）を要求している。仕様のままテストを書くと、監査が要求した第2軸が存在しない実装が「仕様どおり」として通ってしまう。
- **訂正**: 多軸表（発信元軸 IPv6 `/64` 正規化 / フォームセッション Cookie 軸 / 送信間隔下限 / グローバル軸はセマフォ）へ置き換え、詳細を §4.11 に集約。

### SPEC-005: F-018 の署名URL発行 API が生の `objectKey` を受け取る IDOR 構造だった

- **矛盾**: `POST /api/admin/uploads/sign` の Request は `{ "objectKey": "private/xxx" }`。これは「**認証さえ通れば任意のストレージキーに対する署名URLを発行できる**」構造であり、phase-status の「`auth()` に加え『その管理者が閲覧してよい対象か』を毎回サーバー判定」という要求を**API 形状の時点で満たせない**（サーバーが照合すべき「対象」がリクエストに存在しない）。
- **訂正**: クライアントから `objectKey` を受け取る API を廃止し、`POST /api/admin/applications/[applicationId]/photos/[photoId]/sign` へ変更。`objectKey` は必ずサーバーが DB から引く。`photoId` が `applicationId` に属するかを毎回判定し、未存在と非所属を同一の 404 で返す。

### 訂正に至らなかったが注記した点

- **F-010 の「Server Action 可」**: 矛盾ではないが、SEC-037 が要求する「認証非依存ラッパを**全ての**変更系が通る」ことを構造的に保証しにくいため、変更系を Route Handler に統一する旨を明記した。
- **§4.3「サーバーはフィールド別エラーを返す」と AC-PII-2「入力値をエコーバックしない」**: 両立する（フィールド名とエラーコードのみ返せばよい）ため訂正不要。誤読を避けるため AC-PII-2 でレスポンス形状を `{ field, code }` に固定した。
- **`prisma/schema.prisma`**: `LicensePhoto.applicationId` が非 null のため、申込に紐付く前の写真は `LicensePhoto` 行を持たない。したがって orphan 回収は `UploadToken`（`objectKey` を保持）を起点にするのが唯一の経路であり、AC-PII-8 をその形で記述した。**スキーマ変更は不要**。

## 3. P3 のフェーズ分割案とその理由

### 分割

| 単位 | スコープ | 完了条件（要点） |
|------|---------|----------------|
| **P3-a** | レート制限基盤の本番化 + 公開変更系ラッパ + CSP（**条件2 の実体**） | 品質ゲート全通過 ＋ AC-RL-1〜10 / AC-010-10〜15（SEC-033/032/031+041/034/037/002）＋ 閾値の実測記録 ＋ 監査者自身による条件1' の3脅威の非再現確認 |
| **P3-b** | F-008（ステップ式UI・確認画面）+ F-010（送信・スパム対策・冪等性・自動返信）+ /privacy。**写真は含まない** | 品質ゲート全通過 ＋ AC-008-1〜7 / AC-010-1〜9・16 / AC-PII-1〜3。INQUIRY 経路が単独で完結すること |
| **P3-c** | F-009 免許証写真アップロード + orphan 回収バッチ | 品質ゲート全通過 ＋ AC-009-1〜9 / AC-PII-4・8・9。「紐付かなかった写真が実際に消える」ことの結合テスト実証 |
| **P3-d** | F-017 受信管理（+ APPI 削除）+ F-018 署名付きURL閲覧 + 保持期間バッチ | 品質ゲート全通過 ＋ AC-017-1〜6 / AC-018-1〜6 / AC-PII-5〜7。IDOR の実試行と、削除で DB・Blob 両方が消えることの実測 |

実行順序は P3-a → P3-b → P3-c → P3-d（順次）。Designer の UI 設計は P3-a と並列で先行可。

### 判断理由

1. **依存の向きが一方向に切れる**（基盤 → 送信経路 → 写真 → 管理閲覧）。後段が前段の完了を前提にでき、差し戻しが前段へ波及しない。
2. **セキュリティ検証の性質が単位ごとに異なる**（P3-a=可用性/流量、P3-b=入力検証・スパム・PII、P3-c=ファイル実体・トークン、P3-d=IDOR・削除の完全性）。監査を分けると1回に負う脅威モデルが小さくなり、P2/P2.5 で2度起きた「テストは green だが脅威が閉じていない」型の見落としを検知しやすい。
3. **条件2 は F-010 の完了条件だが、実体はレート制限基盤の本番化**であり、フォームUIとは独立に実装・実測できる。先に片付けることで、UI 実装の途中で基盤設計をやり直す差し戻しを避ける。
4. **CSP（SEC-002）は「/apply の公開と同時」が要求**なので、フォーム完成後に足すのでは順序が逆。P3-a に置く。
5. **写真（P3-c）を送信経路（P3-b）から切る**と、INQUIRY と写真なし APPLICATION が先に動く状態を作れる。デモとして早く価値が出るうえ、写真という最も機微な資産の実装を、送信経路が安定してから単独で監査できる。

### 単位をまたぐ約束

- **F-010 を「完了」と宣言できるのは P3-a と P3-b の両方が通ってから**（条件2 が F-010 の完了条件であるため）。P3-b 単独では完了とみなさない。
- 各単位で `docs/review-p3X-*.md` / `docs/security-audit.md` に追記し、次単位の入力にする。
- 各単位の Security 監査で P2/P2.5 の教訓を明示確認する: (1) テスト対象が本番経路か、(2) テスト green でも脅威シナリオが実測で再現しないか、(3) 文書に事実と異なる数値が入っていないか。

## 4. 確定した保持期間と根拠（business-spec §2.3）

| 対象 | 期間 | 根拠（要約） |
|------|------|------------|
| 申込データ（APPLICATION）| **3年**（受信日起算）| 入所〜卒業〜免許取得が最長約1年（教習期限9ヶ月＋検定・本免）。卒業証明の再発行相談・再入所照会を1〜2シーズンぶんカバー。入所後は別系統の教習原簿があるため、これ以上の長期保管は重複 |
| 問い合わせデータ（INQUIRY）| **1年**（受信日起算）| 収集項目が少なく（住所・免許情報・写真なし）、目的は回答に限られる。同一相談者の再問い合わせ（次の入所シーズン）まで |
| 免許証写真（Blob + LicensePhoto）| **対応完了(DONE)から30日、受信から最長180日**（早い方）| 本人確認の一時的照合資料であり、本受付では窓口で原本確認する。漏えい時の被害が突出して大きいため**申込本体より意図的に短く** |
| 未紐付けアップロード | **トークン失効から24時間** | フォーム離脱後の再開猶予を24時間置き、以後は滞留させない（REV-004 orphan 回収） |
| 削除要求を受けたデータ | **受付から14日以内に削除** | APPI の「遅滞なく」の社内基準 |
| 同意の記録 | 紐付く申込・問い合わせと**同一寿命** | 単独保持は意味をなさず、本人特定情報を伴えば保持期間の延長と同義になるため |

**教習原簿との関係**: 入所後に法令に基づき作成・保管される教習原簿等は**別系統の記録**であり、本節の対象外。Web 申込データを法定年数まで長期保管することはしない（重複保持は最小限保持の原則に反する）。

**デモのスコープ**: 実在の個人情報は本運用で保管しない（business §1.3）が、**デモ実装は §2.3 の値をそのまま実装する**（値が実装に無いと保持期間の遵守を検証できないため）。
