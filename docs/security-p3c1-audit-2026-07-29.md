## 1. SEC-067 —「自己維持の切断」は達成されていない（**最優先の指摘**）

### 1.1 申告の内容

実装記録 §「SEC-067 / SEC-068」および §申告事項 1 は次のように整理している。

| 項目 | 実装記録の申告 |
|------|--------------|
| 自己維持の切断（`hasVerifiedSession`） | **結線まで完了** |
| 回復経路（`challengeToken`） | 正典関数の契約のみ。結線は P3-c2 |

### 1.2 実測（プローブ 1）— **切れていない**

原指摘 SEC-067 の「自己維持」は、私が次のように定義したものである:

> 印の付いた利用者は `app/(public)/apply/page.tsx:55-71` で `hasSession=false` と判定され、
> **ページを開くたびに `/api/form-session` へリダイレクトして発行枠をもう 1 つ消費する**。
> すなわち**被害者の再試行そのものが無コスト枠を食い潰し、ロックアウトが自己維持する**。

本番ルート `app/api/form-session/route.ts:137-148` の判定をそのまま写して実測した:

```
攻撃者が 10 回発行して無コスト枠を使い切った
被害者の初回来訪: Cookie 発行=true / 印なし(=使える)=false
被害者の再訪 10 回: 発行された=10 / already-verified で発行が省かれた=0
>>> 印付き被害者の再訪で発行枠が消費され続ける = YES（自己維持は切れていない）
```

**原因は構造的であり、実装ミスではない。** `hasVerifiedSession` は

```ts
hasVerifiedSession: presented !== null && !isFormSessionRenewable(presented, now)
```

で決まるが、**印の付いた Cookie に対して `verifyFormSessionValue` は必ず `null` を返す**
（`lib/form-session.ts:249-264` / SEC-068 の設計上そうでなければならない）。
したがって**印の付いた利用者では `hasVerifiedSession` が原理的に `true` にならない**。
そしてそれは**正しい**——ここを `true` にすると Senior 申し送り 2 と
`form-session-route.int.ts:345` が禁じた「ロックアウトの恒久化」になる。

すなわち `hasVerifiedSession` は、**自己維持ループの被害者にはそもそも到達しない**。

### 1.3 では `hasVerifiedSession` は何を閉じたのか（過小報告にしないための評価）

**別の、かつ実在する攻撃経路を閉じている。** REV-P3C1-001 が指摘した
「攻撃者が 1 枚の有効な Cookie を提示し続けて印の無い Cookie を積み上げる」経路である。
プローブ 3(a) で実測した:

```
(a) 有効な Cookie を 200 回提示 → 使える Cookie の追加取得 = 0 枚
```

これは **SEC-057 の再発防止**として価値がある（実装記録が引く「素朴な実装では到達数 600」という
Test Agent の実測が正しければ、上界 30 の 20 倍を防いだことになる）。
**閉じたこと自体は本物であり、過小評価してはならない。** 誤っているのは**ラベル**である。

さらに NEW-003（更新窓 / `isFormSessionRenewable`）は、
「有効な Cookie を持つ限り二度と更新されず 30 分で必ず失効する」という
**この修正自身が作りかけた新しい締め出し**を先回りして潰している。これも正当な成果である。

### 1.4 残っている攻撃可能性（**具体的に述べよ**という依頼への回答）

**攻撃 A（SEC-067 本体・未是正）**: 縮退構成で、第三者が `GET /api/form-session` を
**10 回/10 分**（≒ 1 分に 1 回）送るだけで、以後その窓の新規来訪者全員が
印付き Cookie を受け取り、送信が 403 Tier B になる。**CAPTCHA では抜けられない**
（Turnstile 検証は `app/api/applications/route.ts:283` のハンドラ内にあり、
`lib/public-guard.ts:374-385` の Tier B 判定より後なので一度も評価されない）。

**攻撃 B（自己維持・未是正 / プローブ 2 で実測）**: **攻撃者が完全に手を引いた後も**、
被害者の再試行トラフィックだけで締め出しが継続する。

```
W1: 15 人中 使える Cookie を得たのは 0 人
W2（攻撃者は不在。被害者 15 人の再訪のみ）: 回復できたのは 10 人 / 15 人
>>> 攻撃が止まっても、再訪が 10 件/窓 を超える限り 5 人が締め出されたまま
```

窓は固定窓（`lib/rate-limit.ts` は `resetAt` を延長しない）なので**無限には続かない**が、
**10 分あたり `/apply` の来訪が 10 件を超えるサイトでは、超過分が常に締め出される定常状態になる。**
`docs/impl-p3b-fix2-notes-2026-07-29.md` §4 が「E2E の通常操作だけで窓内 23 回に到達」と
実測しているとおり、10 件/10 分は**通常利用で日常的に超える水準**である。

### 1.5 判定

- **「部分是正」というラベル自体は妥当**（クローズではない、という結論は正しい）。
- **内訳の申告は不正確。** 正しくは:

| 項目 | 正しい状態 |
|------|-----------|
| **自己維持の切断** | **未是正**（印付き利用者には `hasVerifiedSession` が到達しない / 実測） |
| 有効 Cookie を使った無コスト枠の収穫（REV-P3C1-001） | **是正済み・結線済み**（＝ SEC-057 の追加ハードニング） |
| 更新窓（NEW-003） | 是正済み・結線済み |
| 回復経路（`challengeToken`） | 正典関数のみ。**本番導線は存在しない** |
| 印の不可読化（SEC-068） | 完了 |

- **重大度は据え置き Medium**（想定配備 Vercel では発生しない / 可用性のみ / 最大 10 分の固定窓 /
  電話導線あり）。**非 Vercel 本番へ配備する判断が出た時点で High（ブロッカー）へ昇格**する。
- **P3-c2 のブロッカーにはしない。** 理由は §7。

## 2. SEC-057 は再び開いていないか（依頼事項 2）— **開いていない**

新設された 3 経路をそれぞれ攻撃してプローブで実測した。

| 経路 | 攻撃 | 実測 | 判定 |
|------|------|------|------|
| `already-verified` | 有効な Cookie を 200 回提示して発行を収穫 | **追加取得 0 枚**（発行そのものを行わないため） | ✅ 悪用不可 |
| **更新窓**（`isFormSessionRenewable`） | 失効間近（20〜30 分帯）の Cookie を**同じものを 200 回**提示。毎回 `renewable=true` になるので発行経路へ入る | **使える Cookie は 10 枚** = 無コスト枠そのもの。**枠を超えない** | ✅ 悪用不可 |
| `challengeToken`（同一トークン） | 同一トークンを 200 回 | **1 枚**（増幅率 1） | ✅ 契約どおり |

**更新窓は Senior が 2 度指摘した経路（REV-P3C1-001 / NEW-001）の隣にある新設経路**であり、
「有効な Cookie を提示すれば発行される」状態を意図的に作り直している。ここが無コスト枠を
迂回していれば SEC-057 は静かに再開していたが、**実測では枠に従属しており迂回していない**
（`unverified` の判定が `consume` の結果のみから決まり、`hasVerifiedSession` 分岐を抜けた
要求はすべて同じ枠を通るため）。

### ただし `challengeToken` は **P3-c2 で SEC-057 を 1 行で再開できる**

```
異なるトークン 200 種 → 使える Cookie = 200 枚
```

これは実装が正しく動いた結果である（トークン 1 つにつき 1 枚）。危険なのは**結線の仕方**で、
`challengeToken` の型は素の `string` であり、安全性は
「⚠️ **クライアントの自己申告を渡してはならない**」という**コメントだけ**に依存している。

このプロジェクトは同じ形の失敗を **SEC-021 → SEC-029 → SEC-030 → SEC-043 と 4 度**繰り返し、
`lib/form-session.ts:33-51` で「**名指しの警告コメントでは止められなかった。したがって
共有キーを返せない型にする以外に手段がない**」と自ら結論している（`PerRequesterKey`）。
**同じ結論をこの継ぎ目にも適用すべきである。**（→ P3-c2 条件 1 / §7）

## 3. SEC-061 / SEC-069（`TRUST_PROXY`）— 本番でレート制限を緩める経路になっていないか（依頼事項 3）

### 3.1 実測（プローブ 5）— Senior の 2 指摘はいずれも**実装で閉じている**

```
env信頼 + x-vercel-forwarded-for 偽装        → {"key":"unknown","trusted":false}      ← REV-P3C1-003 閉
env信頼 + append構成 XFF(9.9.9.9, 実IP) + x-real-ip → {"key":"203.0.113.7","source":"x-real-ip"} ← NEW-005 閉
env信頼 + x-real-ip 無し(上書き構成)          → {"key":"203.0.113.7","source":"x-forwarded-for"} ← 機能を壊していない
VERCEL=1 かつ TRUST_PROXY=1                  → {"source":"x-vercel-forwarded-for"}     ← platform 意味論を保持
TRUST_PROXY="yes"/"TRUE"/""/"0"              → trusted=false                          ← fail-closed
```

provenance（`platform` / `env` / `explicit`）を「trusted の真偽」と分離した設計は妥当であり、
**採用ヘッダの集合と順序を出所ごとに変える**という形は、この問題に対する正しい抽象である。

### 3.2 残余 A（**受容 / 運用条件**）: append 構成で `x-real-ip` 未設定なら偽装が通る

```
env信頼 + append構成で x-real-ip 未設定 → {"key":"9.9.9.9","trusted":true}  ← 攻撃者の名乗りを採用
```

`lib/http-guard.ts:147-153` と `docs/tech-stack.md` §4.5 に警告があり、
テストがコメントに `append` の語が残ることまで固定している（空振り検出済み）。
**実装で塞ぐことは原理的にできない**（前段の構成はアプリから観測できない）ので、
運用条件として受容する。**`TRUST_PROXY=1` を立てる際は `X-Real-IP $remote_addr` の併設を必須とすること。**

### 3.3 残余 B（**新規指摘 SEC-071**）: `options.trustProxy` は非 Vercel でも platform 意味論を与える

```
呼び出し側が {trustProxy:true} を渡した場合（非 Vercel）:
  x-vercel-forwarded-for 偽装 → {"key":"1.2.3.4","trusted":true,"source":"x-vercel-forwarded-for"}
```

§3.1 で閉じたはずの REV-P3C1-003 の攻撃が、**呼び出し方を変えるだけで完全に復活する。**
詳細と是正方針は §5 の SEC-071。

## 5. 新規指摘

### [SEC-071] `options.trustProxy` が非 Vercel でも `x-vercel-forwarded-for` を信頼させる／ルート pin が新規ルートを覆わない

- **重大度**: **Medium**（現状の 2 ルートは安全。**P3-c2 で新ルートを足す瞬間に到達可能**になる）
- **カテゴリ**: 認証・認可（信頼境界）/ D. Rate Limiting
- **場所**: `lib/http-guard.ts:201-219`（`resolveTrust` の `explicit` 分岐）、
  `tests/unit/trust-proxy-env.test.ts:455-468`（ルート pin のハードコード列挙）
- **説明**: `resolveTrust` は `explicit !== undefined` のとき provenance を
  `onPlatform ? 'platform' : 'explicit'` とする。`'explicit'` は
  `provenance === 'env'` に**一致しない**ので、`resolveClientIp` は `PLATFORM_IP_HEADERS`
  （`x-vercel-forwarded-for` を含む）を使う。**実測で偽装が成功する**（§3.3）。

  `TRUST_PROXY` という env が**新設された今**、
  `resolveClientIp(req, { trustProxy: env.TRUST_PROXY })` は
  **極めて自然に書かれうる形**である（env を読んで渡す、という素直な発想）。
  防いでいるのは (a) docstring の警告と (b) **2 つのルートパスをハードコードした pin** だけで、
  **P3-c2 が追加する `app/api/uploads/route.ts` は (b) の列挙に含まれない。**
- **影響**: 非 Vercel 本番で攻撃者が `X-Vercel-Forwarded-For:` を付けるだけで
  `trusted: true` かつ**自分で選んだ key** を得る ⇒
  発信元軸のバケット無限生成 / `lib/form-session-issue.ts:254` の `!clientIp.trusted` ガードが外れて
  **SEC-057 の是正が丸ごと無効化** / `auth.ts` のログイン IP 軸で被害者を騙り管理者を締め出す（SEC-030 の再来）。
  これは実装記録 `lib/http-guard.ts:94-101` が**自分で列挙している影響そのもの**である。
- **修正方針**（安い順）:
  1. **pin を列挙からグロブへ**: `app/api/**/route.ts` を走査して `trustProxy` の不在を検査する。
     1 行の変更で P3-c2 以降の全ルートを自動的に覆う。**最優先。**
  2. **`explicit` に platform 意味論を与えない**: `provenance: onPlatform ? 'platform' : 'env'` とする。
     `tests/unit/client-ip.test.ts` の既存 6 件は `x-forwarded-for` / `x-real-ip` しか使っていないため、
     この変更で壊れるのは「明示引数で `x-vercel-forwarded-for` を採る」テストのみ（存在するなら、
     それはこの欠陥を固定しているテストである）。
  3. `ResolveClientIpOptions` を `{ trustProxy: boolean; provenance: 'test-only' }` のような
     **書くのが面倒な型**にする（`PerRequesterKey` と同じ手法）。
- **参考**: CWE-348（Use of Less Trusted Source）/ OWASP A05:2021。

### [SEC-072] `verifyFormSessionValue` は未検証ラベルを試さない — コメント・実装記録と実コードが食い違う

- **重大度**: **Low**（実挙動は**記述より安全**。問題は記録の誤りとその帰結）
- **場所**: `lib/form-session.ts:249-264`、`docs/impl-p3c1-notes-2026-07-29.md`「SEC-068」節
- **説明**: コメントは「**未検証ラベルでも一致しないかを確かめる**」と書き、実装記録は
  「検証は**最大 2 回 HMAC を計算する**」「印の付いた値と偽造値は 2 回」と書いているが、
  **実コードは検証済みラベルで 1 回計算し、一致しなければ即 `null` を返す。**
  未検証ラベル（`HKDF_INFO_UNVERIFIED`）は `sign()` の発行側からしか使われない。
- **なぜ Low だが記録するのか**: 実挙動のほうが**優れている**（常に 1 回 = 印付きと偽造で
  計算量が変わらない＝タイミング差が出ない）。しかし記述を信じた次の実装者が
  「コメントどおりに 2 回目の検証を足す」と、**印付きと偽造を計算時間で区別できるオラクル**を
  新設することになる——SEC-068 が消したはずの状態オラクルの復活である。
- **P3-c2 への帰結（こちらが本題）**: この設計の必然として、**サーバーは「この利用者は印付き」と
  「この Cookie は偽造・破損」を区別できない。** したがって P3-c2 で回復導線 UI
  （「CAPTCHA を解けば回復します」）を出そうとすると、区別する経路を新設したくなる。
  **新設すればオラクルが戻る。** 回復導線は「印を検出して出し分ける」のではなく
  **「Tier B が続いたら誰にでも出す」**（RV-P3B-009 の既存方式）で設計すること。
- **修正方針**: コメントと実装記録を実コードに合わせる。2 回検証を「足す」方向へ直さない。

### [SEC-073] cron 認可の試行計数が、上限到達後に**毎リクエスト** warn を出す（ログ増幅）

- **重大度**: **Low**
- **場所**: `lib/cron-auth.ts:126-136`（`recordFailure`）
- **説明**: `consume` が `success:false` を返すたびに `logger.warn` を出す。
  カウンタは単一の定数キー（`'cron:auth-failure'`）なので、上限 10 に達した後は
  **窓が明けるまで全ての失敗要求が 1 行ずつログを出す**。
- **影響**: 未認証の第三者が**自分の要求レートに比例した量のログ**を書かせられる。
  ホスト型ログ基盤では課金・保持枠の消費であり、同時に**本物の攻撃の兆候を埋もれさせる**
  ——本項目の成果物が「観測」である以上、観測そのものを潰せるのは目的に反する。
  このプロジェクトは同型の増幅を SEC-023 / SEC-031 / SEC-041 で 3 度扱っている。
- **修正方針**: 窓ごとに 1 回だけ出す。`consume` の結果から「ちょうど上限を跨いだ瞬間」
  （`limit - remaining === limit + 1` に相当する遷移）を検出するか、
  直近に出力した `resetAt` を保持して同一窓での重複出力を抑える。
  **抑制ではなく検知が目的なので、1 窓 1 行で情報は失われない。**

### [SEC-074] 非公開コースへの申込が受理される（`lookupCourse` に `published` 条件が無い）

- **重大度**: **Low**
- **場所**: `app/api/applications/route.ts:171-191`（`lookupCourse`）
- **説明**: 実装記録が自己申告しているとおり、照合条件に `published` が入っていない。
  非公開（下書き・準備中・終了）のコース ID を知っている第三者は、そのコースを指定して
  申込を成立させられ、**`priceFromSnapshot` にも非公開の価格が記録される。**
  `application-course-fk.int.ts:178` は seed に非公開コースが無ければ何も測らない。
- **影響**: 公開前の価格・コース名が受付記録として確定する。直接の情報漏えいではない
  （攻撃者は自分が指定した ID の結果を応答からは受け取らない）が、
  **業務上は「売っていない商品の注文が成立する」状態**であり、F-017 の受信管理に不正な行が混ざる。
- **修正方針**: 仕様判断が要る（Spec Agent 案件）。`published: true` を照合条件に足して 422 にするのが
  自然だが、「公開停止中のコースに既存の申込がある」場合の扱いを先に決めること。
  **本監査は実装欠陥ではなく仕様の空白として報告する。**

## 6. SEC-063 の繰越記述は妥当か（依頼事項）— **妥当**

`docs/security-audit.md` :3270 を範囲読みで確認した。REV-P3C1-004 の 3 条件を満たしている:

1. 監査票の当該行に「**P3-c1 では対応しない（明示的に繰越）**」と書かれている。
2. **訂正後の契約**（`count` は `current + 1`）が繰越先（`test-design-p3c1` §10）へ引き継がれている。
3. 繰り越した**理由**（Lua で 1 往復に畳むとフェイク Redis が解釈できず観測点を失う／費用対効果）が書かれている。

**加えて、残余の実害を独立に確認した。** `lib/kv.ts:99-115` は
`INCR` の戻り値が 1 のときと **TTL が失われたときにのみ** `PEXPIRE` を張る。
すなわち**上限到達後に INCR が続いても固定窓は延びない**——
「正規利用者が恒久的に締め出される」形にはなっていない。
残余は「窓内でカウンタが上限を超えて単調増加する」ことのみで、
判定にも窓の長さにも影響しない。**`任意` という格付けは実態に合っている。**

## 7. P3-c2（免許証写真アップロード）着手可否

### **着手可。新規 Critical / High は 0 件。**

前回監査が唯一のブロッカーとした SEC-057 は閉じたまま維持されており（§2 で能動的に確認）、
P3-c1 が閉じるべきとした前提項目（SEC-058 / 060 / 061 / 064 / 065 / 070 と SEC-046）は
**いずれも実装で閉じている**。SEC-067 は継続だが可用性のみ・縮退構成限定であり、
`.claude/skills/security.md` のブロック基準（Critical/High）に該当しない。

### 申し送る条件 5 件（**1 と 2 は P3-c2 のスコープ内で必ず**）

1. **`challengeToken` を素の `string` のまま結線しないこと。**
   プローブ 4 の実測どおり、**異なるトークンを 200 種渡せば印は 200 回外れる**。
   安全性が「コメントを読むこと」に依存している状態で結線すると、SEC-057 が全面的に再開する。
   `verifyTurnstile` の戻り値からしか作れない branded type
   （`VerifiedChallengeToken`＝`PerRequesterKey` と同じ手法）にしてから結線すること。
   **このプロジェクトはコメントで 4 度止められなかった実績を自分で記録している。**
2. **`usedChallengeTokens` を KV 実装へ結線してから回復導線を公開すること。**
   既定は**プロセス大域のメモリ**であり、複数インスタンスでは
   「1 回解いた CAPTCHA をインスタンス数だけ流用できる」＝ 増幅率がインスタンス数になる。
   REV-P3C1-002 が固定した「増幅率 1」は**単一インスタンスでしか成立していない。**
3. **`trust-proxy-env.test.ts:455` のルート pin をグロブ走査へ変えること**（SEC-071 修正方針 1）。
   新しい公開ルートを足す P3-c2 は、この pin が列挙のままだと**最初の未カバー事例**になる。
4. **SEC-067 は継続中であることを前提に設計すること。**
   uploads は同じ `verifyFormSessionValue` を Tier B 判定に使う想定であり、
   縮退構成では**写真アップロードも同じ締め出しを受ける**。滞在時間が長いぶん影響は申込より大きい。
   NEW-003（更新窓）は 30 分失効を緩和するが、**印による締め出しは緩和しない。**
   回復導線 UI は SEC-072 のとおり「印を検出して出し分ける」形にしないこと。
5. **`prismaErrorLogFields` に返却フィールドを増やす場合**、
   `prisma-error-log.test.ts:200`（PII セーフラッパの列挙が効くこと）は
   実装記録の変異検算どおり**その増えたフィールドを守らない**。増やすならテストも足すこと。

## 8. 記録の正確性について（ID を割り当てない指摘）

監査の判断材料そのものに関わるので記録する。

1. **実装記録の「未解決 1 件」は既に解消している。**
   `tests/unit/form-session-degraded-recovery.test.ts` を単独実行して **29/29 green** を確認した。
   :392 のテストは実装記録が §提案 で示した形（`isUnmarked` を使わず**発行時刻と同じ時刻で検証**）に
   修正済みである。**この修正は妥当**——測りたい性質（TTL を跨げば同一トークンでも初回扱い）は
   完全に保たれ、Cookie 寿命の判定と混ざらなくなっている。アサーションの弱体化ではない。
   実装記録の「テストは変更していない / 1 failed」という記述は**現状と食い違う**ので、
   完了報告に転記する際は現状（826 全パス）に合わせること。
2. **§1.5 のとおり、SEC-067 の内訳の申告が実測と食い違う。**
   「自己維持の切断＝結線まで完了」は**成立していない**。
   `docs/phase-status.md` / 監査票へ転記する際は、
   **「有効 Cookie を使った無コスト枠の収穫を封じた（REV-P3C1-001）。自己維持は未是正」**と書くこと。
3. **SEC-068 の「最大 2 回 HMAC」は事実でない**（§5 の SEC-072）。

いずれも**隠蔽ではなく取り違え**であり、実装記録全体の誠実さ
（SEC-046 の「総当たりを抑制しない」、変異検算による空振り検出、
「1 件だけ弱い」の自己申告）は**このプロジェクトで最も価値のある習慣**として評価する。
本監査が指摘を出せたのは、その記録が具体的だったからである。
